# 진행 방향

2026-10-11

## 목적의 가설

BOSS가 실제 제품을 만들면서 목적·변경·검증·효과를 연결하고, 반복 확인과 수습의 부담을 줄인다. 이는 검토할 Mission 가설이며 도구 설치나 작업량 증가를 목적 달성으로 간주하지 않는다.

## 기술 선택

웹/API는 Elixir와 Phoenix로 구성한다. 태극의 로컬 상태 저장에는 SQLite를 사용한다. 웹앱/API는 Elixir를 유지한다. 설치·패키징은 Python 표준 라이브러리로, CLI의 측정·증거 검증은 Rust로 구현한다. 승인된 흐름 역할은 TOML에 역할별 모델·추론 설정을 지정할 수 있으며, 명시하지 않은 역할과 전역 Codex 설정은 기존 설정을 상속한다.

## 초기 범위

초기 범위는 리서치 원본과 출처·검토 범위 보존, Codex 역할 6개와 스킬 10개, 재실행 가능한 설치 스크립트, 측정과 증거 검증 CLI, 로컬 웹/API 기반이다. 이 흐름 보완에서 역할 3개를 추가해 현재 역할 수는 9개이며 스킬 10개는 유지한다. 웹 초기 화면은 작업 방식과 기능 상태를 안내한다. 수집 자료의 제안을 모두 승인 규칙으로 승격하지 않는다.

## 단계

1. 초기 구성을 설치하고 실패·충돌·미확인 사례로 보조 도구를 검사한다.
2. 실제 제품 하나의 핵심 사용자 흐름과 수용 사례를 정한다. 제품을 아직 임의로 선정하지 않는다.
3. 그 흐름에 현재 에이전트와 스킬을 적용하고, 기존 도구를 활용해 작은 변경을 전달한다.
4. 제품 문제와 개발 체계 문제를 나눠 회고한다. 반복된 누락·중복 실행·인계 오류만 도구로 보완한다.
5. SQLite 상태 API로 작업·근거·revision·실행 자원 소유권을 기록한다. 모델 실행과 실제 프로세스 제어는 별도 실행자에 남긴다. 실제 공유 호출 필요가 생기면 기존 CLI 로직 위에 MCP를 노출한다.

## 완료와 관측

초기 구성 완료는 파일 생성·설치·실행 검사로 판단한다. 역할 TOML 설정은 역할 발견이나 모델 실행을 증명하지 않는다. 에이전트 신뢰도, 사용자 효과와 Mission 타당성은 실제 작업에서 평가한다. 배포 권한과 운영 복구 조건은 프로젝트별로 정한다.
