# 에이전트 스킬 CLI MCP 도구 분담안

2026-10-11 · 설계 제안 · 구성과 도구 채택 전

## 분류 기준

에이전트는 목적과 맥락을 해석하며 다음 행동을 판단하는 책임을 맡는다. 스킬은 그 책임을 수행할 때 따르는 반복 절차와 기록 형식을 제공한다. 외부 도구는 정확한 계산·실행·조회·영속 상태·권한 통제를 담당한다.

세 가지는 같은 작업의 서로 다른 층이다. ‘검증’을 통째로 한 종류에 배정하지 않는다. 에이전트가 어떤 증거를 확인할지 판단하고, 스킬이 검사 선택·기록 순서를 안내하며, 도구가 검사와 상태 조회를 실행하는 구성을 제안한다. 역할 수와 실제 프로세스·모델 수는 별도로 결정한다.

| 질문 | 배치 |
|---|---|
| 목적·맥락·대안을 읽고 다음 행동을 선택해야 하는가? | 에이전트 책임 |
| 여러 작업에서 같은 절차·양식·주의점을 적용하는가? | 스킬 |
| 같은 입력에서 정확한 계산·검증·실행 결과가 필요한가? | 도구 |
| 저장·잠금·시간 한도·접근 권한을 실제로 강제해야 하는가? | 실행 시스템 또는 도구 |
| 누구의 어떤 변화가 가치 있는지, 기준을 바꿀지 결정하는가? | 제작자·사용자의 판단. 에이전트는 근거와 대안 제시 |

스킬에 ‘권한을 지켜라’라고 적는 것과 실제 접근 통제는 다르다. 에이전트의 ‘통과’ 문장과 검사 실행 결과도 다르다. 프롬프트가 실행 시스템의 보장을 대신하지 않도록 경계를 둔다.

## 기존 열 가지 특징의 분담

| 특징 | 에이전트가 판단할 내용 | 스킬로 만들 절차 후보 | CLI MCP 및 실행 시스템이 제공할 기능 |
|---|---|---|---|
| 목적을 작업 가설로 연결 | 사용자 문제·예상 효과·대안·보류 | 목적–요구–수용 사례 연결 | 승인된 사용자 자료·사용 결과 읽기, 계약 저장 |
| 문제 후보 발견 | 신호의 의미·실제 문제·조사 우선순위 | 증거 조사와 후보 축소 | 코드·이력 검색, 실패 기록·운영 지표 조회 |
| 검증 계획 구성 | 보호 조건·위험·검사 조합·제외 근거 | 작업 속성별 검증 계획 | 계약 형식·참조 누락 검사, 검사 목록 조회 |
| 재현과 원인 조사 | 원인 가설·실험 선택·가설 수정 | 최소 재현과 반증 기록 | 격리 실행, 시간 제한, 데이터 준비·정리, 결과 조회 |
| 작은 변경 | 구현 대안·영향·수정 순서 | 범위 고정·동작 보존·변경 기록 | 작업 사본, diff·빌드·검사·대상 버전 확인 |
| 교차 검증 | 판정 근거·독립성·미확인 범위 | 증거 조합·결과 대조 | 기존 검사기 실행·구조화 결과·원시 증거 보존 |
| 측정 해석 | 원인 후보·편향·추가 관측 | 지표 정의·측정기 검증·판정 | 집계·분포·집합 비교·측정 snapshot |
| 구조 정리 | 실제 변경 부담·현상 유지·정리 시점 | 기능 사이 구조 점검·종료 | 참조·이력 분석, 동작 비교·회귀 검사 실행 |
| 기록과 재개 | 결정 요약·미완료 범위·다음 행동 | 인계·재개 전 실제 상태 확인 | 영속 기록·잠금·취소·실행 상태 조회 |
| 효과와 규칙 진화 | 사용자 효과·재발·개정 필요 | 효과 대조·구/신 기준 비교 제안 | 배포·사고·사용 기록 연결, 승인된 기준 버전 조회 |

## 에이전트 역할 후보

### 기본 세 역할

| 역할 | 책임과 결과 | 권한 경계 |
|---|---|---|
| 개발 책임자 | 목적 가설과 승인 요구에 연결해 일감·범위·검증 계획을 정리하고, 증거에 따라 다음 단계 선택 | Mission·규칙을 혼자 확정하지 않음. 승인된 요구를 재해석해 확장하지 않음 |
| 구현자 | 문제 재현, 대안 비교, 작은 패치, 관련 검사와 인계 | 범위·합격선 변경을 분리. 실제 권한은 도구가 제한 |
| 검증자 | 안정된 변경 대상에서 기대값 근거·검사 범위·실제 효과·증거 공백을 검토 | 구현자의 완료 주장을 그대로 승인하지 않음. 검사 기준을 완화하지 않음 |

검증 역할 분리는 다른 관점에서 검토하기 위한 것이다. 같은 모델과 같은 기대값을 공유하면 같은 오류를 놓칠 수 있다. 별도 에이전트를 둔 것만으로 독립 검증이 성립하지 않으며, 승인 사례와 실제 실행·다른 관측 지점의 증거가 필요하다.

### 필요가 생길 때 분리할 역할

| 역할 | 분리할 조건 | 기본 책임과의 관계 |
|---|---|---|
| 제품 관측·학습 | 사용 결과·사고·사용자 의견을 지속적으로 조사할 일이 쌓임 | 처음에는 개발 책임자가 효과 대조 스킬로 수행 |
| 구조 검토 | 여러 변경의 결합·변경 부담을 검토할 책임이 반복됨 | 처음에는 검증자에게 별도 검토 관점으로 부여 |
| 규칙 검토 | 누락·오탐·기준 변화의 근거를 비교하는 일이 반복됨 | 처음에는 개발 책임자가 개정안 스킬로 수행 |
| 전달·운영 검토 | 배포 대상·복구 경계·관측 창을 별도로 관리해야 함 | 초기에는 검증 계획과 전달 스킬에 포함 |

이 역할들을 모두 상시 실행하거나 새 모델 인스턴스로 만들 필요는 없다. 같은 역할을 별도 실행 문맥으로 수행할지, 여러 역할을 분리할지는 실제 작업량·간섭·비용으로 결정한다. 지속 실행과 예약은 스케줄러·실행 시스템의 책임이다.

## 스킬 후보

| 이름 후보 | 입력 | 반복 절차와 결과 |
|---|---|---|
| work-contract | 목적 가설·요구·권한·대상 | 범위·비목표·보존 조건·완료 증거·미결정 사항 정리 |
| investigate-and-reproduce | 문제 신호·관련 코드/기록 | 사실/가설 분리 → 원인 후보 → 최소 재현 → 다음 조사 |
| implement-small-change | 작업 계약·재현·현재 버전 | 대안 비교 → 작은 변경 → 관련 검사 → 실제 인계 |
| plan-cross-verification | 변경 속성·위험·승인 기준 | 주 검사·다른 증거·제외 이유·환경·복구 조건 선택 |
| verify-measurement | 지표 정의·원시 사건·측정식 | 사건 단위·분모·창 확인 → 고정 반례 → 수집/계산/판정 대조 |
| inspect-changeability | 반복 변경 부담·현재 작업 | 정리 필요·시점 → 최소 정리 → 동작 보존·종료 확인 |
| verify-delivery-effect | 검사 증거·배포 대상·권한 | 산출물 동일성 → 허용 전달 → 업무·데이터 효과 → 회복 확인 |
| resume-with-evidence | 작업 기록·실제 대상 | 버전·권한·진행/외부 효과 조회 → 재실행 여부 → 다음 단계 |
| propose-rule-change | 누락·오탐·환경 변화 | 재현 → 구/신 기준 차이 → 영향·전환안 → BOSS 확인 |
| learn-from-outcome | 사용·사고·개입·목적 가설 | 산출/사용 결과/목적 연결 → 반례·재발 → 다음 가설 |

이들은 절차 이름 후보다. 지금 열 개를 모두 설치하는 결정은 아니다. 실제 작업에서 함께 쓰는 절차는 하나의 스킬과 보조 자료로 묶을 수 있다. 문서에 있는 38개 지표도 스킬을 38개로 분리하지 않고 선택 지침과 측정 정의 자료로 참조한다.

## 외부 도구 후보와 제작 범위

### 기존 도구를 활용할 기능

코드·이력 검색, 빌드·테스트·정적 검사, 속성·계약·부하·모델 검사는 기존 도구의 실행 기능을 우선 검토한다. 운영 측정 저장소와 배포 시스템도 이미 제공하는 조회·실행·이력을 활용한다. Pact·JMeter·PropEr·TLC·Prometheus 등 앞서 나온 이름은 후보이며 현재 프로젝트의 채택 목록이 아니다.

기존 도구가 필요한 입력·결과·권한·재현성을 제공한다면 직접 사용한다. 결과 형식이나 실행 통제가 부족하면 얇은 어댑터를 만든다. 검증 엔진 전체를 다시 만드는 것과 어댑터 제작은 구분한다.

### 자체 제작 또는 어댑터가 필요한 기능 후보

| 기능 | 필요한 계약 | 재사용과 자체 제작의 경계 | 실제 검증 |
|---|---|---|---|
| 작업·증거 기록 | 작업·규칙·아티팩트·검사·효과의 ID와 버전 연결, 누락·미확인 보존 | 파일·기존 작업 시스템으로 시작. 반복되는 연결 오류가 있으면 검증/조회 어댑터 | 오래된 결과·누락 참조·아티팩트 불일치를 거부 |
| 검사 실행과 결과 정규화 | 입력·대상·도구 버전, 실행 ID·시간·원시 출력·판정 이유 | 기존 CLI를 감싸 공통 결과 제공. 빌드·검사 엔진은 재사용 | timeout·비정상 종료·부분 결과·skip을 통과로 만들지 않음 |
| 측정 조회·계산 | 서비스·사건 단위·시간창·쿼리 버전·데이터 품질·집계 결과 | 기존 조회 API와 계산 우선. 공통 품질 검사/업무 집합 대조가 없을 때 제작 | 0 분모·누락·중복·불균등 집계·reset·시간 경계 사례 |
| 업무 효과 대조 | 요청/업무/시도와 실제 저장·외부 효과 연결, 확정/불명 결과 | 제품별 read API·원장 활용. 필요한 대조 로직은 해당 제품에 구현 | 응답 유실 후 성공, 부분 성공, 중복, 진행 중 결과 |
| 실행 수명과 재개 통제 | 실행 ID·상태·예산·잠금·취소·영속 기록·효과 조회 | 기존 실행기의 보장을 확인. 없는 기능만 보완 | 중단 뒤 재개, 중복 실행 경쟁, 취소 뒤 남은 효과 |
| 전달·복구 연결 | 정확 아티팩트·환경·배포 이력·상태·회복 조건 | 기존 배포/운영 도구 어댑터. 제품별 데이터 복구는 별도 | 잘못된 버전·권한 밖 대상·혼합 버전·회복 미완료 |
| 승인 기준과 권한 검사 | 신뢰할 수 있는 승인 출처·버전·주체·대상·행동 | 기존 정책/인증 계층 사용. 모델 출력으로 승인 기록 생성 금지 | 미승인 기준·낡은 승인·대상 변경·권한 초과 |

작업 기록의 해시는 아티팩트 식별과 변경 탐지에 쓸 수 있다. 해시만으로 기록의 진실성·독립성·승인 여부가 보장되지는 않는다. 도구가 자동 판정할 수 있는 조건과 의미 검토가 필요한 조건을 분리한다.

업무 효과 대조는 해당 제품의 저장·실패·재시도 의미를 알아야 한다. 범용 실행 도구가 임의로 ‘이 작업은 성공했다’고 정의하지 않는다. 제품별 검증 함수를 연결하고, 연결이 없으면 효과 확인 불가로 남긴다.

## CLI와 MCP를 선택하는 기준

CLI와 MCP는 기능에 접근하는 인터페이스 선택이다. 동일한 실행·검증 로직을 공유하도록 설계할 수 있으며, 둘을 별도 엔진으로 만들 필요는 없다.

| 조건 | 우선 검토할 인터페이스 |
|---|---|
| 로컬 파일·빌드·검사, 개발자 재현, CI 실행 | CLI |
| 도구 목록·구조화 인자·결과를 에이전트가 발견해 사용, 공유 서비스 연계 | MCP |
| 오래 걸리는 실행 | 실행 ID를 반환하고 상태 조회·취소·결과 조회 제공. CLI/MCP 모두 가능 |
| 권한·대상 통제 | 두 인터페이스 뒤의 공통 실행·정책 계층에서 강제 |

로컬 작업은 CLI부터 시작하고, 여러 실행 주체가 반복 사용하며 MCP 연결의 이득이 확인되면 같은 기능을 MCP로 노출하는 순서를 제안한다. 기존에 적합한 MCP가 있다면 우선 활용할 수 있다. MCP 제공 자체가 인증·승인·격리·멱등성을 완성하는 것은 아니다.

결과 계약에는 실행의 성공 여부와 검사 대상의 판정, 데이터 품질을 구분한다. 예를 들어 명령이 정상 종료했지만 검사에서 결함을 찾았거나, 쿼리는 성공했지만 데이터가 비었을 수 있다. 실제 도구별 exit code 의미는 어댑터에 명시한다.

## 역할 사이의 최소 계약

공유 계약은 다음을 연결한다.

```yaml
work:
  id: <work id>
  purpose_hypothesis: <expected user effect>
  requirement_version: <approved requirement>
  rule_version: <approved rule>
  scope: <target and allowed change>
  preserve: <invariants and existing behavior>
verification:
  checks: <selected checks and oracle sources>
  artifact: <exact target identity>
  evidence: <actual runs and raw results>
  quality: <data validity and gaps>
  verdict: <PASS, FAIL, UNKNOWN, NOT_RUN, NOT_APPLICABLE>
execution:
  operation_id: <when an effectful operation was attempted>
  actual_state: <queried target state>
  authorization_ref: <trusted approval or policy reference>
  limits: <time, cost, retries and effects>
next:
  action: <continue, investigate, deliver, observe or propose>
  reason: <evidence and unresolved conditions>
```

에이전트가 쓰는 실행 계획과 도구가 확인한 실행 기록을 분리한다. 수정·재빌드·규칙 버전 변경 뒤에는 영향받는 검증을 다시 실행한다. 텍스트 요약만 전달하지 않고 실제 아티팩트·증거 참조를 함께 넘긴다.

## 처음 적용할 구성

작은 실제 작업 하나에서 개발 책임자·구현자·검증자의 책임을 구분하고, 작업 계약·작은 수정·교차 검증 절차부터 적용한다. 검색·빌드·검사는 기존 도구를 사용하고, 결과 연결이 부족하면 최소 어댑터만 추가한다.

실행 중단·응답 유실·운영 배포가 포함되면 해당 상태 조회·재개·권한·복구 기능은 뒤로 미루지 않는다. 그런 경계가 없는 로컬 변경에는 운영 실행 플랫폼을 미리 만들지 않는다. 사용 효과 관측은 별도 무인 서비스가 없어도 검토 주기와 기록으로 시작할 수 있다.

첫 적용의 결과에서 반복되는 누락·오탐·인계 오류·중복 실행을 확인한 뒤 도구 제작 범위를 정한다. 실제 도구와 에이전트 능력은 정상·실패·중단·권한 초과·미확인 사례로 평가한다.
