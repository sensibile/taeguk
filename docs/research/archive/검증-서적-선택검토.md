# 검증 서적 선택 검토 기록

2026-10-05 · 선택 검토 완료 · 정독 및 도구 실행과 구분

## 목적과 읽기 범위

BOSS가 요청한 것은 작업 속성에 맞춰 검증 도구와 지표를 선택하고 교차 확인하는 지침이다. 이번에는 여섯 권에서 방법의 적용 조건, 판단 근거, 한계까지 확인할 수 있는 구간을 골랐다. 책 전체 정독, 모든 그림의 시각 확인, 예제 전체 실행은 하지 않았다. 아래의 ‘읽음’은 해당 본문을 확인했다는 뜻이며 도구 실행을 뜻하지 않는다.

앞서 전체 읽기를 완료한 구현 기술 여섯 권과 이번 검증 서적 여섯 권은 별도 묶음이다. 기존 [전체 읽기 기록](전체-읽기-기록.md)의 완료 범위를 이번 책들에 확대하지 않는다.

선택 검토의 종료 조건은 각 방법에 대해 ① 찾으려는 문제 ② 적용 전제 ③ 관찰할 증거와 지표 ④ 함께 써야 할 다른 검사 ⑤ 통과로 보장하지 못하는 범위를 설명할 수 있는 것이다. 아래 추출 내용은 이 조건을 충족하지만 실제 제품에서의 효과는 아직 검증하지 않았다.

## 1. Testing Web APIs — Mark Winteringham

[O'Reilly 원문](https://learning.oreilly.com/library/view/testing-web-apis/9781617299537/)

| 범위 | 확인 수준 |
|---|---|
| 7장 테스트 전략 | 본문 전체: 품질·위험·활동 연결, 테스트 가능성, 계획과 피드백 |
| 9장 계약 테스트 | 9.1, 9.2, 9.2.1, 9.5와 요약. 9.3·9.4 구현 튜토리얼은 제외 |
| 10장 성능 | 10.1 전체, 10.3 전체, 10.4와 요약. 10.2 JMeter GUI 튜토리얼 제외 |
| 11장 보안 | 도입, 11.1·11.1.1, 11.2 도입·11.2.1, 11.2.3·11.3. 11.1.2 STRIDE와 11.2.2 실습은 일부 확인 |

**추출:** 품질 위험에서 검사 활동을 도출하고, 계약·성능·보안 검사를 별도 증거로 다룬다. 소비자 계약은 실제 사용 필드를 확인하며, 실제 API 호출의 비즈니스 효과까지 보장하지 않는다. 부하는 사용자 흐름·비율·데이터·지속 시간·자원 관측을 함께 설계한다. 보안은 자산과 신뢰 경계에서 공격 시나리오를 만들고 정적 검사·의존성 검사·실제 요청을 조합한다.

**적용 주의:** 책의 응답시간·백분위 예시를 공통 합격선으로 채택하지 않는다. 4xx 전부를 서버 장애로 집계하지 않는다. API가 HTML을 직접 반환하지 않아도 저장된 내용이 UI에 표시되면 XSS 경로가 생길 수 있다. 부하 중 CPU와 지연의 동반 상승만으로 원인을 확정하지 않는다. 도구의 예제 버전을 현재 권장 버전으로 간주하지 않는다.

## 2. Explore It! — Elisabeth Hendrickson

[O'Reilly 원문](https://learning.oreilly.com/library/view/explore-it/9781941222584/)

**읽음:** 2장 도입, Charter an Expedition, A Simple Charter Template, Good Charters. 5장 도입, Never and Always, Alternative Resources, Approximations. 해당 본문은 읽었으며 연습문제와 이미지에만 있는 예시는 별도 검증하지 않았다.

**추출:** 탐색을 ‘대상·수단·알아내려는 정보’로 한정한다. 요구사항의 항상/절대 조건, 내부 일관성, 적합한 외부 기준, 근사값과 결과의 특성으로 판정 근거를 다양화한다. 명확한 기대값이 없는 작업도 검증을 포기하지 않고 관찰 가능한 제약을 찾는다.

**적용 주의:** 유사 제품은 요구사항의 대체물이 아니다. 왕복 변환이 맞아도 양방향이 같은 오류를 공유할 수 있다. 범위 안의 난수가 나왔다고 분포나 보안 난수 품질을 보장하지 않는다. 탐색에서 나온 새 기대 행동은 사용자 확인 없이 기존 요구사항으로 승격하지 않는다.

## 3. Property-Based Testing with PropEr, Erlang, and Elixir — Fred Hebert

[O'Reilly 원문](https://learning.oreilly.com/library/view/property-based-testing-with/9781680506556/)

**읽음:** Part III 도입, 9장 도입, Laying Out Stateful Tests, How Stateful Tests Run, Testing Parallel Executions 전체. Writing Properties는 앞부분, Testing a Basic Cache는 위치 확인만 했다. 기본 캐시 구현 및 나머지 장 전체는 읽지 않았다.

**추출:** 참조 상태, 명령 생성기, 사전조건, 상태 전이, 사후조건으로 상태 변화의 검사를 구성한다. 실패를 재현할 수 있는 짧은 명령열로 축소한다. 병렬 명령의 결과를 허용 가능한 순차 실행과 비교하고, 명령 분포를 기록해 특정 경로가 거의 생성되지 않는 문제를 확인한다.

**적용 주의:** 참조 모델에 제품 구현을 복사하면 같은 오류를 놓친다. 축소 과정에서도 사전조건을 유지해야 한다. 많은 무작위 실행이 특정 스케줄을 보장하지 않는다. 책의 yield·VM 설정은 테스트 환경에서의 탐지 방법이며 운영 코드의 수정 지침이 아니다. Concuerror 같은 스케줄 탐색도 탐색 범위와 환경을 명시해야 한다.

## 4. Systems Performance, Second Edition — Brendan Gregg

[O'Reilly 원문](https://learning.oreilly.com/library/view/systems-performance-2nd/9780136821694/)

**읽음:** 2.5.9 USE, 2.5.10 RED, 2.5.11 Workload Characterization, 2.8.2 Averages, 2.8.3 Standard Deviations, Percentiles, Median. 12.3.1 Passive Benchmarking, 12.3.2 Active Benchmarking, 12.3.3 CPU Profiling, 12.3.4 USE Method, 12.3.7 Ramping Load, 12.3.8 Sanity Check, 12.3.9 Statistical Analysis, 12.3.10 Benchmarking Checklist. 나머지 절과 전체 그림의 시각 검토는 제외했다.

**추출:** 서비스의 요청률·오류·지연(RED)과 자원의 사용·포화·오류(USE)를 연결한다. 부하 발생기와 대상 시스템을 모두 관측한다. 결과를 해석하기 전에 실제 측정 대상, 캐시, 자원 제한, 단위, 물리적 상한, 반복 편차를 확인한다. 프로파일은 원인 후보를 좁히는 증거다.

**적용 주의:** 평균은 꼬리 지연과 짧은 포화를 숨긴다. 여러 노드의 p99를 평균 내서 전체 p99로 쓰지 않는다. CPU 사용률 100%가 모든 종류의 자원에서 동일한 의미는 아니다. 호스트 여유 자원과 컨테이너 제한을 구분한다. strace 같은 관측 도구의 오버헤드가 측정값을 바꿀 수 있다. Linux 도구는 권한·커널·환경 지원을 확인한 뒤 선택한다.

## 5. Chaos Engineering — Casey Rosenthal, Nora Jones

[O'Reilly 원문](https://learning.oreilly.com/library/view/chaos-engineering/9781492043850/)

**읽음:** 3장 도입, What Chaos Engineering Is, Experimentation Versus Testing, Verification Versus Validation, What Chaos Engineering Is Not와 Breaking Stuff 앞부분. Advanced Principles 중 Build a Hypothesis Around Steady State Behavior, Vary Real-World Events, Minimize Blast Radius 전체. 12장 도입, Choosing Experiments, Random Search, Observability: The Opportunity 전체와 전문가 관련 논의 일부. 16장 도입·Where Continuous Verification Comes From, Types of Continuous Verification 대부분, Performance Testing·Data Artifacts·Correctness 전체. 나머지 사례·운영 구현은 제외했다.

**추출:** 정상 상태를 비즈니스 결과로 정의하고 장애가 생겨도 유지될 것이라는 가설을 시험한다. 트레이스와 의존 관계에서 실제 영향 경로를 고른다. 지연·일부 실패·데이터 손실 등 서로 다른 장애를 구별하고 실험 중단 조건과 복구 증거를 남긴다. 배포 후 성능·산출물·정확성 관측도 개발 검증과 연결한다.

**적용 주의:** 장애를 일으킨 것 자체는 검증 성과가 아니다. 관측이 없는 실험의 무사 종료를 회복력 증거로 쓰지 않는다. 작은 실험의 성공을 모든 장애 조합으로 확대하지 않는다. 책의 verification/validation 용어 구분은 해당 논의의 구분이며 일반 표준 정의를 대체하지 않는다. 운영 장애 실험 권한은 이 문서에서 새로 부여하지 않는다.

## 6. Practical TLA+ — Hillel Wayne

[O'Reilly 원문](https://learning.oreilly.com/library/view/practical-tla-planning/9781484238295/)

**읽음:** Part I 도입 및 1장 본문 전체. 계좌 이체 예제로 상태·불변식·경쟁·원자적 단계·시간 속성·TLC 반례를 확인했다. 이후 심화 장, 전체 도식의 시각 확인, TLC 실행은 하지 않았다.

**추출:** 동시성과 실패가 얽힌 설계는 상태 모델로 먼저 반례를 탐색할 수 있다. 초기 상태와 탐색 한계를 명시하고 반례를 구현 회귀 검사로 연결한다. 안전 속성과 진행 속성, 최종 수렴과 기한 내 완료를 구분한다.

**적용 주의:** 모델에서 하나로 묶은 단계가 실제 DB·외부 서비스에서 원자적이라는 보장은 없다. 모델의 조건을 실제 트랜잭션과 실패 지점에 대응시켜야 한다. 제한된 상태 공간의 탐색 성공은 무한한 입력·실행 전체의 증명이 아니다. 입력 범위를 줄여 오류를 숨기지 않는다. ‘결국 일관됨’은 실패한 요청이 아무 효과도 남기지 않았다는 조건보다 약하다.

## 충분성 판단과 다음 읽기 조건

이번 범위는 방법 선택과 교차 검증 지침을 만드는 데 충분하다. 제품에 도구를 구현하는 단계의 설치·버전·API 설명으로는 충분하지 않다.

추가 읽기는 특정 작업의 빈틈이 확인될 때 진행한다. 예를 들어 Pact 배포 호환성 게이트를 구현할 때는 해당 공식 문서, 진행 속성을 TLA+로 검증할 때는 fairness·시간 속성 심화, DB 이력 검사를 도입할 때는 실제 모델과 검사기 문서를 추가 확인한다. 미리 모든 책을 완독하는 것을 착수 조건으로 만들지 않는다.

## 공식 도구 문서의 보완 확인

현재 기능의 개요와 사용 조건을 아래 공식 자료로 교차 확인했다. 설치·제품 적용·예제 실행은 하지 않았다.

- [Pact 개요](https://docs.pact.io/): 소비자·공급자 계약 검사의 범위.
- [JMeter best practices](https://jmeter.apache.org/usermanual/best-practices.html): CLI, 발생기 비용, coordinated omission 주의.
- [PropEr](https://proper-testing.github.io/): 속성 기반·상태 기반 검사.
- [Jepsen](https://jepsen.io/): 분산 시스템 안전 속성 검사의 목적. 특정 검사기 구성은 미검증.
- [ZAP 문서](https://www.zaproxy.org/docs/), [SpotBugs](https://spotbugs.github.io/), [Find Security Bugs](https://find-sec-bugs.github.io/), [OWASP Dependency-Check](https://owasp.org/projects/dependency-check): 동적·정적·의존성 검사 역할 구분.

책에서 얻은 방법, 이번 문서의 설계 제안, 실제 실행 결과를 혼동하지 않는다. 실행 결과는 이번 기록에 없다. 적용안은 [검증 도구 선택 지침](검증-도구-선택-지침.md)에 정리했다.
