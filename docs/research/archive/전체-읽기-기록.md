## 판정 방식

페이지 열기나 목차 확인은 본문 읽기로 계산하지 않는다. 본문, 코드·표, 의미 있는 도식을 구분해 확인한다. 이전 선택 검토에서 빠진 줄과 도식을 포함하여 보완한다. 외부 참고문헌까지 모두 읽었다는 의미는 아니다. 새 적용 요소는 제안이며 승인된 규칙을 변경하지 않는다.

## Balancing Coupling in Software Design

출처: https://learning.oreilly.com/library/view/balancing-coupling-in/9780137353514/

### 서론 및 1장

서론은 결합을 제거 대상이 아니라 시스템 목적을 달성하기 위한 설계 대상으로 놓는다. 1장은 함께 바뀌는 이유를 공유 지식과 공유 생명주기로 구분한다. 호출이나 import가 없더라도 같은 배포 단위에 속하면 배포·검사 비용이 연결된다. 반대로 서비스 분리는 생명주기 결합을 줄일 수 있지만 지식 의존이 사라진다는 뜻은 아니다.

저장소 인터페이스 사례는 구체 DB 이름을 숨기는 것과 관계형 DB의 질의·트랜잭션 의미를 숨기는 것이 다름을 보여 준다. 인터페이스 존재 자체를 분리 성공으로 판정하면 안 된다. 자체 적용 제안: 변경 후보마다 소비자가 아는 구현 지식과 함께 배포해야 하는 단위를 각각 기록한다. 가상의 DB 교체 가능성만으로 추상화를 추가하지는 않는다.

지식 흐름은 의존 화살표와 반대 방향으로 설명된다. 제공자의 계약·제약을 소비자가 알아야 하기 때문이다. 시스템 목적·구성요소·상호작용은 연결되어 있으므로 파일 수나 서비스 수 감소만으로 개선을 판정하지 않는다. 기계 공학의 공차 예는 균형의 비유이며 소프트웨어 임계값의 실증 근거로 취급하지 않는다.

확인: 서론 및 1장 본문, 각주, 선택 절, 퀴즈 문항 모두 읽음. 1장 그림 1.1–1.8 모두 시각 확인. 책의 예시 코드를 실행했다는 뜻은 아니다.

### 2장

본문·각주·표·퀴즈 전체 및 그림 2.1–2.6 시각 확인 완료. 판단에 필요한 지식이 이미 있는지, 전문가에게 얻을 수 있는지, 통제한 실험이 필요한지, 먼저 장애를 억제해야 하는지를 구분한다. 자체 적용: 모든 발견을 즉시 수정 일감으로 전환하지 말고, 불확실한 원인은 재현·관찰 일감으로 먼저 만든다. 책의 혼합 버전 서버 사례에서 원인을 모른다는 말은 물리적 인과관계가 없다는 뜻이 아니다. 인덱스 소유권이 명확하더라도 성능 결과가 자동으로 확실해지는 것은 아니므로 실제 부하와 실행 계획 검증은 별도로 필요하다.

### 3장

본문·각주·코드 3.1–3.10·퀴즈 전체 읽음. 그림 3.1–3.7 시각 확인. 전체와 내부의 복잡성을 함께 평가해야 한다. 모듈을 합치거나 잘게 쪼개는 것만으로 복잡성을 없앨 수 없다. 입력과 인터페이스가 허용하는 상태를 줄이는 제약은 유용하지만 필요한 기능까지 금지하는 제약은 비용이다. SQL 문자열 → 질의 객체 → 명시적 조회 메서드 비교는 사고 실험이며 저자도 저장소 구현의 정답으로 제시하지 않는다.

**원문 예제 주의점(코드 이미지까지 직접 대조)**

- 예제 3.4는 삼각형 부등식 위반을 `<`로 검사한다. `(1, 1, 2)`처럼 합이 같은 퇴화 삼각형이 통과한다. 설명의 의도는 엄격한 삼각형 부등식이다. 초기 기본값 상태와 정수 덧셈 범위도 실제 구현에서 별도로 다뤄야 한다. 본문의 “유효하지 않은 상태가 불가능”이라는 설명을 코드 자체가 완전히 보장하지 않는다.
- 예제 3.6은 “3개월 이전” 조회를 설명하지만 양수 3개월을 더한 날짜와 비교한다. 뒤의 3.8·3.10은 음수 3개월을 사용한다. 설명과 코드 사이의 불일치이며 실제 DB 실행 검증은 아직 하지 않았다.
- 따라서 서적의 예제는 권위만으로 검증 규칙의 구현 원본이 될 수 없다. 의도한 불변식과 경계 반례를 먼저 확정해야 한다. 이 항목은 신규 규칙 승인 없이 적용 검토 근거로 보관한다.

### 4장 및 2부 도입

본문·각주·표·코드·퀴즈 및 그림 4.1–4.3 전체 확인. 모듈을 기능·내부 논리·실행 문맥으로 설명한다. 함수 시그니처가 숨기는 사전 인증 가정, 런타임 버전, 자원 요구도 통합 계약에 해당한다. 추상화는 불필요한 정보뿐 아니라 필요한 트랜잭션 의미까지 숨기면 오히려 잘못된 사용을 유발한다. 깊은 모듈 두 개가 같은 업무 규칙을 중복하면 각각의 깊이만으로 전체 모듈성을 보장하지 못한다. 모든 미래 변경을 수용하려는 인터페이스는 사용성과 최적화 비용을 키운다. 자체 적용: 자동 정리의 근거에 현재 필요한 변화와 숨기려는 결정을 명시하고, 일반화 자체를 목표로 하지 않는다.

### 5장

본문·각주·코드 5.1–5.9·퀴즈 전체 읽음. 그림 5.1–5.2 시각 확인. 내용·공통·외부·제어·스탬프·데이터 결합의 역사적 분류를 현대 사례와 비교한다. 공유 파일 전체와 필요한 전역 값 일부는 둘 다 갱신 순서·검증 로직·동시성 문제가 있다. 내용 결합과 공통 결합의 차이는 공유 저장소라는 외형보다 통합을 의도했는지다. 메서드가 같은 객체 필드를 사용하는 경우와 여러 서비스가 같은 데이터를 수정하는 경우는 같은 분류여도 비용이 다르다. 자체 적용: 분류명만으로 자동 리팩터링하지 않는다. 제어 인자가 요구사항 자체인지 내부 구현 노출인지 확인해야 하며, DTO도 전달 데이터와 변경 이유가 실제로 분리되어야 한다.

### 6장

본문·각주·코드 6.1–6.15·퀴즈와 그림 6.1–6.4 전체 확인. 이름·타입·의미·알고리즘·위치라는 정적 관계와 실행 순서·시점·값·동일 인스턴스라는 동적 관계를 구분한다. 알고리즘 connascence는 코드 중복 자체가 아니라 송수신 값 해석을 위한 합의다. 시계를 두 번 읽는 예제는 한 시점의 스냅샷으로 바꾸면 시간 경계 오류를 줄일 수 있다. 업무상 필요한 시간 제약은 이름 변경이나 타입화로 없앨 수 없다. 공유 DB만 보고 동일성 결합을 단정하지 않고, 동일 데이터의 변경을 즉시 관찰해야 하는지 확인한다.

주의: 삼각형의 한 변이 바뀌면 다른 변도 반드시 바뀐다는 본문 표현은 너무 강하다. 예컨대 `(3,4,5)`에서 `(3,4,6)`으로의 변경은 나머지 값을 유지해도 유효하다. 정확한 적용은 다른 값과의 제약을 다시 확인해야 한다는 것이다. 또한 클래스 내부 연속 대입만으로 동시 접근에 대한 원자성이 생기는 것은 아니다. 관계 분류는 실행 보장의 증명이 아니다.

### 7–8장 보완

이번에 본문·각주·모든 코드·퀴즈를 줄 누락 없이 다시 읽음. 그림 7.1–7.16, 8.1–8.5 전체 시각 확인. 7장 운영/분석 모델과 통합 DTO 전체 필드를 확인했다. 별도 타입을 만들었다는 사실만으로 결합 강도가 낮아졌다고 판정하지 않는다. 공개 계약의 단위·의미·버전·변환 책임이 실제로 분리되었는지 확인한다. 8장 8.1 예제의 무관한 기능 동거는 변경·배포 생명주기를 결합한다. 반대로 멀리 분리하면 실제 공동 변경에 드는 조정 비용이 커진다. 메시지 큐 도입은 공유 지식 문제를 해결하지 않고, 과거 메시지 때문에 형식 전환에 중간 소비자 버전이 필요할 수 있다.

### 12장

본문·각주·퀴즈와 그림 12.1–12.11 전체 확인. 단순 재배치는 복잡성을 내부와 외부 사이에서 옮기기만 할 수 있으며, 성장으로 책임이 늘면 새 추상화가 필요할 수 있다. 중요한 적용은 각 계층에서 어떤 지식을 숨길지 다시 정하는 것이다. 자연계의 규모 법칙을 소프트웨어 비용 공식으로 사용하지 않는다. 본문의 전결합 가정은 가능한 상호작용 수를 설명하는 사고 실험이지, 모든 프로그램이 같은 비율로 복잡해진다는 측정 결과가 아니다. 새 추상화의 채택 근거는 실제 변경 영향과 탐색 비용이어야 한다.

### 13장

여덟 사례의 본문·각주·코드 13.1–13.14·마지막 검토 질문 읽음. 그림 13.1–13.9 시각 확인.

1. 내부 이벤트를 그대로 공개하면 소비자가 생산자의 모델 변경에 끌려간다. 필요한 정보를 합의한 공개 이벤트로 변환하는 책임을 생산자 경계에 둔다. 공개 이벤트 크기·순서·재생·버전 비용은 별도 검증한다.
2. 같은 모델 결합이어도 실제 변화가 적고 문제가 없다면 추가 통합 계층이 우선 과제는 아니다. 지원 도메인이라는 이름만으로 낮은 변동성을 확정하지 않는다.
3. 기능 변경이 여러 기술 계층을 계속 횡단하면 기능별 수직 분할이 후보가 된다. 폴더 이동만으로 실제 의존이 바뀌었다고 보지 않는다.
4. 복잡한 업무 규칙이 인프라 세부사항에 종속되면 포트와 어댑터를 검토한다. 모든 수직 분할에 동일한 패턴을 강제할 필요는 없다.
5. 애그리거트 경계는 객체 연관관계 전체가 아니라 함께 지켜야 하는 불변식에서 정한다. 책의 메시지 컬렉션은 사례에서 최대 100개였고 본문·첨부는 외부 저장소에 있었다는 각주가 중요하다. 임의 규모에 그대로 적용하지 않는다. 클래스 경계만으로 DB 격리·경합 검증을 대체하지 않는다.
6. 역할별 폴더 대신 함께 바뀌는 책임별 배치는 변경 탐색 비용을 줄이는 후보이다.
7. 알림 인터페이스 분할은 소비자가 실제로 쓰는 기능과 공동 변경 이유로 판단한다.
8. SLA 계산 추출은 자료구조 접근을 계약으로 바꾸는 예다. SLA 미설정 시 기본값을 쓸지는 업무 의미 변경이므로 에이전트가 정리 작업 중 임의 결정하지 않는다.

추가 주의: 예제의 원자성 설명을 실제 저장소 동작의 증명으로 읽지 않는다. 예제 코드의 문법·컬렉션 API·오류 처리까지 제품 품질로 보장된 것은 아니며, 실제 적용 시 타깃 언어와 버전에 맞춰 실행 확인해야 한다.

### 서문·부 도입·14장·후기·부록

편집자 서문, Rebecca Wirfs-Brock와 Kent Beck의 서문, 저자 서문·감사의 글·소개, 세 부의 도입, 14장·후기·부록 A–C를 읽었다. Kent Beck은 자신의 coupling이 저자의 integration strength에 가깝다고 명시한다. 여러 책의 같은 단어를 곧바로 같은 검사 항목으로 통합하면 안 된다. 후기의 글쓰기 비유와 부록 A의 시는 설계 관점을 설명하는 표현이며 검증 근거가 아니다. 부록 B 용어집과 부록 C 정답을 대조했다. 독서와 퀴즈 확인은 실제 제품 적용 검증과 구분한다.

### 9장

본문·각주·표·퀴즈 전체 및 그림 9.1–9.5를 확인했다. 의존 화살표와 지식 흐름은 반대 방향이다. 변동성은 의존하는 상위 모듈에서 전파될 수 있다. 변경 횟수가 적어도 수정 불가능해서 방치된 코드일 수 있으므로 낮은 변경 빈도를 안정성 증거로 단정하지 않는다. 도메인의 전략적 분류는 예상 변동성의 가설이며, 공급자 버전·보안 수정·법규 등 실제 변화 요인으로 보정한다.

### 10장 보완

본문·각주·모든 수식의 줄·표·퀴즈를 대조했다. 그림 10.1의 의존 방향과 지식 흐름도 화면으로 확인했다. 수치 범위와 점수는 저자가 임의로 선택한 휴리스틱이다. 높은 균형 점수가 권한·트랜잭션·운영 안전성을 증명하지 않는다. 특히 안정된 레거시 DB를 직접 읽는 예는 유지보수 변화 비용에 관한 설명이지 사적 인터페이스 접근의 포괄 허가가 아니다.

원문 표 10.5는 화면에서도 `(High, High, Low)`가 세 번 반복되어 9행이고 `(High, Low, Low)` 조합은 빠져 있다. 본문 Boolean 수식은 세 입력의 8가지 조합으로 별도 계산해야 한다. 이는 해당 O’Reilly 판에서 관찰한 표의 불일치이며 저자 정오표 확인 결과는 아니다. 수치 모델을 자동 통과 기준으로 채택하는 제안은 하지 않는다.

### 11장

본문·사례·퀴즈 및 그림 11.1–11.8 전체 확인. 일정 이벤트가 제공하던 최종 일관성에 즉시 일시중지 요구가 추가되면 기존 통합 계약의 전제가 달라진다. REST로 최신 값을 조회해도 조회 후 할당 전 변경이 가능하다. 기능을 같은 서비스로 옮긴다는 설계 결정과 실제 원자적 상태 변경·격리 보장을 구분해야 한다. 일시중지 성공 응답과 진행 중 할당의 선후 관계를 실행 가능한 사례로 명시한다. 중복 계산을 한 생산자에 모으면 소비자가 사용하는 계산 시점·버전·재계산 의미도 함께 정의해야 한다.

자체 적용: 새 동기성 요구, 업무 규칙 중복의 변화 빈도 상승, 서비스나 담당 팀 분리, 공급자 교체는 설계 판단 재검토 신호다. 검증 기준의 의미가 바뀐다면 에이전트가 기준을 수정하지 않고 사용자 승인 대상 제안으로 올린다.

13장 도식 대조 주의: 그림 13.7은 인프라 → 애플리케이션 → 도메인 의존을 그리지만 그림 13.8의 같은 부분은 반대 방향 화살표로 표시된다. 본문은 의존 역전을 설명한다. 화살표 의미를 확인하지 않은 채 그림만 자동 설계 규칙으로 옮기지 않는다. 그림 13.6·13.8의 포털별 작업 이름 배치도 책임 판단의 근거로 그대로 채택하지 않는다. 적용 시 실제 import·호출·포트 구현 관계로 검증한다.

첫 책의 본문·예제·도식 검토를 마쳤다. 참고문헌 목록은 전체 확인했고 색인 항목을 검토 범위와 대조했다. 참고문헌에 나열된 외부 서적·논문까지 읽거나 모든 색인 링크를 클릭한 것은 아니다. 표지·판권 등 출판 부속 정보는 실질 적용 검토 범위와 구분한다. 다른 다섯 책의 최종 상태는 위 범위 표와 아래 기록을 따른다.

## Working Effectively with Legacy Code — 전체 읽기 기록

### 서문·소개·1–2장

서문, 저자 서문·감사의 글, 소개, 1장과 2장의 본문·예제·표·그림을 확인했다. 이 책의 legacy는 테스트가 없는 코드라는 작업상 정의다. 다른 책의 용어와 자동으로 동일시하지 않는다. 예제는 단순화되어 있고 생략된 부분이 있으므로 실행 가능한 제품 코드로 취급하지 않는다.

1장은 변경할 동작과 보존할 동작을 분리한다. 기능 추가·버그 수정·구조 개선·최적화라는 분류만으로 검증 범위를 정하지 않는다. 구조 개선에서도 성능이 달라질 수 있으므로 기능 보존과 자원 예산을 별도로 확인한다. 수정 줄 수를 줄이는 것이 위험을 줄이는 것과 같지는 않다. 두 표와 그림 1.1까지 대조했다.

2장은 변경 지점 → 관찰 가능한 테스트 지점 → 필요한 의존성 절단 → 테스트 → 기능 변경·리팩터링의 순서를 제시한다. 테스트를 만들기 위해 테스트 없이 해야 하는 최초 절단은 최소 범위로 제한하는 부트스트랩 예외다. 이후 변경까지 무검증으로 허용하는 근거가 아니다. 빠른 국소 테스트는 오류 위치를 좁히며 실제 DB·네트워크 통합 검증을 대체하지 않는다. 0.1초 기준은 당시의 피드백 비용 설명이며 모든 환경의 고정 통과 기준으로 채택하지 않는다.

그림 2.1–2.2 대조: 본문은 servlet 대신 invoice ID 목록 전달로 의존을 제거한다고 설명하지만 그림 2.2 생성자 표기에는 InvoiceUpdateServlet도 남아 있다. 실제 적용에서는 호출부·생성자 시그니처·상태 소유권을 코드로 확인한다. 도식만으로 절단 완료를 판정하지 않는다.

### 3–5장

3장 전체 코드와 그림 3.1–3.4 확인. 대역의 역할을 실행 가능하게 분리하는 것과 결과를 관찰하는 것으로 구분한다. 마지막 호출값만 기록하는 대역은 호출 횟수·중간 호출·순서를 증명하지 않는다. 실제 디스플레이 동작은 별도 검증 대상이다. 필요한 관찰 범위만 대역에 구현하고 프로덕션 인터페이스에 테스트 전용 조회를 억지로 추가하지 않는다.

4장 전체 전처리·링크·객체 seam 예제와 그림 4.1 확인. 대체되는 호출 위치뿐 아니라 대체를 선택하는 활성화 지점도 기록한다. 테스트 링크·클래스패스·전처리 설정과 프로덕션 설정을 명확히 구분해야 한다. 성공값만 반환하는 대역은 실패 경로 검증을 제공하지 않는다. 객체 생성이 메서드 내부에 고정되어 있으면 그 호출을 자유롭게 교체할 수 있다고 가정하지 않는다. static 제거·접근 수준 변경·virtual 도입은 언어별 호출 의미를 확인해야 하는 실제 코드 변경이다. 원문 C++ 그래픽 기록 예제는 std::queue에 push_back/pop_front를 사용하고 괄호도 불완전하므로 그대로 컴파일 가능한 예제가 아니다.

5장 전체 본문·예제 확인(도식 없음). 자동 리팩터링 도구도 평가 횟수·부작용을 바꿀 수 있다. 변수 인라인으로 호출이 1회에서 10회로 늘어나는 예를 에이전트 점검 후보로 삼는다. 도구 이름이나 버튼 실행 성공이 동작 보존의 증거가 아니다. 테스트별 인스턴스가 별개여도 static 상태·파일·DB·환경이 공유되면 격리되지 않으므로 본문의 인스턴스 격리 설명을 시스템 전체 격리로 확대하지 않는다. JUnit/CppUnitLite/NUnit/FIT 설명은 출판 당시 API이며 지금의 도구 선택이나 실행 명령으로 그대로 채택하지 않는다. 실행 가능한 업무 예제와 구현 검증의 연결이라는 원리를 적용한다.

### 6–8장

6장 본문과 모든 예제 확인(그림 없음). Sprout Method/Class는 새 코드 자체를 시험할 수 있게 하지만 기존 호출 지점의 통합을 검증하지는 않는다. Wrap Method/Class는 전후에 독립적인 동작을 넣는 경우에 적합하며 내부 알고리즘에 섞여야 하는 변경에는 직접 맞지 않는다. 래퍼 계층 증가·임시 이름·기존 코드 미검증을 남은 비용으로 기록한다. 로그를 지급 전/후 어느 쪽에 둘지는 실패·재시도 의미를 바꾸므로 구조 정리로 임의 선택하지 않는다. 중복 제거 예제도 입력 내부 중복과 기존 저장 데이터 중복을 구별해야 한다. 새 코드 단위 테스트 통과만으로 통합 완료를 보고하지 않는다.

7장 본문과 그림 7.1–7.5 확인. 변경 지연을 이해 비용, 빌드/피드백 대기, 통합 검증 비용으로 나눈다. 인터페이스·패키지 분리는 증분 빌드 시간을 줄이는 후보지만 전체 빌드는 오히려 길어질 수 있다. 적용 전후 같은 변경 시나리오의 증분 빌드와 전체 빌드를 측정한다. 5–10초는 저자의 피드백 목표이며 보편 보증이 아니다. 인터페이스가 실제로 안정적인지 확인하고 단지 인터페이스 수를 늘리는 작업은 피한다.

8장 본문·모든 코드·그림 8.1–8.7 확인. 기능 추가와 중복 제거를 구분하고 각각 테스트 피드백을 받는다. 상속으로 빠르게 변형을 만든 뒤 조합 요구가 생기면 구성·위임으로 이동할 수 있지만 그 중간 상태를 최종 설계 의무로 삼지 않는다. LSP는 소비자 계약에 관한 것이므로 abstract 도입이나 super 호출만으로 충족되는 것이 아니다. 익명 발신자 예제도 발신 주소 변경이 메시지 전체의 익명성을 보장하지 않는다.

8장 원문 정확성 확인: 빈 목록의 double 합계를 0으로 나누면 ArithmeticException이라는 설명과 throws에 선언한 예외를 반드시 본문에서 던져야 컴파일된다는 설명은 Java 동작과 다르다. 자체 최소 예제 `experiments/LegacyLanguageProbe.java`를 현재 로컬 Java로 실행해, 선언만 한 checked exception 메서드가 컴파일되고 0.0/0이 NaN을 반환함을 확인했다. 예외 테스트 설명도 제시된 catch/fail 코드의 통과 조건과 반대로 적힌 부분이 있다. 실제 테스트는 지정한 예외일 때만 성공하도록 구현해야 한다. 원문 전체 예제를 실행했다는 뜻은 아니다.

### 9–10장

9장 전체 본문·예제·그림 9.1–9.5 확인. 생성 장애를 어려운 매개변수, 숨은 외부 자원, 생성 연쇄, 전역 상태, include 연쇄, 상속·별칭으로 나누어 진단한다. 생성 후 필드 교체는 생성 시 이미 발생한 부작용을 없애지 않는다. C++ 소유권·소멸자와 Java/C# 생성 중 가상 호출의 미초기화 상태를 별도 확인한다. null 전달은 사용하지 않는 테스트 경로를 빠르게 찾는 국소 기법이며 프로덕션 계약 완화가 아니다. Null Object도 무동작을 성공으로 세면 잘못된 집계를 만든다. 전역 교체·reset은 병렬 테스트 격리를 자동 보장하지 않으며 원래 상태 복원과 프로덕션 경로에서의 접근 차단이 필요하다. protected 생성자는 Java 동일 패키지에서 생성할 수 있으므로 유일성 보장이라고 보지 않는다. 인터페이스를 상속 계층마다 복제하기 전에 실제로 방해하는 메서드만 분리할 수 있는지 본다.

9장 원문 코드 주의: IRGHConnection 타입 변수에 대역 전용 report 필드를 바로 쓰는 예는 타입 선언과 맞지 않는다. 생성자 매개변수화 예에는 멤버 service 저장이 명시되지 않고 포인터 호출 표기도 섞여 있다. 생략부가 있는 예제의 완전성을 가정하지 말고 초기화·소유권·정리를 실제 코드로 확인한다.

10장 전체 본문·예제·그림 10.1–10.2 확인. private 메서드는 가능한 한 실제 public 경로에서 시험하고, 직접 관찰이 필요하면 책임 분리나 제한된 테스트 접근을 선택한다. 테스트 편의만으로 운영 API·권한을 확대하지 않는다. sealed/final 외부 타입은 소유한 어댑터로 감쌀 수 있지만 어댑터 실제 위임과 외부 통합은 별도 검증한다. GUI에서 명령 처리·값 계산·표시 부작용을 분리하되 호출 순서와 생성 시점을 보존한다.

10장 원문 대조 주의: 파일 길이 조건이 MIN_LEN에서 MAX_LEN으로 바뀌며 반환형·괄호·매개변수 생략도 불일치한다. GUI 추출 뒤 예제에 detailDisplay 직접 호출이 다시 남아 있어 getAccountSymbol override를 우회한다. 따라서 ‘추출했다’는 설명만으로 seam 사용을 확인하지 않고 실제 호출 대상·경계값·오류 경로를 검사한다.

### 11–12장

11장 전체 코드·본문·그림 11.1–11.13 확인. 변경 영향은 호출 그래프뿐 아니라 반환값, 전달된 가변 객체, 전역·정적 상태, 상속 사용자로 전파된다. 변경 지점에서 앞으로 추적해 관찰 지점을 선정하고, 별칭과 객체 수명·반복 호출을 확인한다. private/final/const 표기만으로 깊은 불변성을 단정하지 않는다. CppClass 사례는 parse 재호출이나 다른 별칭을 확인하지 않으면 생성 후 목록 불변 결론이 성립하지 않는다. 내부 getter 재사용은 테스트가 통과하는 경로를 늘리지만 override가 있으면 호출 의미도 달라질 수 있다. 코드의 두 좌표 생성자에는 y에 x를 대입하는 표기가 있으므로 구조 설명을 값 정확성 보증으로 읽지 않는다.

12장 전체 코드·본문·그림 12.1–12.7 확인. 여러 변경의 효과를 소수 지점에서 관찰할 수 있으면 먼저 그 경계에 characterization test를 둘 수 있다. 그 경계는 클래스의 영구 속성이 아니라 이번 변경 집합에 상대적이다. 다른 소비자로 영향이 퍼지는 변경이 추가되면 관찰 지점을 다시 구한다. 단순 도달 가능성은 결과 차이를 검출한다는 증거가 아니므로 대표 변이를 넣어 테스트가 실패하는지 확인하는 방법을 적용 후보로 둔다. 넓은 테스트만 계속 키우면 피드백이 느려지므로 국소 테스트를 추가한다. 다만 국소 테스트가 생겼다는 이유만으로 통합 동작을 보던 기존 테스트를 자동 삭제하지 않는다. 대체 검증이 보존하는 계약을 먼저 대조한다. 그림 12.7에는 getSupplier→setSupplier 방향으로 표기되어 있어 실제 읽기/쓰기 의미와 코드로 대조해야 한다.

### 13–15장

13장 전체 본문·코드 확인(그림 없음). Characterization test는 기존 관찰값의 기록이고 요구사항의 정답이 아니다. 예상 밖 동작은 의심 상태로 남기고 수정의 소비자 영향을 판단한다. 리팩터링 때는 기능 존재뿐 아니라 연결·분기·변환을 시험한다. 기존 소수 절삭 실험과 연결한다. 추가로 함수 인수로 계산을 옮기면 기존 조건부 호출이 무조건 호출될 수 있으므로 값이 같은 정상 사례 외에 호출 횟수·예외·부작용을 검사한다. Java double→int가 일반적으로 자동 변환된다는 설명은 과도하다. 복합 대입의 암묵적 축소 변환과 일반 메서드 인수 변환을 구분해야 한다. PageGenerator 두 번째 최종 예제는 앞서 추가한 assoc 호출이 빠져 있으므로 입력 설정도 보존해야 한다.

14장 전체 본문 확인(코드·그림 없음). 소유하지 않은 라이브러리 의존이 넓게 퍼지면 시험·교체 비용이 커진다. 실제로 필요한 경계에 얇은 어댑터를 두는 후보로 적용한다. 저자의 final/sealed 제한 완화 선호를 보안·불변식의 언어 보장을 관례로 대체해도 된다는 규칙으로 채택하지 않는다.

15장 전체 원문 메일 코드·추출 코드·그림 15.1 확인. 작은 외부 API는 얇게 감싸는 방법, 복잡한 API는 업무 책임별 추출을 먼저 하는 방법을 비교한다. 고수준 추출은 내부에 업무 로직을 감춘 채 미검증으로 남길 수 있으므로 위임 계층과 도메인 로직의 검증 범위를 명시한다. final 클래스도 상속 없이 합성 래퍼로 감쌀 수 있어 본문의 래핑 제한을 일반화하지 않는다. 메일 예제의 발송 후 삭제·재시도·자원 닫기는 구조를 나누는 것만으로 안전해지지 않는다. 발송 성공 뒤 삭제 전 실패의 중복 가능성, finally 내 첫 close 실패로 뒤의 close가 생략되는 경우, 인터럽트 무시를 별도로 다뤄야 한다. 원문은 스스로 정상 작동을 보장하지 않는 나쁜 코드 예로 제시한다.

### 16–18장

16장 전체 본문과 그림 16.1 확인. 관계 스케치·책임 표시·제어 블록·추출 후보를 이해 도구로 사용한다. Scratch refactoring은 폐기 가능한 격리 사본에서 수행하는 이해 실험이며 무검증 납품물이 아니다. 원본에서 가설을 재확인한다. 미사용 코드 삭제는 동적 등록·설정·리플렉션도 확인한다.

17장 전체 본문과 카드 그림 6개 확인. 짧은 아키텍처 설명은 공유 작업 모델에 유용하지만 생략한 제약도 남긴다. 카드의 겹침은 포함 관계, 여러 카드는 인스턴스를 표현한다. 투표 예제의 응답 후 기록 순서는 내구성 보증이 아니다. 이야기에서 발견한 LockingPolicy는 코드와 변경 요구로 검증할 후보이지 명사마다 클래스를 추출하라는 규칙이 아니다.

18장 전체 본문·디렉터리 예제 확인(그림 없음). 테스트 이름·위치는 탐색과 실행 피드백 비용으로 선택한다. 클래스마다 테스트 파일 하나를 강제하지 않는다. 소스에서 가까이 두는 것과 운영 산출물에 배포하는 것은 별개다. 책은 주로 크기를 논하지만 적용 시 테스트 전용 의존성·대역·데이터의 운영 산출물 혼입도 확인한다. 기존 관례와 탐색 기능이 충분하면 폴더 재배치 자체를 일감으로 만들지 않는다.

### 19–20장

19장 전체 본문·C/C++ 코드 확인(그림 없음). 절차형 코드도 링크 대역·전처리·함수 포인터로 경계를 만들 수 있다. 언어 전환이나 객체 지향화가 선결 조건은 아니다. 계산과 전송 분리 후에도 전송 순서·실패·메모리 소유권을 검증한다. 원문 최종 send_command는 command를 만들고 free(message)를 호출하므로 그대로 적용하면 안 된다. 빈 매크로는 실제 함수와 달리 인수 평가도 없앨 수 있다. 테스트/운영 빌드 차이를 기록한다. C→C++ 전환은 ABI·타입 변환·초기화·링크 차이를 확인할 별도 변경이며 기계적 동작 보존을 가정하지 않는다.

20장 전체 본문·예제·그림 20.1–20.14 및 메서드 그룹 그림 확인. 메서드 이름, 숨은 메서드, 변동 가능한 결정, 필드 사용 군집, 주요 책임, 탐색적 리팩터링, 현재 작업의 일곱 관점은 후보를 찾는 휴리스틱이다. 메서드 수나 private 개수만으로 자동 분리하지 않는다. Feature sketch의 사용 방향과 effect sketch의 영향 방향을 구분한다. 군집을 나눌 때 경계를 가로지르는 값·호출이 새 인터페이스 비용이며 의미 있는 이름과 실제 변경 이유가 필요하다. 내부 책임 분리와 소비자 인터페이스 변경은 검증 범위가 다르다. 후자는 호출자 테스트도 필요하다. 컴파일 성공은 상속 메서드 재선택·필드 shadowing을 잡지 못할 수 있다. 원래 진입점을 남기고 본문을 옮기는 단계적 추출을 검토한다. 원문 FeeCalculator 그림의 매개변수 생략 등은 실제 코드로 대조한다. 이상적인 전체 재구성보다 현재 변경에 필요한 범위에서 검증하며 진행한다.

### 21–22장

21장 전체 본문·단계별 코드·그림 21.1–21.5 확인. 같은 프로토콜 지식의 반복을 공통화하면 변경 지점을 줄일 수 있지만 문자상 유사성만으로 결합하지 않는다. 작은 추출 뒤 실제 변경 시나리오로 이득을 평가하고 얇은 기존 진입점은 호환성을 위해 유지할 수 있다. 원문은 byte[]를 char[]로 바꾸거나 abstract 선언을 누락하고, 제거한 commandChar를 계속 사용한다. 최종 private writeBody는 뒤의 AggregateCommand에서 override할 수 없으며 body 크기 계산도 새 집계 형식에 맞추지 않았다. 따라서 '나머지는 그대로 동작'을 적용 근거로 삼지 않는다. 프로토콜 바이트·길이·순서·인코딩·부분 쓰기 실패와 확장 경로를 검증한다. 원문 전체를 실행했다는 의미는 아니다.

22장 전체 본문·코드·그림 22.1–22.4(22.3은 두 이미지) 확인. 큰 메서드는 순차 작업과 깊은 제어 흐름을 구분하여 작은 추출을 선택한다. 인수·반환값 개수는 추출 실수 가능성의 한 단서이며 필드·전역 상태를 제외하므로 실제 결합이나 안전성 점수가 아니다. 관찰용 boolean은 한 번이라도 실행되었는지만 보여 주며 횟수·순서·재호출·동시 실행을 증명하지 않는다. 관찰 변수를 지울 때 필요한 통합 검증까지 사라지지 않게 한다. 메서드 객체를 만들면 호출별 상태 수명과 재사용 여부를 확인한다. 자동 추출 도구만 사용하는 단계와 수동 의미 변경을 분리하되 도구 자체를 무조건 정확하다고 가정하지 않는다. 원문 private 메서드를 하위 클래스에서 override한다는 설명도 접근 수준 수정이 필요하다. UI 등 주변 동작을 덜 중요하다고 임의 분류하여 검증에서 제외하지 않는다.

### 23–24장 및 3부 표제

23장 전체 본문·코드 확인. 한 번에 하나의 의도를 변경하고 다른 발견은 별도 후보로 남긴다. 테스트 진입점을 만드는 초기 변경에서는 시그니처·타입·인수 순서를 보존하며 설계 개선을 섞지 않는다. 컴파일러는 정적 사용처 탐색을 돕지만 상속 fallback·동적 호출·별도 빌드 변형을 완전히 증명하지 않는다. 두 번째 검토자의 점검을 권하지만 에이전트 자기 검토를 독립 검토라고 표시하지 않는다. 코드가 편집되지 않으면 고장 나지 않는다는 도입부 설명은 고정 코드 자체에 한정한다. 실행 환경·데이터·시간·외부 계약 변화로 서비스는 실패할 수 있다.

24장 전체 본문 확인. 전면 재작성은 기존 제품의 계속되는 기능 변경까지 따라가야 하는 비용이 있다. 현재 변경 지점에 빠른 검증 환경을 만드는 점진적 개선을 우선 후보로 삼는다. 팀 사기를 위해 가장 나쁜 코드를 고른다는 조언은 자동 일감 우선순위가 아니다. 실제 변경 수요·영향·비용으로 선택하며 개인 태도를 시스템 문제의 원인으로 단정하지 않는다. 3부는 표제만 있는 페이지임을 확인했다.

### 25장: 24개 의존성 절단 기법

전체 도입·24개 기법의 본문·코드·절차·사이드바와 그림 25.1–25.6 확인. 이는 테스트 진입을 위한 초기 변경 카탈로그이며 완성 설계나 무검증 자동 수정 허가가 아니다. 다음은 실제 적용 시 추가로 확인할 조건이다.

| 기법 | 적용 판단과 검증 조건 |
|---|---|
| Adapt Parameter | 외부의 넓은 API를 필요한 역할로 감싼다. 첫 값·빈 배열·null 의미를 보존하고 실제 어댑터 위임도 시험한다. |
| Break Out Method Object | 호출별 임시 상태를 별도 객체로 이동한다. 참조 수명, 반복 실행, 객체 생성 비용과 접근 범위를 확인한다. |
| Definition Completion | 테스트 전용 실행물에 대체 정의를 연결한다. 운영 정의와 동시 링크되지 않게 하며 대체되지 않은 실제 경로도 검증한다. |
| Encapsulate Global References | 전역 데이터를 묶는 것과 전역 공유 제거를 구분한다. 초기화·공유 정체성·수명이 보존되어야 한다. |
| Expose Static Method | 인스턴스가 필요 없는 계산을 추출하되 기존 동적 진입점은 보존한다. static은 순수 함수라는 뜻이 아니다. |
| Extract and Override Call | 한 외부 호출을 대체할 때 인수 평가 횟수·반환·예외·순서를 보존한다. |
| Extract and Override Factory Method | 생성 중 가상 호출은 언어마다 다르다. Java 하위 필드 미초기화와 C++ 생성 중 dispatch 범위를 확인한다. |
| Extract and Override Getter | 지연 생성은 오류 발생 시점·동시 생성·설정 읽기 시점을 바꿀 수 있다. 모든 사용처와 소멸을 확인한다. |
| Extract Implementer | 기존 타입 이름을 인터페이스로 보존할 수 있지만 생성·상속·ABI·직렬화에 영향이 있다. 계층 전체 변경보다 좁은 인터페이스 추출과 비교한다. |
| Extract Interface | 실제 소비자에게 필요한 메서드만 추출한다. C++ nonvirtual→virtual 변경은 하위 클래스 선택을 바꿀 수 있다. |
| Introduce Instance Delegator | static 호출에 대체 가능한 객체 경계를 만든다. 순수 계산까지 무조건 객체화하지 않는다. |
| Introduce Static Setter | 전역 대체 상태를 복원하고 병렬 실행 격리를 보장한다. const/final 해제를 주석·관례만으로 정당화하지 않는다. |
| Link Substitution | 링크·클래스패스가 실제 어느 구현을 선택했는지 산출물로 확인한다. 호출 기록은 순서·인수·횟수와 실패를 관찰한다. |
| Parameterize Constructor | 기존 생성 경로를 유지하며 주입 경로를 추가한다. 외부 생성으로 달라지는 평가 순서·소유권·초기화를 확인한다. |
| Parameterize Method | 내부 생성을 외부 인수로 옮길 때 기존 삭제보다 새 생성이 먼저 일어날 수 있다. 같은 포인터 전달·예외 경로도 확인한다. |
| Primitivize Parameter | 핵심 계산을 값 표현으로 시험할 수 있지만 변환·통합은 남는다. 복사 비용과 누락된 의미를 명시한다. |
| Pull Up Feature | 시험할 군집과 사용 상태를 올리되 초기화와 기존 상속 dispatch를 확인한다. 영구 상속 설계로 자동 채택하지 않는다. |
| Push Down Dependency | 외부 의존을 하위 구현으로 내린다. UI 제거가 사용자 선택에 따른 업무 상태 변경까지 제거하면 그 테스트는 전체 검증이 아니다. |
| Replace Function with Function Pointer | 함수 포인터의 초기화 전 호출·동시 변경·호출 규약·링크 선언을 확인한다. 런타임 가변 상태이므로 순수 컴파일 시점 변경이라고 볼 수 없다. |
| Replace Global Reference with Getter | 필요한 소비자 범위만 대체한다. 다른 전역 소비자와의 동일 객체 가정이 남는지 확인한다. |
| Subclass and Override Method | 대체한 부분은 테스트하지 않았음을 명시한다. 접근 수준·override 대상·호출 경로를 확인한다. |
| Supersede Instance Variable | 생성 부작용은 이미 발생했다. 별칭·소유권·동일 포인터·소멸 이후 dangling reference를 확인한다. |
| Template Redefinition | 테스트 타입과 운영 타입을 각각 빌드한다. 타입 별칭은 ABI 유지 보증이 아니며 헤더 이동으로 빌드 비용이 늘 수 있다. |
| Text Redefinition | 재정의가 다른 테스트에 남지 않도록 복원 또는 프로세스 격리한다. 런타임 패치의 생산 코드 혼입도 확인한다. |

원문 대조에서 중요한 불일치: Static Method 예제는 equals→==, 길이 >→<=, 체크섬 부정 제거로 조건 자체가 바뀐다. Getter 예제는 virtual·const·이름이 맞지 않고 const 메서드에서 상태를 수정한다. Method Object 예제는 renderer 인수를 pointRenderer에 저장해야 하는데 자기 초기화 표기가 있다. Global Reference 래퍼는 반환값 전달이 빠져 있다. Static Setter Java 예제는 static/인스턴스 인터페이스·this·반환 타입이 혼재한다. Template 예제는 조건에 비교가 아닌 대입을 사용한다. 이들을 검증 완료 코드로 복사하지 않는다. 그림 25.6은 개념적 겹침 설명이고 실제로는 추출 메서드 호출이 있어야 override가 동작한다.

### 부록·용어집·색인과 전권 검토 판정

이 책은 1–25장과 부록의 본문·코드·그림, 앞부분 서문·소개·부 표제, 용어집·색인까지 검토했다. 표지·저작권 고지는 기술 적용 검토에서 제외하며 외부 링크와 참고 서적 전체까지 읽었다는 뜻은 아니다. 대부분의 예제는 원문 대조이며 실행 검증은 별도 표기한 자체 최소 예제에 한정한다. 적용의 중심은 변경 지점→영향 관찰→최소 seam→기존 동작 고정→작은 변경→실제 경계 재검증이다.

## Effective Software Testing — 전권 읽기 진행

### 2장 Specification-based testing

2.1–2.4.13 본문, 코드 2.1–2.15, 연습문제 2.1–2.6, 요약과 그림 2.1–2.6을 모두 확인했다. 요구 이해→탐색→입출력 분할→경계→조합 선택→자동화→경험 기반 보완을 반복하는 방법을 적용 후보로 삼는다. 탐색 결과는 정답 판정 기준을 대신하지 않는다. 조합 제외는 사유와 전제를 남긴다.

적용 시 보완할 점:
- null, 빈 배열, 빈 문자열 하나가 든 배열은 서로 다른 결과다. 부분 문자열 예제의 요구·그림·반환 코드 표현이 일치하지 않는 곳은 계약을 먼저 확정한다.
- 정수 x==10의 가까운 외부 경계는 9와 11이다. 본문에 나온 12와 혼동하지 않으며 실수·소수 타입은 표현 가능한 값에 맞춘다.
- 예외 분할을 한 번만 시험하거나 태그 길이 조합을 생략하는 것은 비용 절감 휴리스틱이다. 예외 우선순위와 길이별 인덱스 계산 차이를 놓칠 수 있다.
- 자릿수 덧셈 코드는 입력 리스트를 reverse하여 변경한다. 무상태라는 설명만 믿지 말고 입력 보존, 같은 객체를 양쪽에 전달한 경우, 반복 호출, 수정 불가능한 리스트, 잘못된 값 이후 상태를 확인한다. 올림 조건은 합이 10 이상이다.
- 빈 입력 두 개의 결과를 [] 또는 [0] 중 무엇으로 할지는 요구 계약이다. 명세에 없는 수학적 관습을 에이전트가 승인된 요구로 바꾸지 않는다.
- 앞단 검증을 근거로 잘못된 입력 시험을 생략하려면 모든 진입 경로에서 해당 계약이 성립하는지 확인해야 한다. 메서드 분할만으로 통합 조합 문제가 사라지지도 않는다.

연습문제도 분할·경계 선정 근거를 대조했다. 경계 통과는 전체 정확성 증명이 아니며 구현에 없는 동작은 구조 커버리지로 발견할 수 없다는 점이 핵심이다.

두 서문·저자 서문·감사의 말·책의 범위와 저자 소개를 읽었다. 이 책은 기능 검증 중심이며 성능·보안·분산 시스템별 시험을 완결하지 않는다. 1장 본문 전체, 코드 1.1–1.9, 그림 1.1–1.8, 연습문제 1.1–1.9와 요약을 확인했다.

### 3장 Structural testing and code coverage

3.1–3.11 전체 본문·코드·표·연습문제 3.1–3.9·요약, 그림 3.1–3.11과 세 수식을 확인했다. 긴 제어 흐름 그림은 하단까지 따로 확인했다. 명세 기반 시험 후 미실행 경로를 찾아 필요성을 판단하고, 변이 시험으로 판정문의 결함 탐지력을 살핀다는 절차를 적용 후보로 삼는다. 제외 사유·분모·도구별 측정 의미를 기록해야 하며 수치만 올리는 변경은 목적에 맞지 않는다.

원문을 그대로 규칙화하면 안 되는 부분:
- MC/DC 표는 코드의 !isLetter를 isLetter로 표기하고 있다. last가 s이면서 r인 조합은 실제 문자 입력으로 실현할 수 없다. 추상 진리표를 실제 입력으로 옮기며 실현 가능성·단락 평가를 확인한다.

- 변이 점수의 분모는 생성된 유효 변이와 동등 변이 처리 정책에 달린다. 변이를 모두 죽여도 모든 실제 결함 탐지 증명은 아니다. 등가 변이는 계약과 관찰 가능 결과를 근거로 판단한다.

### 4장 Designing contracts

4.1–4.5.7 전체 본문, 코드 4.1–4.12, 그림 4.1–4.3, 연습문제와 요약을 확인했다. 호출자의 의무·제공자의 보장·객체 불변식·외부 입력 검증을 각각 기록하고 실제 실행 경계에서 보장되는지 확인하는 방식이 적용 후보다. 사전조건 강화·사후조건 약화는 소비자에 영향을 준다. 그 반대라도 전체 의미·예외·부수효과 계약이 유지되는지 따로 검증한다. 규칙 변경은 여전히 사용자 승인 대상이다.

추가 조건: assert 활성화와 운영 설정을 확인하고 필수 입력 검증을 비활성화 가능한 assert에만 맡기지 않는다. double의 NaN은 value<0과 value>=0의 대응을 깨며 무한대도 별도다. 양수와 0 이상 표현이 섞여 있어 계약을 명확히 한다. 무료 상품이면 금액이 반드시 증가한다는 Basket 조건은 성립하지 않는다. BigDecimal도 반올림 정책 자체를 없애지는 않는다. 불변식 검사 실패는 이미 발생한 상태 변경·외부 효과를 되돌리지 않으며 동시 접근과 예외 경로에도 보존 전략이 필요하다. 입력 검증 예제는 정제한 description 대신 원래 description을 생성자에 전달한다. 검증한 값과 실제 사용값이 같은지 추적한다. squareAt 예제는 board!=null 검사가 역참조 뒤에 있으므로 검사 순서도 확인한다. 상속을 피하더라도 교체 가능한 구현·서비스의 계약 호환성 문제는 남는다.

### 5장 Property-based testing

5.1–5.6.3 전체, 코드 5.1–5.24, 그림 5.1–5.2, 세 연습문제와 요약을 확인했다. 이전 발췌 검토의 약한 unique 속성·컬렉션 뷰 문제를 전장 맥락에서도 재확인했다. 생성기의 범위·분포·경계·제외·seed와 최소 반례를 증거로 남기고 명세 기반 예제를 보완하는 용도로 적용한다. 실행 횟수는 전칭 명제의 증명이 아니다.

unique의 포함·중복 없음·내림차순만으로는 입력에 없는 추가 원소를 배제하지 못한다. 앞선 자체 실험에서 확인한 정확한 원소 집합 판정을 유지한다. 길이 100·값 1–20 고정은 빈 배열·단일 값·음수·극값을 다루지 않는다. indexOf 생성은 삽입 뒤 길이 101인데 끝 위치 100을 생성하지 않으며 @IntRange(max=99)만으로 서술한 최소 0을 보장한다고 가정하지 않는다. 경계·중복·미발견을 별도 분할한다.

Basket 상태 전이 시험은 구현에서 읽어 온 총액·수량으로 기대값을 계산하므로 잘못된 상태를 함께 신뢰할 수 있다. 독립된 모델로 내용·수량·총액을 함께 대조하고 실패 후 상태·가격 변경·정수 수량 누적 오버플로도 계약에 맞춰 검토한다. unmodifiableSet은 복사가 아닌 원본을 반영하는 뷰다. 임의 원소 선택도 seed로 재현되게 해야 한다. 테스트 편의를 위한 공개 메서드는 관찰 계약과 변경 비용을 평가한다.

본문의 lessThan(1)이 1을 생성한다는 설명은 뒤쪽의 ‘가장 가까운 값’ 설명과 맞지 않는다. 생성기가 제약을 위반한다고 전제하지 않는다. 삼각형 예제는 합의 오버플로와 양의 길이 조건을 별도로 다루며 동일 확률 생성이라는 서술만 믿지 말고 실제 분할 분포를 확인한다. Book 생성 예제의 출력문은 완성된 검증문이 아니다.

### 6장 Test doubles and mocks

6.1–6.3.5 전체, 코드 6.1–6.20, 두 그림, 연습문제와 요약을 확인했다. 대역을 쓰는 이유·생략한 실제 경계·계약 일치 확인 방법을 함께 기록한다. 느린 의존성·발생시키기 어려운 실패를 제어하되 단순 값 객체까지 자동으로 mock하지 않는다. 상태 결과가 목적이면 결과를, 외부 협력이 계약이면 필요한 호출 인수·횟수를 확인한다. 외부 라이브러리 래퍼도 실제 라이브러리와 통합 시험해야 한다.

구현 적용 보완: 생성자 주입으로 DB 생성·close가 사라지는 변경은 자원 소유권을 호출자에게 옮긴 것이므로 실제 조립 경로의 종료·예외 처리를 확인한다. verify(send)는 실제 전달·상대 저장을 증명하지 않으며 예상 두 건을 확인하는 것만으로 추가 전송을 배제하지 못한다. SAP 예제의 현재 날짜를 구현과 기대값에서 각각 읽으면 자정에 어긋날 수 있다. Clock·시간대를 고정하고 0·1·2글자와 문자 단위 의미를 시험한다. 날짜와 이름 두 글자 ID는 고유성·재시도 식별자 보장이 아니다. 예외가 발생해도 다음 청구서를 시도하는 계약은 중간 실패로 확인하되 전송 성공 후 응답 유실은 ‘미전송’과 구별해야 한다.

BookStore의 getPriceForCart는 구매 절차를 호출하므로 이름과 명령/질의 분리 설명 사이 차이가 있다. 재호출 부작용·0개 재고·없는 책·수량 경계·동시 재고 변화는 별도 계약이다. mock 사용 후 테스트 실패가 오직 대상 구현 오류 때문이라고 단정하지 않는다. 테스트 설정·대역 계약·시간·도구 오류도 가능하다.

### 7장 Designing for testability

7.1–7.5.7 전체, 코드 7.1–7.16, 그림 7.1–7.3, 연습문제와 요약을 확인했다. 통제하기 어려운 의존성과 관찰하기 어려운 결과를 먼저 식별하고 최소 변경으로 해결한다. 도메인 판단과 외부 효과를 나누되 모든 클래스에 인터페이스나 프레임워크를 도입하는 규칙으로 만들지 않는다. 데이터 인수 전달과 의존성 주입은 호출자 전체 비용을 비교한다.

주요 적용 제한: 배치에서 배송→상태 저장→알림→SAP 호출은 원자적이지 않다. 각 단계 후 실패와 재실행, 중복 배송, 일부 처리 상태를 별도로 다뤄야 한다. mock 호출 검증은 이 문제를 해결하지 않는다. InstallmentGenerator를 결과 반환형으로 바꾼 뒤의 시험은 저장 호출 검증이 빠져 있어 저장을 삭제해도 통과할 수 있다. 순수 생성 결과와 저장 효과를 각각 확인한다. 월말에서 plusMonths를 반복하는 것과 기준일에 n개월을 더하는 것은 다를 수 있다. 현재 시각·할부 0/음수·반올림 잔액·부분 저장도 계약에 맞게 검토한다.

관찰용 getter는 가변 내부 상태 노출 없이 의미 있는 결과를 제공해야 한다. 테스트 수·의존성 수·빈번한 추가는 설계 검토 신호이지 자동 분할 기준이 아니다. A 테스트가 B 결함을 찾은 것이 항상 잘못된 결합이라는 결론도 채택하지 않는다. 테스트의 의도된 범위에 따라 정상적인 통합 결함 발견일 수 있다. 코드에는 LocalDate와 Calendar 혼용 등 교육용 생략·불일치가 있어 실행 가능한 예제로 그대로 취급하지 않는다.

### 8장 Test-driven development

8.1–8.3.6 본문 전체, 코드 8.1–8.14와 중간 대안 코드, 그림 8.1·연습문제 그림, 네 연습문제와 요약을 확인했다. 작은 실패 사례→최소 구현→통과→정리의 피드백 주기를 적용 후보로 삼되 TDD 사용률을 목표로 삼지 않는다. 실패가 의도한 동작 부재 때문인지 확인하며 환경·컴파일 오류와 구분한다. 개발을 이끈 예제 통과 후에도 요구 분할·경계·실제 통합 검토가 남는다.

로마 숫자 예제는 정상 입력 변환까지만 구현하고 잘못된 표기 거부를 연습으로 남긴다. 책이 멈춘 지점은 기능 전체 완료 기준이 아니다. 규칙의 유효 범위·빈 값·미지원 문자·길이/합 오버플로를 정해야 한다. 기존 테스트가 모든 회귀를 포착한다는 표현을 보장으로 채택하지 않는다. 연구 결과는 책에서 상반된 연구와 한계를 함께 소개한다. ‘짧은 주기가 유용하다’를 모든 환경에서 TDD의 우월성이 입증됐다는 뜻으로 확장하지 않는다. 볼링 연습의 스트라이크 설명은 ‘다음 프레임’과 ‘다음 두 투구’를 혼용하므로 연속 스트라이크 계약을 명확히 한 뒤 구현해야 한다.

### 9장 Writing larger tests

9.1–9.4.6 전체, 코드 9.1–9.34와 중간 리팩터링 코드, 그림 9.1–9.7, 연습문제와 요약을 확인했다. 실제 조립 경로·플러그인 프레임워크·DB/SQL·사용자 여정에서만 드러나는 결함을 큰 테스트로 확인한다. 단위 수준과 중복 실행된다는 이유만으로 제거하지 않는다. SQL은 참/거짓 외에 UNKNOWN, 조인 중복·빈 결과·집계·그룹·제약·변환을 다룬다.

실행 조건은 전용 DB, 운영과 맞는 엔진·스키마·마이그레이션, 실제 commit과 별도 연결에서의 가시성, 실패 시 정리, 병렬 시험 격리다. 작은 기능 fixture와 규모/성능 fixture는 목적이 다르다. 저장과 읽기 구현이 같은 오류를 공유할 수 있으므로 중요한 변환은 직접 경계도 대조한다. 본문 double 컬럼을 getInt/setInt로 다루는 예제는 소수 손실을 놓친다. 앞선 자체 실험의 소수 12.5 경계 사례를 유지한다.

웹 테스트는 여정의 대상 단계는 실제 UI로 거치고 준비 데이터만 별도 수단으로 넣는다. reset·fixture API가 운영에 노출되지 않는지 배포 산출물에서 확인해야 한다. 고정 sleep보다 필요한 상태를 기다리되 테이블 보임이 로딩 완료를 항상 뜻하지 않는다. Page Object는 상호작용과 데이터 추출, 테스트는 결과 판정을 맡는다. 그림 9.7의 페이지/클래스 이름은 앞선 코드와 뒤바뀌어 있어 코드 의미를 따른다. 단일 검색 결과·미발견 화면은 목록 화면과 다를 수 있다. browser.close를 모든 세션 자원 종료와 동일시하지 않으며 실패 경로에서도 정리한다. 단순 커버가 아닌 효과 관찰 여부는 변이·부수효과 확인으로 검토한다.

10장 전체 10.1.1–10.2.5, 코드 10.1–10.10, 연습문제와 요약을 읽었다(이미지 없음). 11장 전체 11.1–11.6, 코드 11.1과 그림 11.1을 확인했다. 테스트의 존재 이유·판정력·격리·재현·실패 설명·유지 비용을 검토 기준으로 삼는다. 한 행동에 필요한 여러 판정은 허용하며 assertion 개수를 목표로 삼지 않는다. fixture의 관련 값은 명시하고 공통 builder의 숨은 기본값 변경 영향을 확인한다.

11장은 최종 사용자 목적 검증, 운영 관찰, 비기능·특정 기술별 추가 시험이 남는다고 명시한다. 새 클래스로 로직을 옮겨 단위 검증하더라도 legacy 호출부의 연결·인수·순서·효과 검증은 남는다. 생성된 테스트나 높은 커버리지 역시 요구의 정답 판정을 대신하지 않는다.

### 서문·1–2장: 선택의 근거와 측정 가능한 요구

서문 전체, 1–2장 본문·SQL·표·참고문헌 목록, 그림 1-1–1-2와 2-1–2-6을 확인했다. 참고문헌의 외부 본문까지 읽은 것은 아니다. 2판은 14장이며 1판의 장 번호를 그대로 출처로 쓰지 않는다.

적용 후보: 데이터마다 원본의 권위·파생 관계·갱신 경로·재생성 조건을 명시한다. 데이터베이스 제품 자체가 원본/파생을 결정하지 않는다. 재생성 가능성은 소스 보존, 변환 버전, 외부 입력 보존을 포함해 실제 복구로 확인해야 한다. 분석용 복제도 접근 권한·보존·삭제 전파를 별도로 점검한다. 클라우드는 운영 책임을 없애지 않으며 쿼터·비용·서비스 연결·교체 가능성·공유 자원 격리는 여전히 적용자가 검증한다. 분산화는 측정된 부하·가용성·지리적 요구가 정당화할 때 선택한다.

1장의 법률 설명은 설계 문제를 발견하는 배경 자료로만 사용한다. 현재 법률 적합성을 확정하는 규칙으로 옮기지 않는다. append-only·캐시·모델을 포함한 삭제 전파를 실제 기술 과제로 명시하되 법적 적용 범위는 별도 확인 대상이다.

2장 타임라인 예제의 누락 허용은 해당 제품 의미에 대한 선택이다. 에이전트가 성능 개선을 위해 임의로 데이터를 버리는 근거가 아니다. SQL timestamp 동률, 팔로우 변경, 재전송, 캐시 재구축도 실제 제품 계약에서 별도 정의해야 한다. 평균 팔로워 수와 게시물당 가중 평균 팬아웃을 혼동하지 않는다.

성능 검증은 클라이언트 응답 시간·처리 시간·큐 대기·처리량을 구분하고 부하 형태/기간/표본/실패 포함 범위를 남긴다. p99를 여러 서버에서 평균내지 않고 호환 가능한 히스토그램 등으로 집계한다. 빠른 오류 응답 증가를 성능 개선으로 판정하지 않는다. 부하 급증 후 재시도 때문에 스스로 회복하지 못하는 상태도 시험 대상이다. 장애 허용은 종류·개수·공통 원인 범위가 있는 주장이고 복제본 수만으로 입증되지 않는다.

자동화의 예외 상황과 수동 복구 경로, 변경의 되돌릴 수 있는 시점, 데이터 손실과 일시 중단의 차이를 판단서에 포함한다. 에이전트 자동 수정에도 동일하게 적용한다. 책의 수치와 산업 사례를 우리 시스템의 보편 임계값으로 복사하지 않는다.

### 3장: 모델과 질의의 의미 보존

전체 본문·JSON/SQL/MongoDB/Cypher/Turtle/XML/SPARQL/Datalog/GraphQL 예제·참고문헌 목록과 그림 3-1–3-9를 대조했다. 모델 선택은 관계의 방향·수량·변경 빈도·조회 형태·원자적 변경 범위로 설명한다. 문서 안에 묶는 것이 유리한 작은 one-to-few와 무한히 늘 수 있는 one-to-many를 구별하고, 비정규화에는 갱신·삭제·재구축 비용을 함께 둔다. ORM의 N+1은 실제 질의 수·실행 계획으로 확인한다. 분석 테이블의 한 행 단위와 역사 시점의 차원 값도 계약으로 정의한다.

스키마-on-read는 무계약이 아니다. 과거 형식을 읽는 모든 소비자와 혼합 버전, backfill, 실패 후 재개를 고려한다. 공백으로 사람 이름을 나누는 예제는 실제 이름 모델의 정답이 아니며 데이터 손실 가능성이 있다. SQL 예제 3-6은 Location/location을 혼용하고 Cypher 설명의 LIVING_IN과 코드 LIVES_IN도 일치하지 않는다. 대소문자·라벨·NULL·중복 경로·순환·0길이 경로를 포함한 동등성 시험 없이 질의를 기계 변환하지 않는다.

GraphQL의 제한된 문법이 저비용 실행을 보장하는 것은 아니다. 중첩 깊이·팬아웃·목록 크기·resolver 호출·필드별 권한을 별도로 통제해야 한다. 그래프가 없는 알레르기 간선을 근거로 안전하다고 판정하는 등 데이터 부재를 부정 사실로 바꾸지 않는다. RDF namespace는 식별 충돌을 줄이지만 의미나 권한의 동등성을 보장하지 않는다.

이벤트 소싱에서는 명령 검증과 이벤트 확정 사이의 경쟁, 순서의 보장 범위, 재생 시 외부 조회와 이메일 같은 효과를 분리한다. 취소 이벤트가 이미 수행된 모든 외부 효과를 되돌리는 것은 아니다. 동일 이벤트·동일 코드만으로 재현된다고 가정하지 말고 외부 기준값과 변환 환경도 고정한다. 삭제 요구와 재생성의 충돌은 별도 설계 대상이다. CQRS를 모든 변경의 의무 아키텍처로 확대하지 않는다.

그림 3-9의 비어 있는 평점은 0점과 다르다. 행렬 변환에는 누락·중복 관측·행/열 ID 대응·시점 누출을 검증한다. 그림 3-5의 2026년 1월 요일 표시는 실제 달력 검증용 fixture로 쓰지 않는다.

### 4장: 저장·색인 변경의 검증 범위

전체 본문·bash/SQL 코드·참고문헌 목록과 그림 4-1–4-11을 확인했다. 작은 append-only 예제는 escaping, regex 키, 동시 쓰기, 부분 기록, fsync를 처리하지 않으므로 실제 저장 계층으로 승격하지 않는다. 색인 추가의 읽기 이득뿐 아니라 쓰기 비용·공간·구축 중 부하·잠금·유일성 제약도 검토한다. 색인은 데이터 의미에 영향이 없다는 일반 설명을 UNIQUE 등 제약을 가진 색인에 무조건 적용하지 않는다.

LSM과 B-tree 선택은 실제 키/값 크기, 갱신 분포, range/point 비율, cache 상태와 compaction이 발생하는 충분한 실행 구간에서 비교한다. 빈 DB 삽입 벤치마크만으로 운영 쓰기 성능을 판정하지 않는다. compaction의 임시 공간과 장기 snapshot이 보유한 파일, tombstone의 물리 제거 지연을 함께 측정한다. Bloom filter의 양성은 존재 증명이 아니므로 원본 탐색을 생략할 수 없다. tombstone을 일찍 지우거나 재생성된 색인이 일부 데이터를 누락하면 부정 판정의 전제가 깨진다.

WAL·fsync·복제·snapshot이 각각 무엇을 보장하는지 구별한다. 프로세스 재시작 시험은 전원 장애·장치 손실을 증명하지 않는다. 책의 제품별 설명(예: stall 때 읽기까지 정지, vacuum의 공간 반환, Redis/Couchbase 내구성)은 버전·설정·작업 종류에 따라 실제 공식 문서와 환경 검증이 필요하며 그대로 상수 규칙으로 삼지 않는다.

컬럼 저장은 행 대응과 NULL 의미를 보존해야 한다. 집계 뷰는 count/sum과 평균의 재집계 방식이 다르며 freshness와 삭제/수정 반영도 계약에 포함한다. 파일 포맷·테이블 포맷·카탈로그·질의 엔진을 구분하고 한 계층의 기능을 전체 시스템의 보장으로 확대하지 않는다.

벡터 탐색은 모델/차원/거리 함수/정규화/색인 설정을 고정한 평가가 필요하다. ANN recall과 지연·메모리를 함께 보고, 권한 필터·삭제·재색인 시 구버전 혼합을 시험한다. 유사도가 높다는 이유로 사실의 정확성이나 접근 권한을 인정하지 않는다. 기존 저장소로 충족 가능한 요청에 별도 벡터 DB를 자동 추가하는 근거로 쓰지 않는다.

### 5장: 형식 호환성과 실행 중인 작업의 진화

전체 본문·스키마/바이트/서비스/Temporal 예제·참고문헌 목록과 그림 5-1–5-7(긴 MessagePack 그림 하단 포함)을 확인했다. 호환성은 단일 boolean 대신 writer/reader의 구·신 버전 조합과 요청·응답·보관 데이터·재전달 메시지를 구분한다. 구버전이 신필드를 읽고 수정해 다시 저장하는 왕복 시험으로 unknown-field 유실을 잡는다. 필드 추가가 구문상 허용되더라도 의미·기본값·권한·검증 조건의 변화는 별도 검증한다.

JSON 숫자의 2^53 주변 정밀도, 정수 문자열의 앞자리 0·음수·중복 표현, CSV escaping과 Unicode를 경계 사례로 둔다. patternProperties의 숫자 모양 key가 실제 정수 key 타입이 되는 것은 아니다. 스키마 reference는 버전을 고정하고 검증 시 임의 원격 해석을 피한다. schema-driven이어도 도메인 불변식까지 검증되는 것은 아니다.

예제 자체의 점검 사항: protobuf int64 예제와 signed ZigZag형의 1바이트 범위 설명을 혼동하지 않는다. Avro 그림 5-6은 writer long→reader int 방향을 그려 일반적인 호환 변환으로 받아들이기 어렵고, 새 userID의 기본값도 그림에는 보이지 않는다. union default 규칙은 Avro 구현·버전별 공식 명세로 확인 후 적용해야 한다. 예제 5-3 OpenAPI는 message required를 선언하지 않으므로 코드/스키마가 같은 구조라고 해서 요구 계약까지 같다고 단정하지 않는다.

서버를 모두 먼저 올린다는 가정은 rolling deployment·rollback·장시간 연결에서 성립하는지 증명해야 한다. 영속 데이터와 실행 중 workflow의 수명은 배포보다 길다. migration/rollback 계획에는 과거 스키마와 workflow 버전의 보존·재생 가능성을 포함한다.

Durable execution은 외부 효과의 원자성을 대신하지 않는다. 결제 성공 뒤 activity 완료 기록 전에 끊기는 경우를 시험하고 idempotency key·중복 요청 내용 검증·보존기간·결과 재조회 조건을 둔다. 결정적 replay와 activity 재실행을 구분하며 코드 순서 변경을 단순 정리로 분류하지 않는다. 브로커/actor는 메시지 전달·보존·순서·ack 조건이 다르므로 비동기 통신을 곧바로 무손실·독립 배포로 판정하지 않는다.

### 6장: 복제·지연·충돌

전체 본문·참고문헌 목록과 그림 6-1–6-16을 확인했다. 6-5의 alt 설명은 정족수 그림으로 잘못 되어 있으나 실제 그림은 질문보다 답이 먼저 보이는 인과 순서 문제다. 그림 본체로 의미를 대조했다.

복제는 삭제·오염도 전파하므로 백업을 대체하지 않는다. follower 생성은 일관 snapshot과 정확한 로그 위치·보존 범위가 함께 필요하다. 복구하는 노드가 만드는 부하와 로그 보존 때문에 leader가 공간 부족에 빠지는 경우도 시험한다. 동기 복제는 수신/flush/apply 중 어디까지 기다리는 설정인지 확인하며, acknowledge를 무조건 읽기 가시성·내구성과 동일시하지 않는다.

failover에서는 최신 후보 선정, 구리더 fencing, 클라이언트 재라우팅, 외부 시스템과의 ID 대응을 검증한다. 단순 timeout은 사망 증명이 아니다. 비동기 복제의 미전달 쓰기 손실을 허용할지는 승인된 제품 계약의 문제이며 에이전트가 복구 속도를 위해 임의 선택하지 않는다. 객체 저장소 CAS 지원 자체가 다중 객체 트랜잭션이나 완성된 리더 선출을 제공한다는 뜻도 아니다.

읽기 보장을 read-your-writes·monotonic reads·consistent prefix로 나눠 실제 사용자 흐름에 매핑한다. 같은 replica 고정은 장애 시 전환까지 보장하지 않는다. '1분 동안 leader 조회' 같은 예시는 지연 상한과 시계 조건 없이는 보장이 아니다. 다중 디바이스·다중 region·샤드에 걸친 동작도 포함한다. 로그 위치 차이는 바이트/순서 차이이며 곧바로 지연 초로 바꾸지 않는다.

LWW 수렴은 성공한 변경의 손실을 허용할 수 있고, CRDT 수렴도 잔액·예약 중복·목록 최대 크기 같은 업무 불변식을 자동 만족하지 않는다. 단일 리더 역시 응용 read-modify-write의 lost update를 자동 제거하지 않는다. 병합 규칙 변경은 제품 의미 변경으로 다뤄 승인 대상으로 남긴다. local-first에서도 디스크 부족·권한 취소·동기화 거부를 숨기지 않는다.

w+r>n은 고정 replica 집합과 상태 유지 등 전제 아래의 교집합 조건이다. 미완료 쓰기·동시 읽기/쓰기·복구·재배치·sloppy quorum·시계 오차에서 최신 값 보장을 확대하지 않는다. 실패 응답 뒤 일부 replica에 효과가 남을 수 있으므로 unknown 결과가 필요하다. 버전 벡터는 관찰된 인과 맥락을 전달하는 구조이며 단일 증가 숫자나 벽시계와 같지 않다. 오래 오프라인인 replica와 tombstone 정리·삭제 항목 부활도 실제 병합 시험으로 확인한다.

### 7장: 샤딩·재배치·보조 색인

전체 본문·참고문헌 목록과 그림 7-1–7-10을 확인했다. 후속 8–14장 검토도 아래에 기록했다.

샤딩은 측정된 저장량·쓰기 병목에 대한 선택이다. 테넌트별 분리는 백업·복구·장애 범위를 줄일 수 있으나 인증 주체에 결합된 라우팅과 교차 테넌트 거부를 대신하지 않는다. cell 사이에 공유된 인증·제어면·외부 서비스가 있으면 장애 독립성도 별도 입증한다. 개별 shard 삭제만으로 로그·백업·파생 데이터까지 삭제되었다고 주장하지 않는다.

키 개수 균등 분포와 부하 균등 분포를 구별한다. hash는 단일 hot key를 분산하지 않는다. random suffix는 쓰기를 나누면서 읽기 fan-out·병합·중복 처리·기존 키 전환 비용을 만든다. 범위 샤딩의 시간 집중과 tenant 크기 편향을 실제 분포로 시험한다. 해시 알고리즘·입력 정규화·부호 및 나머지 연산·버전의 일관성을 고정한다. 언어 기본 object hash를 영속 라우팅 계약으로 삼지 않는다.

자동 재배치는 데이터 복사·공간·네트워크·쓰기 추적 비용이 든다. 느린 노드를 죽었다고 오판해 재배치가 연쇄 과부하를 만드는 경로를 검증한다. 부하 여유·동시 이동 수·중지 조건·복구 절차가 없는 자동 확장은 개선 판정 근거가 아니다. shard 수 고정/범위 분할은 서로 다른 제약이며 split 비용은 실제 엔진에서 확인한다. 본문의 모든 split이 파일 전체 재작성이라는 설명은 제품별 보편 보장으로 옮기지 않는다.

라우팅 전환에는 구 mapping을 가진 클라이언트와 진행 중 요청이 남는다. 할당 권한·epoch/fencing·재시도 중복·cutover 중 읽기/쓰기 검증이 필요하다. local index 조회는 partition key 유무에 따라 단일 shard 또는 전체 fan-out이며, global index도 postings 조회 이후 실제 레코드 접근은 여러 shard일 수 있다. 비동기 색인은 오래된 값뿐 아니라 누락 결과를 만들 수 있어 권한 판단·유일성 판단에 무조건 사용하지 않는다. 데이터와 색인을 직접 이중 기록할 때 중간 실패와 동시 갱신을 시험한다.

### 8장: 트랜잭션·격리·분산 커밋

전체 본문·SQL 예제·표 8-1·참고문헌 목록과 그림 8-1–8-14를 확인했다. 예제의 SQL을 실제 DB에서 실행한 것은 아니다.

ACID 표기만으로 보장을 승인하지 않는다. 업무 불변식, 트랜잭션 경계, 엔진/버전/격리 설정, 복제·내구성 설정을 함께 기록한다. read committed는 읽기 시점 간 변화와 lost update를 허용할 수 있고 snapshot은 write skew를 막지 않는다. 같은 이름의 repeatable read/serializable도 제품별 의미가 다르다. 본문 SSI 설명은 교육용 단순화이며 읽은 값이 변경되면 언제나 abort한다는 구현 명세로 삼지 않는다. 직렬화는 트랜잭션 내부의 DB 연산 범위 보장이지 외부 효과·여러 요청에 걸친 사용자 편집의 전체 경쟁 방지 보장이 아니다.

원자적 증가, FOR UPDATE, version CAS, UNIQUE/배제 제약, serializable의 선택은 불변식에 맞춘다. CAS는 영향 행 수와 실패 결과를 확인하고 version 증가가 모든 쓰기 경로에 적용되어야 한다. FOR UPDATE는 반환 행만 잠그는 경우 빈 조회의 부재 조건을 보호하지 못한다. 잠금 예제에 생략된 업무 조건 검사도 실제 구현에는 필수다. snapshot에서 자신의 쓰기 가시성, 장기 snapshot의 vacuum/저장공간 영향, timeout·deadlock·serialization failure 후 전체 트랜잭션 재실행을 시험한다.

연결 끊김은 abort의 증거가 아니다. COMMIT 전송 뒤 응답 유실이면 결과가 unknown일 수 있다. 재시도는 일시 실패 분류·전체 단위·제한/백오프·중복 방지가 필요하다. 트랜잭션 안에서 외부 이메일을 보냈다고 rollback되는 것은 아니다. fsync·복제·백업은 서로 다른 장애를 줄이며 프로세스 종료 시험을 전원/장치 장애 내구성으로 확대하지 않는다.

2PL은 격리, 2PC는 원자적 결정이다. prepare 이후 참가자가 timeout만으로 독자 abort하면 원자성을 깨뜨릴 수 있다. coordinator 결정 로그는 중요 영속 상태이며 애플리케이션 재시작 시 사라지는 임시 디스크에 둘 수 없다. in-doubt 상태와 잠금 보존·결정 재조회·복구 절차를 시험한다. heuristic commit/rollback은 정상 자동 복구 규칙으로 채택하지 않는다. 단일 DB 내부 분산 트랜잭션과 이기종 XA의 운영 조건을 구분한다.

마지막 exactly-once 패턴의 'ack 성공 뒤 message ID 삭제'는 특히 조건부다. 브로커 재전달 보장, 이미 진행 중인 중복, producer 중복, 관리 replay, 백업 복원까지 포함해 다시 나타나지 않음을 증명하지 못하면 삭제하면 안 된다. 중복 키의 tenant/consumer 범위·같은 ID 다른 payload·보존기간·복원 시 정합성도 계약으로 둔다. ID 기록과 업무 쓰기를 같은 DB 트랜잭션에 넣고 동시 UNIQUE 충돌을 처리하되, 이 보장은 외부 HTTP/메일 효과까지 포함하지 않는다.

### 9장: 부분 실패·시계·fencing·검증 모델

전체 본문·코드·참고문헌 목록과 그림 9-1–9-7을 확인했다.

TCP 수신 ack는 애플리케이션 처리/커밋 증명이 아니다. timeout 후 원격 요청이 도착할 수도 있으며 연결 재생성은 중복 제거 범위를 벗어난다. 한 방향 단절·느린 노드·health check만 살아 있는 노드·응답 유실을 구분해 시험한다. 장애 감지와 부하 이동이 양의 피드백을 만들지 않도록 하며, timeout은 측정된 지연과 오탐 비용의 선택이지 사망 판정 사실이 아니다.

경과 시간은 단조 시계, 달력 시각은 wall clock으로 목적을 나눈다. 단조 시계도 호스트/재부팅 사이 비교에 쓰지 않고 suspend 포함 여부를 API별로 확인한다. timestamp 정밀도는 정확도가 아니며 NTP 설정만으로 인과 순서를 보장하지 않는다. UTC epoch 숫자 자체와 DST에 따른 현지 시각 표시 변화를 혼동하지 않는다. 본문 윤초·Java GC 목록·클라우드 QoS·규제 수치 등 시점 의존 주장은 현행 구현/공식 문서 확인 없이 실행 지침으로 옮기지 않는다.

리스 확인 뒤 멈춤, 구 소유자가 보낸 지연 요청, 재시작/복원으로 token이 후퇴하는 경우를 다룬다. fencing은 저장소가 token 비교와 쓰기를 원자적으로 수행하고 높은 token을 영속 보존해야 효력이 있다. 새 소유자가 대상 자원에 fence를 설치하기 전의 공백도 고려한다. token의 증가만으로 인증·위조 방지가 되는 것은 아니며 여러 자원에 fence를 설치해도 다중 자원 원자성은 별도다. LWW+token 예제는 정족수/복구/필드 폭·overflow/동일 epoch 순서 전제까지 필요하다.

안전성(허용하지 않은 효과·중복·불변식 위반)과 진행성(복구 후 완료 가능)을 별도로 명세한다. 모델 검사는 제한된 상태공간의 모델에 대한 증거, DST는 통제한 비결정성 범위의 구현 증거, 실제 장애 주입은 환경 통합 증거다. 어느 하나도 나머지를 대체하지 않는다. seed·스케줄·구현/모델 버전·실패 trace·탐색 한계를 보존한다. 해시 순회·메모리 고갈 등 남은 비결정성도 점검한다. 내부망이라는 이유로 입력 검증/권한 검증을 약화하지 않는다.

### 10장: 선형화·논리 시계·합의

전체 본문·참고문헌 목록과 그림 10-1–10-10을 확인했다.

선형화는 실시간 선후 관계를 지키는 단일 연산 보장, 직렬화는 다중 연산 트랜잭션의 순서 동등성이다. 둘을 혼동해 단일 CAS로 다중 객체 업무 불변식을 보장했다고 판정하지 않는다. 구현별 strict serializability/읽기 옵션은 실제 엔진 버전에서 확인한다. 합의를 사용한다는 사실만으로 follower/cache/read endpoint까지 최신성을 보장하지 않는다. 요청·응답 이력과 미완료/unknown 연산을 포함해 보장을 검증한다.

별도 메시지 채널과 저장소의 순서 차이는 잘못된 버전의 파생 산출물을 영속화할 수 있다. 작업 메시지에 불변 객체 버전/digest를 붙이고 입력 가시성·재시도·출력 출처를 대조한다. 권한 변경 후 다른 기기에서 쓰는 흐름도 검증한다. 그림 10-10의 ID 순서 해결은 예제 MVCC 조건에 대한 설명이며, ID 생성기만으로 권한 검증 전체를 대체할 수 없다.

UUID/ULID·wall timestamp·Lamport·HLC의 유일성, 정렬성, 인과성, 실시간 최신성은 다른 속성이다. Lamport의 작은 값→큰 값이 곧 인과 관계라는 역추론은 금지한다. clock/node ID 재사용·재부팅·overflow를 고려하고, autoincrement도 ID 발급 순서와 트랜잭션 commit 순서를 동일시하지 않는다. 본문 초반의 fetch-and-add와 consensus 동등성은 뒤의 'consensus number 2' 제한을 함께 읽어야 한다.

CAP를 '세 개 중 둘 선택' 규칙으로 옮기지 않는다. 연산별 장애 중 허용 동작·최신성·진행 조건을 정한다. FLP는 특정 비동기 결정적 모델의 종료 불가능성 결과이지 실용 합의 전체의 불가능 주장이 아니다. timeout 추가만으로 아무 조건에서나 종료가 보장되는 것도 아니다.

기존 검증된 합의 구현을 활용하되 membership 변경·구리더 읽기·epoch 영속성·미확정 로그 처리·snapshot 복구·부분 링크 장애를 확인한다. unclean election 등 데이터 손실을 허용하는 옵션은 복구 편의를 위해 에이전트가 자동 변경하지 않는다. 과반수/매 연산 quorum에 대한 본문 일반화는 flexible quorum·lease read 등 프로토콜 전제에 따라 다르므로 자체 알고리즘 구현 명세로 사용하지 않는다. coordination service에 대용량 업무 데이터를 넣거나, stale service discovery와 stale 권한 데이터를 같은 위험으로 취급하지 않는다.

### 11장: 배치·셔플·파생 데이터 제공

전체 본문·셸/Python 예제·참고문헌 목록과 그림 11-1–11-3을 확인했다.

재실행 가능성은 입력 snapshot·코드·환경·외부 참조를 고정하고 효과를 격리했을 때 성립한다. batch라는 이름만으로 불변/결정적/원자적 출력은 보장되지 않는다. 오류 산출물을 과거 출력으로 바꾸는 것과 그 출력으로 이미 수행한 외부 업무를 되돌리는 것을 구분한다. object store의 API 호환성과 POSIX rename/lock·목록 일관성은 다르다. cgroups 자원 제한만으로 데이터 권한 격리가 입증되지 않는다.

로그 예제는 고정 필드 위치·정상 행·문자 인코딩을 가정한다. 잘못된 행/공백 포함 요청·query string의 CSS 판정·동률 순위·locale 정렬·파이프 중간 실패를 실제 입력 계약에서 정한다. Python hash 집계의 distinct cardinality와 sort의 임시 디스크·spill·셔플 비용을 비교한다. shuffle은 모든 엔진에서 전체 정렬을 보장하는 용어가 아니므로 partition 내부/전체 순서 보장을 구분한다.

조인은 키 유일성·누락 dimension·중복 증폭·시점 일치를 검증한다. 생년월일→나이는 실행 시점 또는 사건 시점 중 어느 것을 뜻하는지 명시한다. distributed DataFrame의 순서/인덱스가 로컬 pandas와 같다고 가정하지 않는다. 부동소수 집계의 순서 차이, skew·대형 그룹·재시도 task·speculative 실행·preemption을 포함한다.

배치→Kafka→서비스 저장소는 부하 완충을 제공할 수 있지만 자동으로 전체 원자 공개를 만들지 않는다. dataset version·부분 출력·완료 manifest·검증 후 전환·구버전 유지/복귀를 설계하고 완료 메시지의 선행/유실/중복도 처리한다. bulk load도 진행 중 사용자 가시성과 증분 갱신 충돌을 확인한다. 도구 도입은 데이터 크기·빈도·비용·복구 요구가 뒷받침될 때 선택한다.

### 12장: 스트림 처리·CDC·시간·재생

전체 본문·예제·참고문헌 목록과 그림 12-1–12-8을 확인했다. 그림 12-4는 두 번째 client 1→index 화살표가 `set X = A`로 표시되어 본문의 client 2가 B를 쓰는 설명과 어긋난다. 그림의 최종 DB=B/index=A와 본문 순서 설명으로 의도를 판단하며 그대로 구현하지 않는다.

생산자→broker의 ack, 소비자 수신, 업무 효과 완료를 구분한다. drop/buffer/backpressure는 용량·지연·복구 정책이며 DLQ 이동은 업무 성공이 아니다. poison message를 건너뛸 권한과 재처리 순서·중복 방지 계약을 정한다. offset은 topic/partition 범위와 last/next 관례가 필요하다. 병렬 처리의 마지막 완료 번호가 아닌 연속 완료 범위만 commit하고 rebalance 뒤 구소비자를 차단한다. partition 수 변경은 키 순서에 영향을 준다.

보존 여유는 offset 차이뿐 아니라 이벤트 나이·남은 용량·복구 처리량으로 판단한다. 본문의 20 TB/250 MB/s 약 22시간은 단순 용량 계산이며 복제·기존 사용량·할당량을 포함한 운영 보장은 아니다. CDC snapshot과 log 위치의 일치, schema 변경, replication slot의 원본 저장공간 압박을 확인한다. outbox는 동일 DB 트랜잭션과 모든 쓰기 경로의 준수가 필요하다. dual write는 오류 없이도 순서 역전으로 불일치할 수 있다.

compaction은 완전한 현재 값 대체에 적용하며 delta/patch를 무조건 버릴 수 없다. tombstone 보존기간 밖의 소비자에서 삭제 데이터가 부활하지 않게 한다. 현재 상태 재구성과 감사 이력·시점 조인은 다른 보존 요구다. immutable event를 영구 보존 의무로 해석하지 않는다. 삭제·crypto shredding에는 backup·파생 저장소·평문·키 사본의 범위를 포함한다.

event time과 processing time을 나누고 watermark의 partition·idle source·잘못된 미래 시각·시계 신뢰 가정을 기록한다. 늦은 이벤트를 버리거나 정정하는 선택은 업무 계약이다. window 경계·시간대·late event에 의한 session 병합도 시험한다. 검색-클릭 조인은 session ID만으로 여러 검색을 구분하지 못할 수 있으므로 query/result ID와 누락 이벤트를 구분한다. stream-table 조인은 사건 시점의 차원 버전과 정정/retraction 전파를 포함한다.

exactly-once는 checkpoint 내부 범위와 외부 효과 범위를 구분한다. offset+효과의 원자성, 중복 키 범위·보존기간·결정성·fencing을 검증한다. delete도 같은 키가 재생성된 뒤 재시도하면 새 값을 지울 수 있어, 연산 이름만으로 멱등성이 보장되지 않는다. 상태 snapshot과 offset을 함께 복구하고 log 만료·partition 재분배·상태 schema 변경을 고려한다. 참고문헌 외부 원문까지 읽었다는 의미는 아니다.

### 13장: 데이터 흐름 구성·종단 간 정확성·감사

전체 본문·SQL 예제 13-1/13-2·참고문헌 목록과 그림 13-1/13-2를 확인했다. 저자가 명시한 의견 중심 장이다. unbundling은 기본 도입 지시가 아니다. 단일 제품으로 요구를 충족하면 그것을 우선하고, 분리의 운영·schema·시간·재생 결합 비용을 포함한다. 비동기 fault containment도 로그 용량·보존·공유 자원 한계 안에서 성립한다.

CDC의 순서 준수는 지연 없는 읽기를 뜻하지 않는다. 권한 철회→알림 발송처럼 샤드를 넘는 인과관계는 결과 노출 전 검증한다. 나중의 conflict merge로 이미 보낸 알림을 회수할 수 없다. logical timestamp로 번호를 정렬하는 것과 이전 메시지 도착까지 확인하는 것은 다르다. 구/신 파생 뷰 병행도 원본·과거 코드·외부 효과·신규 쓰기 호환성이 남아 있어야 복귀 가능하다. 구뷰 삭제 이후까지 '모든 단계가 쉽게 가역적'이라고 일반화하지 않는다.

읽기/쓰기 경로의 경계는 조회 비용·갱신 비용·신선도에 맞춰 정한다. 환율처럼 시점에 따라 달라지는 참조는 적용한 버전을 보존한다. offline UI의 offset 재연결은 보존 만료·권한 변경·부분 snapshot·로컬 저장 삭제를 처리해야 한다. 조회 로그에는 민감 정보가 생길 수 있으므로 감사 필요만으로 전부 영구 저장하지 않는다. stateless read 오류도 정보 노출이나 사용자의 후속 결정을 유발할 수 있어 단순 재시작으로 영향이 사라진다고 가정하지 않는다.

중복 억제는 사용자 요청부터 효과 저장까지 동일한 업무 식별자를 전달한다. 단순 입력 hash는 같은 금액의 합법적 두 요청을 합칠 수 있다. 요청 ID를 인증 주체·업무 범위·payload에 결합하고 다른 내용의 재사용을 거부한다. SQL 예제의 unique insert+balance 갱신은 한 트랜잭션이며 계좌 존재·잔액 제약·통화·권한·중복 응답 재현은 별도다. DB별 오류 뒤 트랜잭션 동작도 확인한다.

그림 13-2의 여러 계좌로 향하는 이벤트는 최종 반영 무결성을 보여 주며 모든 계좌의 동시 가시성을 보장하지 않는다. 중복 기록/상태만 저장하고 출력 이벤트 전에 죽으면 재실행을 건너뛰지 않도록 state·offset·출력의 복구 계약이 필요하다. checkpoint rollback 또는 durable outbox 등의 실제 구현으로 각 crash 지점을 시험한다. request ID만 쓰면 같은 계좌가 송신·수신·수수료 역할을 겸할 때 정상 효과까지 중복으로 제거할 수 있으므로 효과 식별자 범위를 정의한다. username sharding은 정규화·partition 변경·구소비자 fencing을 포함한다.

본문의 적시성/무결성 구분을 검증 규칙에 적용한다. timeout은 실패 확정이 아니며 처리 지연과 영구 누락을 다른 상태로 기록한다. overselling·overdraft·보상 허용은 사용자의 업무 규칙 변경 승인 대상이다. 보상은 원래 효과의 소거가 아니며 별도의 실패·재시도·한도가 있다. ACID라는 표지만으로 linearizability를 보장한다고 일반화하지 않는다.

자가 감사는 원본→최종 결과의 대조·복원 실험·누락/중복/합계 불변식으로 구체화한다. 같은 버그 있는 코드를 재실행해 같은 결과가 나오는 것은 독립적인 정확성 증거가 아니다. hash/서명은 기록 변조 탐지에 기여하나 입력이 올바르거나 빠짐없이 기록되었다는 증거는 아니다. Merkle membership도 업무 진실·전체성·현재 권한을 대신하지 않는다. 암호화는 단말 침해까지 모두 해결하지 않는다.

### 14장·용어집·후면 자료: 목적과 데이터 책임

14장 전체 본문·참고문헌 목록, 용어집 전체와 저자 소개를 읽었다. 14장에는 그림이 없다. 색인은 앞부분과 마지막 항목을 확인한 탐색용 참조이며 전 항목 정독으로 계산하지 않는다. 서문과 1–14장 전체 본문·예제·표·의미 있는 그림 검토를 마쳤다. 외부 참고문헌 원문과 책 전체 예제 실행은 이 완료 범위에 포함하지 않는다.

적용 후보: 수집 데이터마다 목적·필요성·열람 주체·보존/삭제·파생물 영향·오류 정정 경로를 정한다. 통계적 평균 성능이 개인별 결정의 정확성을 보장하지 않는다. 보호 속성을 제거해도 proxy를 통한 편향은 남을 수 있다. 자동 판단에는 이의 제기·정정·책임자와 결과의 피드백이 다음 평가 데이터에 미치는 영향을 포함한다. 시스템 자체의 지표 향상이 사용자에게 유리한 결과인지 따로 확인한다.

동의한 원래 목적을 벗어난 재사용이나 관찰 범위 확대는 자동 개선 권한으로 간주하지 않는다. 로그·오프라인 사본·backup·학습/추천용 파생물까지 삭제와 권한 범위를 연결한다. 데이터 보존은 재생/감사의 장점만으로 무기한 확대하지 않는다. 이 장의 법률·규제 사례는 책의 논의를 이해한 것이며 현재 관할별 법적 적합성을 판정한 것이 아니다.

용어집은 저자가 밝힌 대로 축약 정의다. atomic의 동시성/트랜잭션 뜻, serializable/linearizable, 멱등성의 범위를 본문과 함께 사용한다. 결정성은 시간·난수·외부 응답을 명시 입력으로 고정할 수 있는지도 함께 검토한다. CAP가 실무적으로 쓸모없다는 용어집 표현은 저자의 평가이며 보편 검증 규칙으로 채택하지 않는다.

### 앞부분·1–2장: 운영 목적과 항공사 장애

감사의 글, 서문 및 하위 절, 1장 전체, 1부 표제, 2장 전체를 순차 확인했다(f_0004–f_0025). 2장의 HA 구성과 서비스 의존성 도식은 상하단까지 확인했다. 외부 리소스 링크는 본문 독서에 포함하지 않는다.

테스트 통과와 실제 운영 적합성을 구분한다. 소규모 제품에 대형 항공사 수준의 가용성 요구를 자동 부과하지 않는다. 수명주기 비용은 사용자 부하·장애 비용·배포 빈도·유지비로 계산한다. 본문의 300분×3,000달러는 900,000달러이며 할인율 없는 예시이지 실제 ROI 근거가 아니다. 운영에서 학습하라는 주장은 제한 없는 운영 장애 주입 권한이 아니다.

항공사 사례의 핵심은 DB failover 뒤 오래된 연결, statement.close 예외, connection 미반환, pool 고갈, 상위 서비스 thread 고갈의 연쇄다. finally가 있다는 사실만으로 모든 자원이 해제되지 않는다. 각 자원 해제 실패, 예외 masking, pool 반환/폐기 의미와 대기 timeout을 검증한다. 실제 구현 언어의 자원 관리 구문을 사용하고 종료 실패까지 시험한다. 중복 하드웨어는 소프트웨어의 공통 실패를 격리하지 못한다.

HTTP 상태 페이지와 EJB 업무 thread pool이 달라 정상 health 응답이 업무 가용성을 입증하지 못했다. 핵심 업무 경로·pool 포화·대기시간을 함께 관찰하고 장애 복구 후 종속 서비스도 검증한다. 복구 우선의 사전 진단 수집은 제한된 시간·부하·민감 데이터 보호를 전제로 한다. 로그와 관찰·가설을 분리하며 마지막 변경을 원인으로 단정하지 않는다. 서비스 재시작 후 backlog와 고객 영향이 사라졌는지도 별도 확인한다.

본문의 SIGQUIT/표준 출력·RMI timeout 등 런타임 설명은 당시 구현의 맥락이다. 실제 JVM/컨테이너/드라이버 버전과 진단 권한에서 확인할 필요가 있으며 모든 Java 구현에 그대로 적용하지 않는다. 소스 접근 제약을 우회한 저자의 일화는 에이전트의 권한 확장 근거가 아니다. close 예외 계약만으로도 리뷰 후보를 찾을 수 있으므로 드라이버 내부 지식이 반드시 있어야 발견 가능하다는 주장을 일반화하지 않는다.

### 3장·4장 앞부분: 실패 전파·통합·사용자 부하

3장 전체(f_0026–f_0032), 4장 도입·Integration Points·Chain Reactions·Cascading Failures·Users(f_0033–f_0037)의 전체 본문·코드와 그림/수식 12개를 확인했다. 4장 나머지는 뒤에 계속 기록한다.

안정성은 사용자 업무의 지속 수행이다. 업무 transaction과 DB transaction을 혼동하지 않는다. longevity는 피크뿐 아니라 장기간 저부하·유휴 후 재개·데이터 증가까지 다룬다. 배포가 잦아도 외부 저장소의 누적 상태는 초기화되지 않는다. fault/error/failure는 이 책의 정의를 문맥에 맞게 쓰고 실패를 무응답만으로 제한하지 않는다. 장애 확률은 종속 사건을 독립적으로 곱하지 않는다.

pool 확대는 누수 해결이 아니며 DB 연결 한도와 동시 부하를 악화시킬 수 있다. 버린 thread가 실제 종료되지 않으면 자원은 계속 소비한다. timeout에는 획득·연결·TLS·쓰기·읽기·총 deadline과 취소 후 실제 작업 지속을 포함한다. 메시징을 도입해도 대기·중복·역압력 문제가 자동 소멸하지 않는다. failover/idle firewall 만료/부분 응답/잘못된 상태·형식/SDK callback 재진입을 고장 주입 후보로 둔다. 실제 제품 버전의 timeout·keepalive·접속 검증 동작을 확인한다.

원문 기술 설명 주의: 그림 속 spiderweb 연결 수 `2^N`은 N개 단순 노드의 직접 연결 최대치와 다르다(방향성 단순 그래프는 N(N−1), 무방향은 N(N−1)/2). SYN backlog/accept queue 동작, ICMP 'reset', ARP 풀네임 등 설명은 구현 명세로 복사하지 않는다. 패킷 캡처는 권한 있는 범위에서 수행하고 민감 payload를 별도로 보호한다. lock 순서 규약은 SDK 내부 lock·callback 실행 문맥까지 알아야 적용 가능하다.

동일 계층 chain reaction과 상위 계층 cascading failure를 분리한다. 장애 후 남은 노드의 여유 용량·새 노드 준비시간·의존 저장소 병목·quota·비용을 검증한다. autoscaling이 반응 속도만 빠르면 항상 가용하다는 주장은 충분조건이 아니다. 재시도/hedged request에는 전체 예산·지터·멱등성과 잔여 deadline이 필요하다.

사용자 부하 절은 session 보유 시간과 최악 거래 mix를 다룬다. 모든 웹 요청이 서버 메모리 session을 필요로 한다고 가정하지 않는다. weak/soft reference를 여러 언어에서 같은 메모리 부족 정책으로 취급하지 않으며 재계산 폭증·null·원본 데이터 유실을 고려한다. Redis로 옮기면 네트워크·퇴거·저장성·권한이라는 새 계약이 생긴다. pagination 재조회는 결과 일관성 요구와 함께 판단한다.

중요한 원문 오류 후보: inbound 연결마다 서버의 새 ephemeral port를 할당하며 한 IP가 약 64K 연결로 제한된다는 설명은 TCP 연결의 양 끝 주소/포트 조합 식별을 빠뜨린다. 49152–65535와 1024–65535의 포함 개수도 각각 16,384와 64,512다. 이를 근거로 IP를 추가하거나 TIME_WAIT를 무조건 줄이지 않는다. fd·메모리·outbound 대상·NAT 등의 실제 한도를 측정한다. cookie 암호화만으로 무결성이 생기지 않으며 인증/인가와 서명 검증이 필요하다. 동일 행 경합은 곧바로 deadlock을 뜻하지 않는다. 사용자 agent/IP로 자동 차단하면 공유망 사용자 오탐이 생기므로 정책과 복구 경로를 정한다. 2018년의 특허·공격 통계·robots 표준 상태·추천 baseline 기간은 현재 운영 규칙으로 자동 전환하지 않는다.

### 4장 나머지: 블로킹·자체 과부하·확장·자동화·무제한 결과

f_0038–f_0046 전체 본문·예제·각주를 확인했다. Scaling Effects의 도식 3개, Unbalanced Capacities의 도식 1개, Force Multiplier의 도식 2개도 확인했다. 이로써 4장 전체 검토를 마쳤다.

외부 synthetic 업무 검증과 내부 자원 지표를 연결한다. synthetic 호출도 실제 결제·메일 등을 발생시키지 않게 데이터/효과를 분리한다. cache miss의 remote call을 전역 lock 안에서 실행하지 않는다. bounded cache·TTL·무효화·동일 키 요청 합치기·stampede·오류/음수 결과의 캐시 의미를 함께 검토한다. immutable DTO나 CQRS만으로 동시 쓰기 불변식이 보장되지 않는다. 동기화 추가가 항상 LSP 위반이라는 일반화나 언어가 다른 LSP 위반을 모두 막는다는 설명은 채택하지 않는다.

future timeout으로 호출자가 돌아와도 worker는 계속 실행될 수 있다. worker/pool/queue 상한과 실제 취소·늦은 완료 처리·외부 효과 중복 억제가 필요하다. 모든 cache에 weak reference를 사용한다는 처방은 채택하지 않는다. 도구의 명성과 실제 버전의 테스트 증거도 구분한다.

행사·배치·설정 배포·콜드 캐시 재시작을 함께 모델링한다. jitter는 실행 시각 분산이지 시스템 시계 임의 변경이 아니다. 고정 exponential backoff만으로 동기화가 항상 풀리지 않아 지터와 전체 예산을 포함한다. 책의 전기 차단기 고정 일화는 실행 지침이 아니다. pessimistic lock 장애 시 optimistic lock으로 전환하는 것은 공통 version 검증과 불변식이 유지될 때만 가능하다. 기능적으로 조용히 제약을 약화시키지 않는다.

point-to-point의 O(N²)는 all-to-all일 때이며 모든 일대일 통신에 해당하지 않는다. TCP 자체의 multicast나 pub/sub 이름만으로 지속 보관을 기대하지 않는다. 공유 자원이 복제되어도 무한히 증설 가능한 것은 아니다. 용량 비교에는 thread 개수뿐 아니라 연산 시간·DB/연결 한도·업무 mix·rate limit을 포함하고 스트레스 제거 후 복구를 확인한다.

자동화 적용 핵심: 원하는 상태·관측 상태·관측 유효성·현재 실행 중인 변경을 구분한다. 관측 누락을 자원 부재로 간주해 정상 자원을 삭제하지 않는다. 유지보수 모드가 다른 controller의 재기동으로 취소되지 않도록 해야 한다. 관측 주기보다 긴 실행 지연에는 in-flight 작업 기록·히스테리시스·증감률·총량/비용 제한을 둔다. 책의 80% 값은 예시이며 자동 승인 임계값으로 복사하지 않는다. 새 자원 생성도 비용·의존 부하를 늘리므로 무조건 더 안전하다고 보지 않는다.

느린 응답은 서비스 처리·대기·네트워크·GC를 분리해 진단한다. 20건 이동 평균/100ms는 예시로만 사용하고 전체 latency 분포·실패율·업무 중요도로 overload 정책을 정한다. 반환 행 수·응답 bytes·객체 크기·처리시간을 제한하고 pagination에 안정 정렬/커서/동시 변경 의미를 정의한다. LIMIT만으로 DB 전체 스캔 비용이 줄어드는 것은 아니며 일부 결과를 전체 결과인 것처럼 반환하지 않는다. 표준 SQL 제한 구문이 없다는 원문 문장은 현재 구현 판단의 근거로 사용하지 않는다. 운영 규모를 닮은 데이터는 필요하지만 실제 개인정보 복제가 필수인 것은 아니다.

### 5장: 안정성 패턴 전체

f_0047–f_0060 전체 본문·예제·각주를 확인했다. Circuit Breaker의 수식·상태도, Bulkheads의 전후 도식, middleware 스펙트럼 도식도 확인했다. f_0061은 빈 페이지, f_0062는 2부 표제다.

패턴 수를 개선 지표로 삼지 않는다. timeout/retry는 전체 deadline·효과 불명 상태·중복 방지·취소·대기 자원 정리와 함께 적용한다. 책의 10–100ms나 '대부분 나중에 재시도'는 업무 계약 없이 기본값으로 채택하지 않는다. queued는 성공과 다른 상태이며 영속 수락·조회·최종 실패 통지가 필요하다.

Circuit Breaker는 오류 종류·측정 기간·최소 표본·열림/반열림/닫힘·시험 호출 수·동시 실행·수동 override 권한을 정한다. 상태 변화와 차단 자체의 결과를 관찰한다. 반열림 동시 요청이 한꺼번에 provider를 때리지 않게 한다. per-process는 저자의 권고이며 shared service mesh 등의 구현을 금지하는 법칙이 아니다. fallback의 캐시 신선도·권한·주문/결제 수락 의미 변경은 사용자 승인 대상이다. 원문 상태도의 성공 시 카운터 reset과 본문의 leaky bucket은 같은 정책이 아니므로 구현 선택을 명시한다.

Bulkhead는 업무 중요도와 공통 실패 원인을 따라 선택한다. process/VM/zone/thread pool 분리 뒤에도 DB·호스트·quota·네트워크가 공유될 수 있다. FaaS invocation 분리도 시스템 수준의 무제한 격리를 뜻하지 않는다. 관리 thread pool은 별도 인증과 자원 상한을 갖춘다. CPU affinity만으로 메모리·I/O 고갈이 격리되지 않는다.

Steady State는 누적 속도·회수 속도·보존 정책·미처리 backlog·최대 용량을 함께 기록한다. 승인 없는 삭제는 수행하지 않는다. 회전과 원격 전송만으로 유실 없는 로그 보존이 성립하지 않아 전송 장애·local buffer·재시도·중복·수집기 용량을 시험한다. cache 주기 전체 flush는 dogpile을 유발할 수 있다. 책의 파일시스템 여유 비율·법적 보존 주장·문서 DB의 dangling reference 영향은 환경별 검토 대상이다.

Fail Fast는 저렴한 형식 검증을 먼저 수행하되 도메인 불변식을 제거하지 않는다. 사전 자원 확인 후에도 실패할 수 있고, 모든 자원을 선점하면 hold-and-wait/용량 고갈이 생길 수 있다. 입력 거부·과부하·의존 장애·미확정 결과를 구분해 circuit breaker와 retry가 잘못 반응하지 않게 한다.

Let It Crash에는 격리 단위·재시작 예산·backoff·supervision·복구 상태·재통합 조건을 정한다. 언어 이름만으로 재시작 시간이 보장되지 않으며 persistent corruption·poison message·in-flight 효과는 시작 상태로 복귀하지 않는다. readiness 성공 뒤 점진적 부하 재개를 검증한다. Handshaking/부하 차단은 readiness와 liveness를 구분하고 전체 인스턴스가 동시에 제외되는 상황을 시험한다. 원문의 403='Authentication Required', 'ICMP RST' 등 표현은 정확한 프로토콜 명세가 아니므로 그대로 구현하지 않는다.

하네스는 거절·무응답·부분 응답·느린 바이트·잘못된 형식·과대 응답·인증 실패를 재현하되 대상·버전·seed·시점·관측 결과를 보존한다. mock이 실제 네트워크 계층의 동작을 입증하지 못한다는 점을 적용한다. 실제 통합 환경에서도 장애 주입은 가능하므로 '실제 시스템은 정상 동작만 시험 가능'이라는 절대 명제는 채택하지 않는다. TCP 패킷 순서 변경과 애플리케이션 메시지 순서 변경을 구분한다.

미들웨어 비동기화는 시간 결합을 줄이지만 메시지 schema·broker·순서·보존·역압력·업무 보상 결합을 남긴다. 원문의 'cascading failure가 불가능'·'total decoupling'은 과장이다. bounded queue도 소비자가 영구 중단되면 유한 응답을 보장하지 않아 deadline·거절/드롭 정책을 함께 둔다. backpressure는 caller/provider 역할과 데이터 생산자/소비자 역할을 명확히 적는다. thread pool만 나누고 unbounded worker queue를 만들지 않는다.

Governor는 자동 실행을 없애기보다 승인된 범위 내 누적 작업량·변경률·비용·효과 지연을 제한한다. limiter 상태도 재시작 후 복구되어야 한다. 허용 범위를 벗어났거나 관측이 모순되면 추가 변경을 멈추고 확인을 요청하도록 하는 후보이며, 승인된 기존 규칙을 바꾸지는 않는다.

### Release It! 2판 — 6장 전체 확인

범위: f_0061 빈 구분 페이지, f_0062 Part II, f_0063–f_0073의 모든 본문·각주 목록. f_0067·f_0069·f_0070의 세 시스템 그림을 각각 화면으로 확인했다. 외부 각주 사이트는 읽지 않았다.

사례는 완료된 요청의 지연만으로 장애를 놓칠 수 있음을 보여준다. 진행 중 요청의 나이·timeout·대기열·pool 대기를 함께 측정한다. 프런트의 여유 CPU는 하류 병목이 없다는 증거가 아니다. 3,000→450→25 thread의 연쇄에서 마케팅 변경과 하류 유지보수가 유효 용량을 바꿨다. thread 수를 그대로 처리량으로 환산하지 않고 실제 부하·서비스 시간·공유 경로를 확인한다. 원문은 프런트 100 servers라고도 쓰지만 그림은 20 hosts/75 DRPs이므로 일관된 수치 모델로 재사용하지 않는다.

별도 scheduling pool이 기능별 제한 지점을 제공했다. max=0과 checkoutBlockTime=0을 설정해도 시작 시 읽는 설정이라 효과가 없었고 해당 component 재시작이 필요했다. 따라서 desired 설정·적용된 설정·관측된 효과를 분리한다. 회복한 인스턴스 한 대로 모든 부하가 몰렸으므로 readiness와 복귀 속도·여유 용량을 함께 검증한다. 전체 재시작보다 작은 복구 단위를 우선 검토하되 in-flight 결과와 공유 자원을 확인한다.

home delivery를 끄는 것은 업무 동작 변경이다. 사례의 사업 책임자 판단을 에이전트의 임의 fallback 권한으로 일반화하지 않는다. 연결 수 조절도 서버별 합계·하류 실제 용량·재시작 비용·복구 조건을 포함한다. 반복 CPU 경고가 무시되던 상황은 임계값 삭제 근거가 아니라 사용자 영향과 연결한 경보 품질 개선 후보로 남긴다. 유지보수와 캠페인 일정은 배포/부하 검증 입력이다.

### Release It! 2판 — 7–8장 전체 확인

범위: f_0074–f_0082 모든 본문·코드·각주 목록. 그림: 7장 책임 계층과 4-NIC 네트워크 각 1개, 8장 배포/실행 관점 2개와 누적 변경/불변 이미지 2개 전부 시각 확인. 외부 링크는 별도 확인하지 않았다.

실행 환경 책임을 기반 시설·인스턴스·연결·제어·운영으로 나눠 누가 무엇을 검증하는지 적는다. 이름/주소/인스턴스의 수명을 분리하고 bind 주소·외부 광고 주소·DNS·라우팅·관리 경로를 실제 환경에서 검증한다. wildcard bind를 무조건 금지하거나 특정 hostname bind를 보안 보장으로 삼지 않는다. 컨테이너 네트워크 namespace와 노출 정책을 함께 본다. 원문의 FQDN=hostname+search domain, 모든 다중 경로=설정 오류, NIC당 64,000 연결 상한, VXLAN이 IP header에 24 bits를 추가한다는 설명은 그대로 규칙화하지 않는다. 해당 프로토콜/플랫폼의 정확한 명세가 필요한 부분이다.

CPU 아키텍처·오케스트레이터 우세·클라우드 순위·VM IP가 매 부팅 변경된다는 설명은 2018년 서술이며 현재 환경 사실로 사용하지 않는다. VM 자원 경합과 pause, wall clock 변경을 시험하되 NTP를 쓴다고 단조 증가나 분산 순서가 보장되지 않는다. storage는 처리량뿐 아니라 지연 꼬리·내구성·일관성·복구 특성을 본다. 컨테이너 시작 1초는 저자의 목표 예시이며 보편 기준이 아니다. 긴 초기화를 이유로 컨테이너 사용을 일괄 금지하지 않고 readiness·시작 예산·warmup·확장 지연을 정한다.

배포 산출물과 실행 중 프로세스를 구분한다. 같은 검증된 artifact를 환경 간 승격하고 소스·의존성·빌드 도구/플러그인·설정 버전·실제 실행 digest의 연결을 남긴다. 사설 저장소·서명·CI 서버만으로 신뢰가 완성되지 않아 허용된 발행자/키·격리·권한·변조 방지와 검증 대상의 연결이 필요하다. 'only code in version control'은 lockfile·배포 선언·검증 자료를 배제하는 규칙이 아니다.

불변 이미지 재생성은 누적 설정 드리프트를 줄이지만 volume·DB·외부 효과를 초기화하지 않는다. 이미지가 같다는 이유로 권한·네트워크·환경 설정까지 같다고 주장하지 않는다. 비밀은 소스/이미지/로그에 넣지 않는다. 별도 Git 저장소만으로 비밀 보관을 해결하지 않으며 공급 경로·최소 권한·회전·폐기를 정한다. env/user-data 공급도 노출 경로를 검토한다. 설정 schema·기능을 드러내는 이름·단위·기본값·검증·실제 적용 시점을 명시한다. 설정 서비스는 추가 가용성 의존성이므로 현재 필요와 운영 비용으로 결정한다.

관측 정책과 수집을 분리하되 관측 대상의 의미를 잃지 않는다. 로컬 개선이 최종 사용자 결과를 개선했는지 end-to-end로 확인한다. 로그의 시간상 인접함을 원인으로 단정하지 않는다. 'Reset required'와 같이 실행 주체가 불명확한 메시지 대신 대상·원인·자동 조치 여부·최종 결과·필요한 운영 조치를 적는다. correlation ID는 범위·위변조·개인정보 노출을 관리하고 session token을 그대로 로그에 남기지 않는다. 관측 전송 실패·역압력·비용·sampling도 검증한다.

### AI Engineering — 2장 전체 본문·도표 확인

샘플링 설정과 모델 버전을 고정하되 temperature 0·seed 고정도 모든 하드웨어/서빙 경로에서 동일 출력을 보장하지 않는다. 토큰 확률·평균 logprob는 사실 정확도나 업무 성공 확률이 아니다. 반복 생성은 횟수·비용·시간 한계를 설정하고 성공 후보 선택기를 별도 검증한다. 다수결은 공통 오답을 제거하지 않고 최고 점수 선택은 평가기 허점을 증폭할 수 있다. 구문이 유효한 SQL이 권한과 업무 의미까지 올바른 SQL은 아니다. 문법 수정 후에도 원출력·수정 내용·재검증 결과를 남기며 잘린 출력을 임의 보완해 성공으로 처리하지 않는다.

JSON 문법·스키마·업무 불변식·실행 권한·실제 효과를 서로 다른 검증으로 둔다. classifier head도 클래스 중 하나를 고르게 할 뿐 올바른 클래스임을 보장하지 않는다. 과거 YAML 복구율 99.99%는 우리 출력 검증 기준을 완화하는 근거가 아니다. 생성 retry는 아직 실행 전 단계로 제한하고 이미 실행한 외부 효과의 retry와 분리한다. 캐시는 사용자/권한/자료·모델 버전을 키와 무효화 정책에 반영해야 하며 일관된 오답을 고착시킬 수도 있다.

### AI Engineering — 3장 전체 확인

범위: ch03.html 전체 본문(약 9.4만 자)·표 3-1–3-6·코드·수식·각주 1–24, 그림 3-1–3-10(3-7 하단 추가 확인).

검증 설계 적용: 자동 개발의 완료 판정은 실제 의도한 동작의 증거를 중심으로 한다. 테스트 통과는 명시된 사례에 대한 결과이며 보안·운영·요구사항 완전성 전체를 증명하지 않는다. pass@k는 k개 중 성공 후보 존재 비율이라 실제 후보 선택과 1회 운영 성공률과 다르다. 생성 코드의 실행은 격리·시간·자원·권한 제한 아래 수행한다. 기준 답안도 틀리거나 가능한 정답을 빠뜨릴 수 있어 실패를 곧바로 구현 탓으로 돌리지 않는다. 그렇다고 에이전트가 통과 목적으로 기준을 바꾸지 않고 근거와 반례를 변경 제안으로 남긴다.

평가 계약에는 데이터·판정기·모델·프롬프트·샘플링·채점 척도·집계 방법 버전을 함께 둔다. judge 변경 때 같은 고정 사례를 구/신 판정기로 교차 평가해야 제품 개선과 평가기 변화가 분리된다. 자기 검토는 보조 점검이며 독립 검증으로 표시하지 않는다. 순서 교환·반복 판정·길이와 문체 통제·근거 대조로 judge의 순서/자기/장문 선호를 점검한다. 그럴듯한 판정 이유도 증거의 진위를 보장하지 않는다. 표본 검토는 전체 검사로 보고하지 않고 분모·선정 방법·미검사 범위를 남긴다.

유사도·정확도·선호의 구분: 정확한 산술로 계산한 유사도라도 의미상 옳다는 판정은 아니다. 문장 포함 매칭은 5가 들어간 오답도 통과시킬 수 있다. 숫자·부정·주체·단위·시점 차이는 임베딩 유사도가 높아도 업무상 치명적이다. cosine=1은 양의 스칼라 배수 벡터에도 성립하고 zero vector는 분모가 0이다. 같은 차원만으로 다른 embedding 모델 공간의 벡터를 직접 비교할 수 없다. 모델·전처리·버전 일치와 실제 검색/분류 업무 평가가 필요하다.

통계 해석: 엔트로피 예시 1/2 bits는 동일 확률 가정 아래다. perplexity는 동일 데이터·tokenizer·문맥 길이·계산 규칙에서 비교하며 정확도 역수로 일반화하지 않는다. 낮은 perplexity만으로 학습 데이터 포함·암기·중복을 확정할 수 없다. ASCII 7비트라는 문자 정의와 실제 파일의 1바이트 저장을 혼동하면 BPB 비용 계산이 틀린다. 본문/그림의 성장 곡선이나 GitHub 도구 수는 투자액을 직접 측정하지 않는다. 그림 3-6의 image encoder 출력에도 Text embedding 라벨이 붙어 있다.

비교 순위는 절대 출시 기준이 아니다. 두 후보 모두 불합격일 수 있고 승률이 업무 해결률로 바로 환산되지 않는다. 동률·둘 다 실패·판정 불가를 보존한다. 순환 선호와 다른 질문/평가자 분포가 존재하면 모든 쌍에 맞는 단일 순위를 보장할 수 없다. 공개 리더보드의 표본·게임 가능성·시점을 명시하고 업무 데이터에서 품질/비용/지연 기준을 별도로 확인한다. 개인정보와 사내 데이터를 외부 judge로 보내는 것은 별도의 데이터 전송 경계다.

### AI Engineering — 4장 전체 확인

범위: ch04.html 전체 본문(약 11.7만 자)·표 4-1–4-7·프롬프트·각주 1–29, 그림 4-1–4-10. 긴 4-9 상하단도 확인했다.

적용: 요구사항을 업무 능력·생성 품질·지시 이행·비용/지연으로 나눠 각각 관측한다. 하드 제약과 개선 목표를 구분하고 하나의 평균으로 권한·정확성 실패를 상쇄하지 않는다. 최종 작업·턴·중간 구성요소를 함께 평가해 어디서 실패했는지 찾는다. PDF 추출과 추출된 텍스트 해석이 따로 성공해도 실제 end-to-end 결과를 확인한다. 범위 밖 요청·존재하지 않는 대상·불충분한 근거·긴 입력·오타·한국어를 평가 집합에 포함한다. 변경 구현에 반복 사용한 개발용 사례와 최종 검증 사례를 분리하며, 평가 데이터를 학습 자료로 재사용하면 더 이상 독립 검증 집합으로 세지 않는다.

사실성 구분: 주어진 문서에 충실한 답과 외부 세계에서 참인 답은 별개다. 출처의 날짜·권한·신뢰성과 상충 자료를 함께 기록한다. supported/contradicted/unknown을 보존하고 검색 결과가 없다는 것을 거짓 증명으로 바꾸지 않는다. 여러 번 같은 답을 생성해도 사실임을 입증하지 못한다. SAFE식 원자 주장 분해에서도 대상·조건·시점·관계가 손실될 수 있어 원문 연결이 필요하다. 실행 검증은 주장에 대한 검색보다 실제 상태·부작용·테스트 증거를 우선한다.

평가 진화 제안: 규칙 변경 요청에는 관측된 미검출/오탐, 원인 가설, 구/신 규칙의 같은 사례 판정, 비용·영향, 적용 버전·재검증 대상을 넣는다. 인간 확인 전에는 기존 승인 기준을 유지한다. 온/오프라인 품질과 업무 지표의 관계는 실제 데이터로 확인하며 책의 사실성 80/90/98%와 자동화 30/50/90% 예시는 우리 임계값이 아니다. INFOBench처럼 일부 조건 충족 비율과 모든 필수 조건을 충족한 작업 성공률도 구분한다.

표본 검토: 동일 사례의 paired 비교와 사용자/작업 단위 의존성, 희귀 치명 실패, 여러 후보를 반복 선택한 효과를 고려한다. bootstrap은 관측하지 못한 실패군이나 편향된 모집단을 만들어 주지 못한다. 표 4-7의 10/100/1,000/10,000개는 가정이 필요한 근삿값이며 보편적인 95% 보장이 아니다. 표 4-6의 Simpson 예시는 후보 간 집단별 표본 구성이 다르다. 같은 가중치의 동일 평가 집합에서 모든 부분집합 우위가 총합에서 역전한다고 오해하지 않는다. 상관 없음에서 인과적 영향 없음을 추론하지 않는다.

원문 주의: 표 4-5에서 HellaSwag–TruthfulQA 0.4809와 반대 방향 0.4228은 상관행렬의 대칭성에 맞지 않는다. logprobs를 30–40%로 부르는 설명은 확률과 로그확률을 혼동한다. 낮은 perplexity/13-gram 일치는 오염 후보 증거이며 확정이나 무조건 삭제 근거가 아니다. 모델 가중치 공개를 라이선스와 무관하게 open source라 부르는 것은 이 책의 편의적 정의다. Gemma Apache 2.0 주장, Llama 출력 학습 금지 설명, 저작권·상업 API 계약 책임은 현재 법률/라이선스 판단에 사용하지 않고 실제 버전의 원문 확인이 필요하다. 공개 모델은 항상 뒤처진다는 예측과 self-host 기능 제약 표도 시점 의존적이다.

호스팅 판단은 모델 성능만 아니라 데이터 전송·보존·계약·모델 접근 중단·운영 인력·실제 부하·에너지·장애 비용으로 한다. 같은 모델명/호환 API도 공급자별 처리·안전 필터·샘플링 차이가 있어 교체 회귀 검증이 필요하다. 관측되지 않은 공급자 변경은 재검증 신호이며 자동 합격 근거가 아니다.

### AI Engineering — 5장 전체 확인

범위: ch05.html 전체 본문·표 5-1–5-4·코드·공격/방어 예시·각주 1–22, 그림 5-1–5-16. 큰 5-6은 앞뒤에서 범례와 하단 축도 확인했다. 책 속 공격 문자열은 검토 자료로만 읽었고 실행하지 않았다.

적용 후보: 프롬프트의 목표·입력·출력·예시·불확실 시 행동을 명시하고 실제 렌더링 결과를 확인한다. 공급자 chat template와 업무 prompt template를 구분해 버전을 고정한다. 프롬프트/모델/전처리 변경을 독립 사례와 시스템 전체에서 비교한다. 단순한 프롬프트부터 시작하며 최적화 도구의 숨은 요청 수·비용·기본 프롬프트도 관측한다. 자동 prompt search는 개발 평가 집합에 대한 최적화이고 승인된 기준이나 holdout을 자동 수정하지 않는다.

분해는 독립 관측과 오류 국소화에 도움이 되지만 분류 오류·중간 상태 손실·추가 호출·TTFT 증가를 만들 수 있다. 병렬화는 독립된 읽기/계산에 적용하고 상태 변경의 충돌·실행 순서를 따로 검증한다. 긴 문맥을 받을 수 있다는 것과 모든 정보를 정확히 활용한다는 것은 다르다. 정보 위치·상충 사실·부정 조건·멀티홉·실제 작업 완료를 평가하며 단일 needle 회수만으로 저장소 전체 이해를 선언하지 않는다. 역할 지시는 전문성/정답/권한을 부여하지 않고 CoT/자기 검토도 실제 실행 증거를 대신하지 않는다.

자율 실행의 경계: 검색 문서·이메일·코드 주석·도구 결과는 업무 데이터이며 실행 권한을 새로 부여할 수 없다. 허용된 principal/tenant/action/resource 범위는 모델 밖의 도구와 저장 계층에서 검증한다. 프롬프트에 비밀을 넣고 공개하지 말라고 하는 방식은 격리가 아니다. SQL의 DELETE/UPDATE 문자열 필터 대신 실제 동작·권한·파라미터·대상 범위를 통제한다. VM도 네트워크·호스트 mount·자격 증명이 열려 있으면 피해를 제한하지 못한다. 자동화는 승인된 행동 범위 안에서 수행하고 범위 확대나 규칙 변경을 사용자 확인으로 보낸다.

평가는 공격 성공률만 아니라 정상 요청의 잘못된 거절률을 함께 본다. 차단/수정/거절이 발생한 정확한 단계와 실행 효과를 기록한다. 반복 요청 자체만으로 악의라고 확정하지 않으며 Unicode/낯선 문자 차단은 한국어와 정상 입력도 손상시킬 수 있다. 문구 반복·입출력 필터·계층 학습은 방어층이지 완전한 보증이 아니다. 민감한 최종 프롬프트를 디버깅 로그에 그대로 남기지 않고 마스킹·접근·보존 기준을 둔다.

원문 검토: Git과 함께 관리하면 모든 소비자가 자동 업데이트된다는 설명은 배포/버전 pin 방식에 따라 다르므로 별도 prompt catalog 도입의 필연적 근거가 아니다. 예제 query_openai에는 결과 반환이 없고 datetime import도 생략되어 있어 실행 가능한 완성 코드로 다루지 않는다. IT support 예제의 {"IT support requested"}는 JSON object가 아니다. 그림 5-6의 SVAMP 풀이는 수학 벤치마크와 맞지 않는 생물정보학 용어로 적혔다. 그림 5-2는 일부 날짜 순서와 앞 문단의 GPT 세대별 문맥 수치가 맞지 않는다. 허용 corpus로만 훈련하는 것 역시 유추/생성에 의한 범위 밖 출력을 불가능하게 하지 않는다. 특허·저작권 비유와 데이터 암기율은 일반 법률 판단이나 모든 모델의 고정 위험률로 옮기지 않는다.

### AI Engineering — 6장 전체 확인

범위: ch06.html 전체 본문(약 11만 자)·표·코드·수식·각주, 그림 6-1–6-16. 긴 6-12·6-15는 상하단을 나눠 확인했다.

검색 적용: top-k 검색은 관련 자료 선택이지 전체 읽기나 전체 검사의 증거가 아니다. 이 독서 작업처럼 완전한 범위가 필요한 일은 목차/항목 목록과 읽기 기록의 대조가 필요하다. BM25 기준선에서 시작해 실제 업무 데이터로 embedding/hybrid의 이익을 확인한다. 정확한 최근접 이웃도 업무상 정답은 아니며 ANN recall과 문서 관련성 recall, 최종 작업 성공률은 분리한다. chunk 단위·중복·분모와 문서 버전/위치를 기록한다. 사용자/tenant별 접근 필터와 삭제 전파는 검색·캐시·문맥 구성 모두에서 확인한다.

구현 조건: query/corpus embedding 공간과 전처리를 맞춘다. chunk 크기의 단위, 전체 prompt와 출력 예약분을 포함한 문맥 예산을 확인한다. overlap이 의미 보존을 보장하지 않는다. 식별자 검색에는 lexical 방식도 평가하며, 순차 검색의 첫 필터가 정답을 제거하면 후속 reranker가 복구할 수 없다. query rewrite는 원래 대상·기간·의도를 보존해야 하고 생성 metadata를 원문 사실로 표시하지 않는다. 새 문서라는 이유만으로 더 권위 있다고 판단하지 않는다.

도구 계약에는 principal/action/resource, 입력·출력 schema, 사전·사후조건, 버전, timeout, idempotency, 결과 불명 상태를 둔다. 읽기 도구도 데이터 전송·비용·rate limit을 일으킨다. 계획 검증과 실행 직전의 권한/상태 검증을 분리하고 requested/attempted/confirmed를 실행 기록으로 구분한다. 글로 backtracking한다고 외부 쓰기가 취소되지 않는다. 재시도는 총 시간·비용·횟수에 묶고 unknown 결과는 조회/조정한다. 동시 도구 호출은 상태 충돌과 읽은 시점 차이를 고려한다.

완료 판정: 50명 중 40명만 배정하고 끝났다고 하는 본문의 사례처럼 자기 reflection도 실패할 수 있다. 전체 대상 수·필수 조건·실제 결과를 대조한다. 자연어 계획을 다른 모델이 API로 번역하면 새로운 계약 경계가 생긴다. required tool choice는 올바른 도구·인자·효과를 보장하지 않는다. 자주 이어 쓰는 도구라도 권한/트랜잭션 경계가 다르면 자동 합치지 않는다. 도구 ablation의 평균 점수만으로 드문 복구 도구를 제거하지 않는다. 한 번 성공한 새 skill은 자동 신뢰 대상으로 승격하지 않고 회귀·권한·버전을 확인한다.

메모리 적용: 요약은 목표·제약·완료/미완료·실패·증거를 보존해야 한다. FIFO 제거로 최초 요구사항을 잃지 않게 한다. 새 문장은 기존 승인 규칙을 자동 대체하지 않는다. 자주 필요한 정보도 최신 권한/가격/상태라면 finetuning 대상으로 적합하지 않을 수 있다. 외부 memory 삭제가 캐시·백업·학습된 가중치까지 삭제했음을 뜻하지 않는다.

원문 주의: TF-IDF 설명의 N/df와 log 수식 차이, Annoy를 LSH로 묶은 뒤 random tree로 설명하는 부분, PQ를 일반적 차원 축소로 설명하는 부분은 구분한다. RRF의 60은 예시 상수다. Elasticsearch와 BM25는 제품과 알고리즘이므로 같은 층의 대안이 아니다. SQL 예시의 product_name/schema 명칭, 최근 7일의 자정/rolling 기간·미래 행·시간대·NULL 합계·환불 조건은 실제 schema/업무 계약에 맞춰야 한다. 도구 이름도 get_today_date/get_time 등 앞뒤에서 바뀐다. 그림 6-10의 int는 JSON Schema integer와 다르며 소수 중량 처리도 빠져 있다. 단계별 95%의 거듭제곱은 일정한 조건부 성공률 등 가정이 있는 예시이지 실측 위험률이 아니다. 그림 6-13의 괄호 개수 비교는 올바른 중첩/순서 검사를 대체하지 못한다. 메모리가 limited이면 삭제가 불필요하다는 문장은 앞뒤 논리와 반대다. 예제·프레임워크를 그대로 운영 코드로 승격하지 않는다.

### AI Engineering — 7장 전체 확인

범위: ch07.html 전체 본문(약 11.4만 자)·표 7-1–7-7·수식·각주 1–37, 그림 7-1–7-20(7-11 하단 추가 확인).

적용 판단: 실패 원인을 정보 부족, 행동/형식, 도구/시스템 문제로 나눈 후 prompt·검색·모델 변경·finetuning을 비교한다. RAG는 사실, finetuning은 형식이라는 요약은 출발점이며 배타적 분류나 보장이 아니다. prompt 실험의 지표·버전·회귀 집합을 먼저 갖추고, 실제 부족분과 총 유지 비용이 확인될 때 학습을 선택한다. 특화 모델이 반드시 우세하지 않으며 한 작업의 개선은 다른 작업의 회귀를 허용하는 근거가 아니다. 새 base model로의 교체·재학습·복구 기준도 필요하다.

자원 계획: 가중치 N×바이트 계산은 하한에 가깝다. KV cache·activation·optimizer·gradient·master weights·임시 버퍼·batch/sequence·장치 분할과 변환 비용을 포함해 측정한다. 추론 메모리 1.2배는 예시 가정이고 예약량으로 고정하지 않는다. checkpointing은 재계산 비용과 교환한다. 작은 학습으로 데이터 입출력·저장·재시작까지 먼저 검증한다. batch 크기와 effective batch/누적·학습률·손실 masking·epoch·seed를 기록하고 held-out 작업 성능으로 비교한다. 학습 loss 하락만으로 성공을 선언하지 않는다.

LoRA 적용: W를 고정하고 저랭크 업데이트 AB를 학습한다. 배포 때 합친 가중치와 분리 adapter 방식의 지연·저장·전환 비용을 실제 부하에서 비교한다. tenant별 adapter 선택도 인증된 identity에 묶어야 한다. base weights/tokenizer/template/adapter/quantization 조합을 고정하고 merge 후에도 회귀를 확인한다. 양자화는 dtype·range·kernel 지원·변환 비용을 함께 검증한다. QLoRA의 저장 4비트가 전체 계산·optimizer까지 4비트라는 뜻은 아니다. 모델 합성은 실험적 선택이며 원 모델의 모든 능력·안전 성질의 합집합을 보장하지 않는다. 학습/합성 데이터의 출처·권한·평가 오염도 별도로 관리한다.

원문 수학/구현 주의: LoRA를 원래 W의 분해라고 부른 설명은 업데이트 행렬 분해와 혼동된다. 임의 9×9 행렬은 rank-1 곱으로 정확히 표현할 수 없다. factor의 열/열이라고 적힌 rank 설명은 첫 행렬의 열과 둘째의 행이어야 한다. 표 7-6의 GPT-3 r=2 query/key 조건은 앞에서 계산한 네 행렬 18.87M과 불일치한다. 연결한 adapter의 설정 rank 합과 결과 행렬의 실제 rank는 다를 수 있다. 그림 7-15의 (0.04+0.6)/2=0.32는 맞지만 모든 가중치 평균이 의미를 보존하지 않는다. 학습 gradient는 손실에 대한 국소 미분이지 원인 기여량의 완전한 측정이 아니다. 층 수 1/10만 학습한다고 항상 파라미터 10%가 되지는 않는다.

원문 외부 확인이 필요한 주장: Sonnet 70B 표기, GPT-4-0314 각주의 2024년(앞 문단 2023년과 충돌), BitFit을 추가 adapter로 분류한 설명, Mixture-of-Agents를 가중치 layer stacking 사례로 묶은 설명, SOLAR의 summing 설명은 현재 구현 근거로 채택하지 않는다. 그림 7-19는 두 32층 모델에서 각 24층을 택하는 모습으로 본문 16층 summing과 다르다. TF32 유효 연산 정밀도 19비트를 저장 19비트로 환산하지 않는다. GitHub issue 수는 사용량의 편향된 대리 지표다. 학습률 범위·10% prompt loss·batch 8·rank 4–64·예제 수는 보편 규칙으로 승격하지 않는다.

### AI Engineering — 8장 전체 확인

범위: ch08.html 전체 본문(약 9.2만 자)·표 8-1–8-4·예제·각주 1–16, 그림 8-1–8-7(8-4 하단 축 추가 확인).

적용 후보: 데이터 계약을 quality/coverage/quantity로 나누고 실제 작업·언어·기간·사용자군·오류·멀티턴·도구 실패의 분포를 확인한다. 수집 경로·사용 목적·버전·권한·처리 이력·보존/삭제를 기록한다. 사용자 로그라고 모두 대표적이거나 재학습에 사용할 수 있는 것은 아니다. 관측된 사용자, 실패 후 이탈, 피드백 제공자의 선택 편향을 확인한다. 동일 지침으로 평가/학습 annotation을 만들더라도 사례와 파생 계보는 분리한다. holdout을 합성 seed로 쓰면 독립 평가 집합으로 유지할 수 없다.

합성 검증: 생성한 사례·정답·테스트가 같은 잘못된 전제를 공유할 수 있다. parser/linter/unit test 통과와 실제 요구 충족을 분리한다. 합성 API 결과는 실제 API 효과의 증거가 아니다. 역번역 일치는 왕복 과정의 같은 오류나 정보 손실을 놓칠 수 있어 의미·단위·경계·실행으로 보완한다. password reset과 change는 서로 다른 권한/상태 흐름이므로 단순 동의어로 증강하지 않는다. crop·회전·단어 치환이 label을 보존하는지 확인한다. 희귀 실패를 outlier라는 이유만으로 삭제하지 않는다.

정제 적용: 원본을 보존 가능한 범위에서 유지하고 파생본을 새 버전으로 만든다. 소규모 trial로 schema·tokenizer·template·loss masking·샘플 수·분포 변화·복구를 확인한다. 정제 순서는 비용만 아니라 의미와 중복 판정에 영향을 준다. HTML/Markdown/공백은 코드·구조 의미를 가질 수 있어 무조건 제거하지 않는다. 근접 중복은 후보이고 숫자·부정·시점·권한이 다른 사례는 합치지 않는다. Bloom filter의 양성은 실제 중복 확정이 아니다. split은 문서/사용자/대화와 합성 원본 계보의 누출을 방지한다.

검증의 한계: AI가 선호한 사례를 반복 학습하면 판정기 편향을 증폭할 수 있다. 순서 교환은 position bias 일부만 다룬다. 합성 데이터가 현실적으로 보인다는 것은 사실성·대표성·개인정보 비포함 증거가 아니다. 재귀 생성의 collapse는 조건에 따라 평가해야 하며 일정 혼합 비율의 보편 보장은 없다. 제거한 학습 행이 이미 학습된 모델에서 잊혔다는 뜻도 아니다. 크기별 학습 곡선을 독립 검증 집합에서 비교하고 작은 데이터에서의 성공/실패를 무조건 외삽하지 않는다.

원문 주의: 16조 tokens÷2,000은 80억 examples이며 본문 150억과 다르다. 수집 예제의 100 templates가 다음 문장에서 10으로 바뀐다. 그림 8-6의 unique verb-noun 수는 GPT-4 5,229, GPT-3 6,133으로, GPT-4가 더 다양한 조합이라는 본문 단정과 일치하지 않는다. 그림 8-2는 데이터량뿐 아니라 epoch도 16과 1로 다르다. mushroom을 일괄 edible로 붙인 예시는 실제 식용 판정에 사용할 수 없다. 특정 논문의 개선률·합성 비율·표본 수·제거 휴리스틱은 해당 실험 조건을 벗어나 규칙으로 채택하지 않는다. 데이터 라이선스/개인정보 법률의 일반화는 하지 않고 실제 도입 시 해당 출처와 계약을 확인한다.

### AI Engineering — 9장 전체 확인

범위: ch09.html 전체 본문(약 8.6만 자)·표 9-1–9-3·수식·각주 1–27, 그림 9-1–9-19. 긴 9-10은 표시된 원본 이미지로 전체 확인했고 9-14는 하단 축을 추가 확인했다.

적용 후보: 최적화 전 실제 부하의 입력/출력 길이·동시성·도착률·cold/warm cache·실패/취소를 측정한다. 사용자에게 첫 결과가 보이는 시간과 모델 내부 TTFT를 구분한다. p50/p95/p99뿐 아니라 timeout·누락 요청을 분모에 포함하고 최종 작업 완료 시간도 본다. 처리량보다 정해진 품질/지연 조건을 함께 만족한 처리량과 성공 작업당 총 비용을 우선한다. 모델 품질을 고정한다고 serving 변경의 회귀 검사를 생략하지 않는다. quantization·kernel·batching·routing이 결과/수치·기한 내 완료에 미치는 영향을 검증한다.

병목과 비용: compute·대역폭·용량·queue·통신을 구분해서 측정하고 최적화 후 병목 이동을 확인한다. 가중치당 바이트나 GPU 활동률만으로 효율을 확정하지 않는다. prefill/decode 분리는 실제 병목과 통신 비용이 정당화할 때 적용한다. batch는 대기 상한·취소·공정성·긴 요청의 영향까지 확인한다. cache는 모델/template/tokenizer/권한/데이터 버전과 연결하고 invalidation·TTL·저장 비용·miss 경로를 테스트한다. prompt cache는 계산 재사용이지 모델의 완전한 이해나 최신 사실 보장이 아니다.

안전한 최적화: streaming 뒤 삭제해도 이미 노출된 내용이나 발생한 부작용을 되돌릴 수 없다. 출력 검사가 필요한 작업은 공개/실행 시점 전에 검사한다. speculative decoding은 정확한 수락/보정 알고리즘이 있어야 분포 보존을 주장할 수 있고 단순 일치 비교만으로 일반 sampling을 대체하지 않는다. draft 품질·거절률·K·추가 메모리·실제 지연을 측정한다. 구조/정밀도/attention window 변경은 별도 품질 검증 대상이다. sparse 값이 늘어도 지원 layout/kernel이 없으면 저장·속도 이득은 자동 발생하지 않는다.

수식/그림 검토: TTFT가 첫 토큰을 포함하고 TPOT가 이후 간격이면 전체 시간은 TTFT+(N−1)×TPOT다. TTFT 예제의 10개 값은 합 3,900ms, 평균 390ms로 산술상 맞지만 평균만으로 꼬리 지연을 설명할 수 없다. 그림 9-4에서 TTFT≤200 및 TPOT≤100을 모두 만족하는 것은 150/70과 140/60 두 요청이다. 170/105는 실패하므로 caption의 3RPS와 다르다. 7B×2bytes×100/s=1,400GB/s이며 본문의 700GB/s는 산술 오류다. 1,400/2,000=70%이나 본문 700/2,000은 35%다. 이 bandwidth 근사도 batch에서 가중치 공유 및 KV traffic을 반영하지 못한다.

원문 주의: attention 계산을 exponentially라고 부른 본문과 각주 O(n²)는 모순이며 일반 full attention은 제시 조건에서 이차 증가다. KV 식은 MHA 조건의 근사로 GQA/MQA의 KV head 차원·분할·overhead를 반영해야 한다. batching이 throughput을 reduce한다는 문장은 주변 설명과 반대다. SLO는 service-level objective다. sequence parallelism을 attention/FFN 기계 분리로 설명한 부분은 실제 프레임워크 정의 확인 전 구현 근거로 사용하지 않는다. 소비자 GPU HBM 24–80GB, 전력·cloud 가격·제품 지원 현황은 집필 시점/제품군을 혼합한 수치라 현재 구매 기준으로 쓰지 않는다. 컴퓨트 최적화 사례는 출력 품질 평가가 빠진 경우를 명시한다.

### AI Engineering — 10장 및 에필로그 전체 확인

범위: ch10.html 전체 본문(약 8.3만 자)·표 10-1·gateway 코드·각주 1–12, 그림 10-1–10-21. 10-11·10-14·10-17은 잘린 상하단도 확인했다. afterword01.html 에필로그 전체(그림 없음)를 읽었다.

아키텍처 적용: 필요한 실패를 해결할 때만 retrieval/router/gateway/cache/orchestrator를 더한다. 승인된 task와 규칙 버전, 실행 권한, 결과 기록, 검증 판정의 최소 흐름부터 구성한다. 복잡한 패턴 자체가 목표가 아니다. 관측은 처음부터 설계하고 구성요소의 시작/종료/실패/결과 불명·도구 효과·버전·비용을 연결한다. 실패율/탐지/응답/복구 시간은 시작·끝·분모를 정의한다. MTTR의 response와 resolved를 섞어 측정하지 않는다. 운영 발견은 평가 사례 후보로 되돌리되 검증 규칙의 변경 승인은 사용자에게 둔다.

권한/복구 적용: gateway의 통합 인터페이스가 의미 호환성이나 권한 보장을 만들지는 않는다. 모델/도구별 차이·실패·fallback의 데이터 전송 경계와 허용 자원을 명시한다. fallback은 자동으로 다른 공급자에게 민감자료를 보낼 권한이 아니다. 재시도/병렬 후보 생성은 부작용 없는 생성과 실제 쓰기를 구분하고, 동일 작업 키·시도 수·취소·조회·보상으로 제어한다. 응답 반환과 쓰기 효과 확정은 별도 상태다. 그림 10-10에 쓰기 결과를 다시 대조하는 경로가 없으므로 이것만으로 완료 판정을 구현하지 않는다.

정보 경계: PII masking도 문맥 재식별·여러 값의 충돌·복원 map의 유출을 막아야 한다. map은 요청/사용자에 묶고 임의 모델 출력이 다른 secret을 복원하지 못하게 한다. 모델·검색·판정기가 외부 호출이면 각각 전송 경계다. routing과 PII 제거를 병렬로 실행하라는 조언은 router에 이미 원문이 전송될 수 있으므로 적용 조건을 따져야 한다. 로그는 비밀을 모두 저장하는 방식 대신 필요 증거·마스킹·접근·보존을 설계한다. 캐시 hit 경로도 현재 권한과 데이터/규칙 버전을 검증하며 그림처럼 검증을 우회하는 빠른 경로를 그대로 채택하지 않는다.

피드백 적용: 사용자의 명시적 오류 지적과 실제 작업 결과를 먼저 확인한다. 재생성·중단·공유·삭제·이름 변경·대화 길이만으로 성공/불만/선호를 확정하지 않는다. 수정된 코드도 자동 정답 label이 아니므로 검증한다. 모름/동률/둘 다 실패와 신호의 불확실성을 보존하고, 실제 노출·표본·UI 위치·비응답의 편향을 고려한다. 선호와 사실성을 분리하며 편향된 피드백을 자동 규칙 변경이나 무조건 재학습으로 연결하지 않는다. 필요한 맥락 수집과 외부 전송/학습 사용은 목적과 허용 범위에 맞춰야 한다.

원문 주의: gateway 예제는 저자도 비동작 예시라고 명시한다. import/들여쓰기/미지원 model_type/오류 경로가 빠져 있고 공급자 response 형태도 같은 것으로 취급하므로 운영 코드로 복사하지 않는다. 그림 10-3은 URL 오류 교정 예시이지 403 원인 확정 증거가 아니다. semantic cache에 전용 vector DB가 반드시 필요한 것은 아니다. 사용자별 cache도 올바른 key/TTL/권한 경계라면 가능하므로 일괄 금지하지 않는다. 표본 비율 감소가 곧 편향 증가라는 설명은 분산과 선택 편향을 구분해야 한다. 강한 refusal 감축이 정확성/권한 경계를 넘는 답변을 장려하지 않게 한다. 그림 10-18의 upscale과 본문의 unscaled 표기를 구분한다. 에필로그의 외부 참고 링크 전체는 이 책 읽기 범위에 포함하지 않았다.

여섯 권의 모든 본문 장을 읽고 코드·표·도식을 대조했다. DDIA 색인은 일부 탐색 확인이며, 표지·판권 등 출판 정보와 외부 참조 원문은 기술 적용 검토 범위에 포함하지 않는다. 연습문제와 제공 해설을 읽은 것과 모든 문제를 독립적으로 풀어 실행한 것은 구분한다.

원문 불일치는 이 판에서 직접 관찰한 내용과 자체 계산·반례다. 출판사 공인 정오표로 확정했다는 뜻은 아니다. 기술 선택은 [구현 기술 심화](구현-기술-심화.md), 적용 전제와 반례는 [정밀 검토](적용요소-정밀검토.md), 실제 실행 증거는 [실험 안내](experiments/README.md)를 따른다. 기존 승인 규칙은 변경하지 않았다.
