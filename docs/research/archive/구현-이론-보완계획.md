# 구현 이론과 기술 보완 계획

작성일: 2026-10-05 · 문서 버전: 0.1 · 상태: 검토 계획과 적용 가설

기존 개발 지침은 권한과 판정 조건을 다룬다. 이 문서는 문제 원인을 설명하고 해결책을 선택하는 데 필요한 설계·변경·검증 기술을 보완한다. 기존 수집 문서와 승인 규칙은 변경하지 않았다.

이번 확인 범위는 출판사와 O’Reilly의 공개 소개·목차다. 아래 순서와 산출물은 이 프로젝트에 대한 제안이며, 책의 본문에서 도출해 검증한 규칙이 아니다. 로그인 세션에서 전체 본문을 검토하거나 실제 프로젝트에 적용한 상태도 아니다.

## 우선 검토할 서적

### 1. Balancing Coupling in Software Design

Vlad Khononov. [O’Reilly 소개와 목차](https://www.oreilly.com/library/view/balancing-coupling-in/9780137353514/).

확인한 범위: 목차에 결합과 모듈성, 통합 강도, 거리, 변동성, 결합 균형과 재조정이 포함된다. 우선 7~11장을 검토하고 4~6장을 개념 보완에 사용한다.

보완할 질문: 함께 바뀌는 코드가 발견됐을 때 합칠지, 분리할지, 관계를 유지할지 어떻게 판단하는가?

작성할 지침: 관계별 의존 내용·변경 이유·전파 범위를 확인하고, 현상 유지·배치 변경·인터페이스 분리 대안의 비용을 비교한다. 결합을 무조건 제거하거나 서비스 수를 늘리는 방향으로 일반화하지 않는다. 기존 SEL-005의 조사 결과를 실제 설계 대안으로 연결하는 것이 목적이다.

### 2. Working Effectively with Legacy Code

Michael Feathers. [출판사 소개와 목차](https://www.informit.com/store/working-effectively-with-legacy-code-9780131177055), [O’Reilly 본문 진입점](https://www.oreilly.com/library/view/working-effectively-with/0131177052/ch16.html).

확인한 범위: 관찰과 분리, seam 모델, 무엇을 검사할지 모르는 상황, 코드 이해, 의존성 분리 기법을 다룬다. 우선 3·4·13·16장과 25장의 관련 기법을 검토한다.

보완할 질문: 기존 코드의 동작을 충분히 모르고 테스트도 약할 때 어디부터 바꿀 수 있는가?

작성할 지침: 현재 동작 관찰 → 변경 지점과 의존성 확인 → 검사 가능한 경계 확보 → 작은 변경 → 비교 검사로 이어지는 절차. 현재 동작을 기록하는 특성화 테스트와 바람직한 요구사항의 판정은 구분한다. 기존 버그를 기대값으로 영구 승인하지 않는다. 책의 오래된 도구 예시는 대상 언어와 도구에 맞게 재검증한다.

### 3. Effective Software Testing

Maurício Aniche. [출판사 소개](https://www.manning.com/books/effective-software-testing).

확인한 범위: 명세·경계·구조 기반 검사, 사전·사후 조건과 불변식, 속성 기반 검사, 테스트 가능한 설계, 단위·통합·시스템 검사 선택을 다룬다. 이 주제들을 우선 검토한다. 정확한 절 번호는 본문 확인 후 고정한다.

보완할 질문: 예시 몇 개를 통과하는 것 외에, 구현의 오류를 드러낼 검사를 어떻게 설계하는가?

작성할 지침: 입력 공간 분할과 경계 도출, 불변식 표현, 검사 계층 선택, 테스트 대역과 실제 연동 검사의 역할 구분. 승인된 요구사항에서 기대값이 나오는지 추적한다. 높은 커버리지나 에이전트가 만든 테스트 수를 정확성의 증거로 사용하지 않는다. Java 예제의 개념과 프로젝트 구현법을 구분한다.

### 4. Designing Data-Intensive Applications, 2nd Edition

Martin Kleppmann, Chris Riccomini. [O’Reilly 소개와 목차](https://www.oreilly.com/library/view/designing-data-intensive-applications/9781098119058/).

확인한 범위: 데이터 시스템의 설계 선택과 비용을 비교하는 책이며, 단일 노드와 분산 시스템의 선택도 다룬다. 트랜잭션·동시성·부분 실패·일관성 관련 본문을 우선 탐색한다. 1판의 장 번호를 2판에 그대로 적용하지 않는다.

보완할 질문: 동시에 실행되거나 응답이 유실되거나 재시도될 때 데이터의 의미를 어떻게 보존하는가?

작성할 지침: 업무 불변식과 원자적 처리 범위, 중복 요청 처리, 결과를 모르는 실패, 일관성 요구와 복구 가능성의 판단. 중복 생성·갱신 유실·처리 성공 후 응답 유실 사례를 작은 실험으로 검증한다. 이 책을 읽는다는 이유로 분산 구조를 도입하지 않는다. DB별 격리와 드라이버 동작은 공식 문서 및 실제 테스트로 보완한다.

### 5. Release It!, Second Edition

Michael T. Nygard. [출판사 소개와 목차](https://books.pragprog.com/titles/mnee2/release-it-second-edition/).

확인한 범위: 연동 지점과 연쇄 실패, 느린 응답 등의 실패 양상, 타임아웃·차단기·격벽·역압력 등 안정성 패턴을 다룬다. Stability Antipatterns와 Stability Patterns를 우선 검토한다.

보완할 질문: 외부 의존성이 느려지거나 멈췄을 때 제품의 다른 부분까지 무너지는 것을 어떻게 제한하는가?

작성할 지침: 실패 전파 경로와 자원 점유 확인, 시간·동시 실행·대기열 한도 선택, 장애 주입과 회복 확인. 기존 Continuous Delivery 검토가 배포 경로를 다뤘다면 여기서는 실행 중인 제품의 실패 대응을 보완한다. 수치와 패턴 채택은 부하·사용자 요구에 따라 정한다.

### 6. AI Engineering

Chip Huyen. [O’Reilly 평가 장과 전체 목차](https://www.oreilly.com/library/view/ai-engineering/9781098166298/ch04.html).

확인한 범위: 평가 방법과 시스템 평가, 에이전트 도구·계획·실패 양상·평가를 다룬다. 평가 관련 장과 Agents 부분을 우선 검토한다.

보완할 질문: 에이전트가 작업을 수행할 수 있다는 주장과 실제 신뢰 가능한 수행을 어떻게 구분하는가?

작성할 지침: 작업 성공 기준, 도구 호출과 결과 증거, 실패 사례 집합, 반복 실행의 편차, 비용과 지연을 포함한 평가. 이 책만으로 지속 실행 엔진의 체크포인트·취소·재개·격리가 완성된다고 보지 않는다. 실행 엔진 선정 후 공식 문서와 중단·재실행 실험으로 별도 확인한다.

## 지침으로 변환할 형식

책별 요약보다 문제별 해결 지침을 만든다. 다음 형식은 작성 제안이며 자동 실행 규칙이 아니다.

| 항목 | 남길 내용 |
|---|---|
| 문제 신호 | 어떤 코드·실패·변경 이력이 이 지침을 필요로 하는가 |
| 설명할 원리 | 왜 문제가 발생하는가. 출처와 검토한 절 |
| 확인할 사실 | 원인 가설을 지지하거나 반박할 코드와 실행 결과 |
| 대안과 조건 | 현상 유지도 포함한 선택지와 적용·비적용 조건 |
| 변경 절차 | 작은 순서, 중간 상태, 호환성과 복구 조건 |
| 검증 | 보존할 동작, 기대 개선, 실패·경계·동시성 사례 |
| 비용과 한계 | 추가 복잡도, 성능·운영 비용, 아직 모르는 사항 |
| 프로젝트 구현 | 실제 언어·라이브러리·DB·명령과 재현 결과 |

예를 들어 동시 변경이 발견됐다는 이유만으로 인터페이스를 추가하지 않는다. 함께 바뀌는 이유를 확인하고, 책임 이동·공통 모델·경계 유지 등의 선택지를 비교한 뒤 필요한 변경과 검사를 정한다. 이 예시는 향후 지침의 형식을 설명하며 특정 저장소에 대한 설계 결론이 아니다.

## 진행 순서와 남은 공백

첫 묶음은 설계 판단, 기존 코드 변경, 검증 설계다. Balancing Coupling과 Working Effectively with Legacy Code의 관련 부분을 읽고 Effective Software Testing으로 검증법을 연결한다. 산출물은 각각 관계 조정, 검사 가능한 변경 경계 확보, 검사 사례 도출 지침이다.

두 번째 묶음은 데이터 정확성과 부분 실패다. 데이터 상태를 바꾸는 실제 작업 하나를 골라 DDIA와 Release It!의 해당 부분을 연결한다. 세 번째는 에이전트 실행 자체의 평가와 복구다. 이 순서는 학습 우선순위이며 데이터·실패 처리가 필요한 작업을 검증 없이 먼저 구현한다는 뜻은 아니다.

이 여섯 권이 모든 구현 지식을 채우지는 않는다. 도메인 모델링, 보안·권한 격리, 스키마 변경, 구체적인 상태 머신 검증, 언어별 자원 관리와 동시성은 작업에 따라 추가 근거가 필요하다. 프레임워크와 도구를 선택하기 전에는 특정 실행법이나 수치 기준을 확정하지 않는다.
