# 개발 지침 통합과 LLM 에이전트에 적합한 특징

2026-10-10 · 적용 후보 · 기존 승인 규칙 유지

## 지금까지 정리한 개발 방향

제품 개발은 목적의 가설을 구체적인 요구와 검사로 연결하고, 작은 변경의 실제 효과에서 다시 배우는 과정이다. LLM 에이전트에 우선 맡길 후보는 승인된 목적과 경계 안에서 근거를 조사하고, 검증 가능한 작업을 만들고, 수정·검증·결과 대조를 반복하는 부분이다.

아래 적합성은 지금까지의 자료를 연결한 설계 판단이다. 특정 모델이나 도구가 실제 제품에서 해당 책임을 신뢰성 있게 수행한다는 실증 결과는 아니다.

| 축 | 정리한 내용 | 연결할 결과 |
|---|---|---|
| Mission과 학습 | 누구의 어떤 상황을 개선하려는지 가설로 세우고 실제 사용으로 갱신 | 기능 추가를 선택하거나 보류할 근거 |
| 요구사항과 계약 | 목적에서 범위를 정하고 대표·경계·실패 사례로 의미를 합의 | 요구사항–작업계획–검증계획 연결 |
| 자율 개발 | 관찰된 문제를 조사하고 영향·가치·위험을 비교해 작은 수정 | 문제 근거와 검증·복구 가능한 변경 |
| 구조와 변경 가능성 | 현재 방해 요인·반복 변경 부담에서 정리 필요를 찾음 | 동작 보존과 실제 변경 부담 개선의 별도 증거 |
| 검증 다양화 | 작업 속성에 맞는 검사와 서로 다른 증거를 조합 | 기능·계약·상태·동시성·성능·보안의 관련 결과 |
| 측정과 운영 | 지표별 사건·수집·계산·측정기 검증·판정 한계를 정의 | 측정 신뢰성과 제품 품질의 구분 |
| 전달과 회복 | 검증한 산출물, 대상 환경, 실제 효과와 복구 상태 연결 | 구현·배포·관측·회복을 구별한 완료 기록 |
| 규칙 진화 | 실제 누락·오탐·환경 변화에서 변경안을 만듦 | 구·신 기준의 차이와 BOSS 확인 |

Mission은 구현에 앞서 완성해야 할 영구 명세가 아니다. 제작자와 사용자가 실제 결과를 통해 다듬는 목적의 가설이다. 에이전트는 발견과 제안에 참여할 수 있지만, 관측한 사용량이나 기술 지표만으로 그 목적을 확정하지 않는다.

이 구분의 배경은 켄트 벡 영상에서 다룬 effort·output·outcome·mission과 features·futures 논의다. [영상](https://www.youtube.com/watch?v=B-tCy2bKSMc), [주최 측 원문](https://www.rise8.us/videos/kent-beck-software-engineering-in-the-age-of-ai). 여기에 붙인 에이전트 역할과 실행 조건은 자체 적용 제안이다.

## 적합성을 판단하는 조건

‘반복 가능한 일’만으로 LLM 적합성을 판단하지 않는다. 계산과 단순 반복만 필요한 작업은 일반 프로그램으로 처리할 수 있다. LLM은 문맥을 읽고 문제를 좁히거나 여러 대안을 구성하는 부분의 후보로 두고, 외부 결과를 확인할 수 있게 연결한다.

다음 조건이 갖춰질수록 자율 실행 범위를 구체화하기 쉽다.

- 입력과 대상이 식별되고 필요한 맥락에 접근할 수 있다.
- 기대 행동과 보존 조건의 근거가 있다.
- 제안의 옳고 그름을 실행·관측·독립 자료로 확인할 수 있다.
- 수정의 영향 범위를 제한하고 효과를 조회할 수 있다.
- 실패·결과 미확인·재개·종료를 구분할 수 있다.
- 권한·시간·비용·누적 변경의 한계가 정해져 있다.

판정 근거가 부족하면 조사와 대안 제안은 진행할 수 있어도, 자율 수정의 완료 판정까지 같은 권한으로 확대하지 않는다.

## 추출한 열 가지 특징

### 1 목적을 구체적인 작업 가설로 연결

**LLM이 맡을 부분:** 사용자 요구·관측·이슈를 연결해 ‘이 변경이 어떤 상황을 개선할 것인가’를 설명한다. 대안과 현상 유지도 비교한다.

**적합 조건:** 승인된 목적 또는 검토할 목적 가설, 실제 사용자 상황과 제약이 주어진다.

**결과:** 대상 사용자, 문제 근거, 예상 변화, 반증할 관찰. 단기 지표 개선만으로 목적 달성을 선언하지 않는다. 목적의 충돌과 새 가치 판단은 사용자와 논의할 항목으로 남긴다.

### 2 여러 자료에서 문제 후보를 찾고 좁히기

**LLM이 맡을 부분:** 코드·이력·실패 검사·운영 기록을 연결하고, 결함·반복 비용·오탐 후보를 구별한다. 점수나 경보에서 바로 수정으로 넘어가지 않는다.

**도구가 맡을 부분:** 검색, 변경 이력 집계, 자원·오류 측정과 원시 증거 수집.

**결과:** 위치·버전·관측 사실·원인 가설·추가 확인 방법. 증거가 약하면 조사 후보로 유지하고, 문제 없음이나 변경 불필요도 유효한 결과로 인정한다.

### 3 요구를 사례와 검증 계획으로 변환

**LLM이 맡을 부분:** 입력·초기 상태·출력·부수 효과를 정리하고, 경계·실패·중복·동시 실행에서 달라지는 행동을 찾아 검사 후보를 제안한다.

**적합 조건:** 기대값을 승인 명세·합의 사례·독립 모델에서 설명할 수 있다.

**결과:** 보호 조건 → 작업 → 검사 → 증거의 연결. 현재 구현을 기대값으로 복사하지 않는다. 미결정 요구는 미결정으로 남긴다.

### 4 재현을 만들고 원인 가설을 반증

**LLM이 맡을 부분:** 실패 경로를 좁히고 최소 재현·실험 순서를 만든다. 관측 결과에 따라 가설을 바꾼다.

**도구가 맡을 부분:** 실제 실행, 상태 조회, 스케줄·부하·실패 입력의 통제와 기록.

**결과:** 초기 상태·실행 조건·실패·재현 가능성·남은 불확실성. timeout과 확정 실패를 구별하고, 현재 상태를 조회할 수 없는 외부 효과를 임의로 재실행하지 않는다.

### 5 하나의 의도로 작은 변경을 수행

**LLM이 맡을 부분:** 확인된 원인에 필요한 패치와 관련 검사를 작성한다. 기존 코드 맥락과 언어 의미를 반영해 변경을 조정한다.

**적합 조건:** 수정 범위, 보존할 계약, 실패 시 처리와 실제 실행 환경이 정해져 있다.

**결과:** 변경 전 문제와 변경 후 해소 증거, 관련 회귀 결과. 적은 줄 수만으로 안전하다고 보지 않고, 부수적인 공통 플랫폼·추상화로 확대하지 않는다.

### 6 작업 속성에 따라 검증을 조합

**LLM이 맡을 부분:** 변경의 속성과 위험을 읽어 검사·교차 관찰·제외 범위를 선택하고 설명한다.

**대표 조합:** API 계약+실제 저장 효과, 상태 모델+실제 동시 실행, 부하 결과+자원 관측, 보안 발견+실제 권한 거부와 데이터 대조.

**결과:** 검사별 목적·판정 근거·대상·실행 결과·한계. 도구 수나 에이전트들의 동의를 독립 검증으로 간주하지 않는다. 같은 오류를 공유하는 기대값과 데이터 경로를 확인한다.

### 7 측정 결과를 해석하고 증거의 빈틈을 조사

**LLM이 맡을 부분:** 지표와 로그·이력을 연결해 원인 후보와 필요한 추가 관찰을 제안한다. 불균등 집계·재시도·표본 편향·누락 등 해석 문제를 검토한다.

**도구가 맡을 부분:** 건수·비율·분포·집합 차이·쿼리 실행·측정기 고정 사례 검증. 반복적인 정확 계산을 LLM의 설명에 의존하지 않는다.

**결과:** 측정 품질과 제품 판정을 별도 기록한다. `PASS / FAIL / UNKNOWN / NOT_RUN / NOT_APPLICABLE`을 구분하며, 누락된 관측이 있어도 확실한 위반은 보고한다.

### 8 실제 변경 부담에 근거해 구조를 정리

**LLM이 맡을 부분:** 반복 수정·불필요한 동시 변경·검사 불가 경계 같은 구체적 문제에서 책임 이동·계약 축소·현상 유지를 비교한다.

**적합 조건:** 정리의 보호 목적과 끝낼 조건, 동작 보존 검사, 실제 변경 수요가 있다.

**결과:** 정리가 해소한 방해 요인과 비용·영향 비교. 다음 변경의 여지는 구체적 변경 사례로 확인하고, 복잡도 점수·파일 수·미관을 목표로 삼지 않는다. 기능 사이의 점검은 승인 범위 내에서 자율 진행할 수 있으며 매번 사람을 호출하는 절차로 만들 필요는 없다.

### 9 결과와 결정을 남겨 중단 후에도 이어가기

**LLM이 맡을 부분:** 목적·가설·선택 이유·대상 버전·증거·미확인 항목을 압축해 다음 작업이나 역할에 전달한다.

**실행 시스템이 맡을 부분:** 영속 기록, 잠금·동시 실행 통제, 실행 권한, 시간·자원 한계, 취소·효과 조회. 문서에 적었다는 것만으로 구현된 통제가 아니다.

**결과:** 어디까지 실행됐으며 무엇을 다시 확인해야 하는지 복원 가능한 기록. 재개 때 실제 상태·버전·권한을 재확인한다. 기억 요약이나 낡은 통과 기록을 그대로 현재 증거로 쓰지 않는다.

### 10 운영 효과에서 다음 일감과 규칙 개정안을 도출

**LLM이 맡을 부분:** 수정 후 실제 효과·재발·사람 개입·지표와 결과의 불일치를 정리한다. 기존 규칙이 놓친 사례나 오탐을 재현해 개정안을 만든다.

**적합 조건:** 관측 기간과 대상 노출, 현재 규칙 버전, 비교 가능한 결과가 있다.

**결과:** 효과 확인 또는 추가 관찰, 다음 작은 일감, 구·신 규칙의 판정 차이. 지표를 개선하려고 분모·기대값·합격선을 바꾸지 않는다. 실제 목적·허용 행동·규칙의 변경은 BOSS 확인 대상이다.

## 자율 실행으로 바로 묶지 않을 부분

| 영역 | 에이전트가 기여할 부분 | 남겨야 할 판단 또는 조건 |
|---|---|---|
| Mission과 제품 방향 | 사용 근거 수집, 목적 가설, 상충 관계·대안 제시 | 누구의 어떤 변화가 가치 있는지 제작자·사용자가 확인 |
| 요구와 합격 기준 | 모호함·반례·판정 차이 제시 | 기대 행동·합격선·예외의 확정과 변경 |
| 통계와 형식적 보장 | 모델·검사 구성과 결과 해석 보조 | 가정의 타당성, 계산·모델 검사 도구, 구현 경계 대응 |
| 정확성·보안 판단 | 실제 경로 조사·실행·검증된 증거 연결 | 판정 근거와 미확인 범위. 문장 생성만으로 확정 불가 |
| 운영 배포와 복구 | 준비·동일 산출물 대조·효과 조회 | 승인된 대상·행동·데이터 손실 조건과 실제 복구 가능성 |

이 구분은 고정적으로 모든 판단을 사람에게 돌린다는 뜻이 아니다. 필요한 계약·관측·권한이 갖춰지면 자율 실행 범위를 넓힐 수 있다. 현재 수집 자료만으로 그 조건을 갖췄다고 추정하지 않는다.

## 스킬과 역할로 옮길 때의 최소 구성

추출한 특징을 먼저 하나의 작은 실제 작업에 적용한다. 반복 가능한 절차는 스킬, 지속적인 책임은 역할, 계산·실행·강제 통제는 도구 또는 실행 시스템으로 나누는 구성을 제안한다. 특징 하나마다 별도 에이전트를 만드는 것은 필요하지 않다.

우선 절차 후보는 작업 계약 작성, 문제 조사·재현, 작은 수정, 속성별 교차 검증, 효과 대조, 규칙 개정안이다. 구조 점검은 기능 사이와 실제 방해 요인이 있는 시점에 넣는다. 배포는 프로젝트별 권한과 검증 경로가 준비된 경우에만 포함한다.

실행 계약에는 목적 가설과 기대 효과, 승인 요구·규칙, 대상 버전, 작업 범위, 보존 조건, 검사 근거, 외부 효과, 실행 한계, 실제 증거, 다음 행동을 남긴다. 여러 역할을 써도 동일한 계약을 참조하고 실제 아티팩트·상태를 확인한다.

예시: ‘완료 표시가 있지만 산출물이 없는 작업’이 관측되었다면, 업무 효과를 확인하는 문제로 좁힌다. 기록과 효과 저장 경계를 재현하고, 관련 패치를 만든 뒤 응답 유실·재시도·실패 지점에서 결과를 확인한다. 실제 사용에서 재실행·수동 개입이 줄었는지 관측한다. 이 마지막 변화가 목적에 맞는지는 사용자와 확인한다. 자체 구현 예시이며 실행 결과는 아니다.

## 적합성을 실제로 확인할 평가 후보

| 사례 | 확인할 행동 |
|---|---|
| 근거 있는 결함 | 작은 재현·수정·회귀 검사·효과 확인까지 연결 |
| 점수만 나쁘고 실제 문제가 불명확 | 조사 후보로 두고 무의미한 변경을 만들지 않음 |
| 현재 동작과 승인 요구가 충돌 | 현재 동작을 정답으로 영구 승인하지 않음 |
| 검사 통과지만 실제 효과 없음 | 완료 주장과 상태를 대조하고 실패·미확인 보고 |
| 응답 유실과 이미 발생한 외부 효과 | 조회 없이 중복 실행하지 않음 |
| 계측 누락 또는 기준 미정 | 근거의 한계를 표시하고 임의 통과하지 않음 |
| 구조 정리가 범위를 확장 | 현재 목표로 돌아가거나 추가 후보를 분리 |
| 낡은 기록으로 재개 | 실제 버전·상태·권한을 재확인 |
| 지표 개선과 사용자 결과 악화 | 두 결과를 분리하고 목적·규칙 재검토 제안 |

동일한 초기 상태·사례·예산에서 실제 수행을 비교한다. 완료 문장 대신 결과와 제약 준수를 보고, 실패·미확인·재시도·비용을 모두 남긴다. 같은 모델이 만든 변경과 검사의 일치를 독립 증거로 삼지 않는다.

## 근거 문서와 적용 상태

- [개발 사이클](개발-사이클.md), [규칙 관리](규칙-관리.md), [규칙 목록](규칙-목록.md): 자율 적용, 기준 변경, 완료와 전달 경계.
- [서적 검토](서적-검토.md): 목적·사례·점진적 변경·일감 발견·정리·전달의 원칙.
- [구현 기술 심화](구현-기술-심화.md), [적용요소 정밀검토](적용요소-정밀검토.md): 구현 판단, 반례, 실제 효과와 에이전트 평가.
- [검증 도구 선택](검증-도구-선택-지침.md), [검증 서적 기록](검증-서적-선택검토.md): 작업 속성과 교차 검사.
- [SRE 운영 지표](SRE-운영-지표-검토.md), [지표 측정과 검증](지표-측정-검증-설계.md): 운영 피드백, 수집·계산·측정 검증과 판정.

기존 자료를 통합해 특징을 추출한 상태다. 기존 승인 규칙은 변경하지 않았다. 도구의 채택이나 스킬·에이전트 구성을 확정한 문서는 아니다. 책별 읽기 범위는 [검토 안내](검토-안내.md)와 원래 기록을 따른다.
