# 작업 속성에 따른 검증 도구 선택 지침

2026-10-05 · v0.1 · 승인 전 제안

## 목적과 권한

제품을 정교하게 만드는 검증은 도구의 개수가 아니라 서로 다른 오류를 발견하는 증거의 조합으로 설계한다. 각 작업에서 보호할 행동·데이터·실패 조건을 먼저 정하고, 이를 확인할 검사와 그 검사가 놓치는 부분을 교차 확인할 검사를 선택한다.

이 문서는 [검증 서적 선택 검토](검증-서적-선택검토.md)의 해석과 적용 제안이다. 책의 예시 수치, 검사 목록, 도구 이름은 승인된 제품 규칙이 아니다. 승인된 규칙의 적용은 에이전트가 수행하고, 요구사항·합격선·허용 행동·규칙의 변경은 BOSS 확인을 받는 기존 합의를 유지한다. 도구 설치나 운영 장애 실험 권한을 새로 부여하지 않는다.

## 1. 작업에서 먼저 뽑을 속성

다음 질문 중 실제 변경과 관련된 항목을 선택한다. 모든 작업에 모든 도구를 요구하지 않는다.

| 질문 | 검증으로 연결할 대상 |
|---|---|
| 어떤 입력에서 어떤 결과가 나와야 하는가? | 정상·경계·거부 조건, 판정의 출처 |
| 데이터가 생성·수정·삭제되는가? | 저장 결과, 소유권, 실패 후 잔여 효과 |
| 시간과 작업 순서에 따라 결과가 달라지는가? | 상태 전이, 재시도, 만료, 중복, 취소 |
| 여러 요청이 같은 상태를 바꾸는가? | 동시성, 원자성, 허용되는 실행 이력 |
| 다른 서비스·소비자·버전과 연결되는가? | 계약, 호환성, 실제 통합 경계 |
| 규모나 지속 시간에 따라 실패하는가? | 지연, 처리량, 자원 포화, 누수 |
| 권한·신뢰 경계·민감 데이터가 있는가? | 접근 거부, 격리, 공격 경로, 의존성 위험 |
| 배포·복구가 행동이나 데이터를 바꾸는가? | 동일 아티팩트, 마이그레이션, 실제 사용자 결과 |

속성을 붙일 때 근거를 적는다. ‘DB를 쓴다’만으로 분산 이력 검사를 요구하지 않고, ‘같은 키의 동시 갱신에서 업데이트 손실을 허용하지 않는다’처럼 보호할 조건을 적는다.

## 2. 선택과 교차 검증 표

다음은 선택 후보이며 필수 게이트 목록이 아니다. 합격선은 제품 계약과 승인된 규칙에서 가져온다. 출처 번호는 선택 검토 기록의 책 번호다.

| 작업 속성·실패 위험 | 주 검사와 도구 후보 | 다른 증거로 교차 확인 | 지표·관찰값 | 비용과 사각지대 | 출처 |
|---|---|---|---|---|---|
| 계산·분류·변환의 경계 오류 | 예제·경계 검사, 언어에 맞는 속성 기반 검사기 | 독립 계산·명세 예제·탐색 검사 | 조건별 통과/실패, 생성 입력 분포, 축소 반례 | 생성기와 판정기가 같은 오류를 공유할 수 있음 | 2, 3 |
| 검사 자체의 탐지력 부족 | 알려진 오류를 넣어 검사가 잡는지 확인; 필요 시 mutation 검사 | 실제 과거 결함과 경계 사례 재현 | 잡은 오류/유효하게 주입한 오류, 살아남은 변이 분류 | 변이 점수는 전체 제품 품질이 아님. mutation은 기존 검사 지침과 연결한 제안이며 이번 책 구간의 직접 추출이 아님 | 기존 검사 지침 |
| API 소비자·공급자 불일치 | Pact 같은 소비자 계약 검사 | 실제 서버·DB에서 핵심 사용자 흐름 | 소비자별·버전별 확인 결과, 미확인 조합 | 계약 예제가 다루지 않는 의미·권한·저장 효과를 놓침 | 1 |
| 상태 전이·재시도·중복 | PropEr 등 상태 기반 검사, 명령열·사후조건 | 실제 저장 이력, 장애 지점별 재실행 | 명령·전이 분포, 중복 효과, 실패 후 상태 | 모델 오류와 희귀 실행 순서가 사각지대 | 3, 5 |
| 동시성·원자성 | 병렬 상태 검사, 필요한 경우 TLC 설계 모델 | 실제 DB 동시 요청과 실패 주입; Erlang이면 Concuerror 검토 | 위반 이력, 스케줄/상태 탐색 범위, 재현 여부 | 유한 탐색·모델 가정·런타임 차이 | 3, 6 |
| 분산 데이터 보장 | 시스템 계약에 맞는 이력 검사; 필요 시 Jepsen 도입 검토 | 재시도·복구 후 비즈니스 불변식과 데이터 대조 | 손실·중복·금지된 이력, 미완료 작업 | 이력의 관측 불확실성과 검사기 모델 선택. 도입 비용 큼 | 5, 6 |
| 성능·장시간 안정성 | JMeter 등 부하 검사, 기준·증가·지속 부하 | RED와 USE, 발생기·대상 프로파일 | 성공 처리량, 오류 분류, 지연 분포, 큐·대기·자원 | 잘못된 부하·캐시·발생기 포화·측정 오버헤드 | 1, 4 |
| 보안·격리 | 신뢰 경계 시나리오, SAST·SCA·DAST | 실제 인증 정보로 허용/거부 요청과 데이터 효과 확인 | 검증된 발견, 적용 경로, 권한 조합별 결과 | 스캔 0건은 공격 경로·테넌트 격리의 증거가 아님 | 1 |
| 부분 장애·복구 | 정상 상태 가설과 한정된 장애 실험 | 비즈니스 결과·트레이스·복구 후 데이터 대조 | 실패 확산, 복구 시간, 잔여 큐, 데이터 손상 | 관측 누락과 장애 조합. 운영 실험은 별도 권한 필요 | 5 |
| 배포 후 실제 동작 | 승인된 배포 검증, 아티팩트·설정 확인, 핵심 흐름 관측 | 출시 전 결과와 실제 환경의 행동·성능·데이터 비교 | 기대 효과, 오류·지연 변화, 마이그레이션 상태 | 짧은 정상 관측은 장시간·희귀 오류를 보장하지 않음 | 1, 5 |

공식 도구 문서 링크는 [선택 검토 기록](검증-서적-선택검토.md)의 마지막 절에 있다. 특정 언어용 도구를 전체 제품의 기본 도구로 고정하지 않는다. 실제 채택 시 지원 버전·권한·실행 비용·결과 형식을 확인한다.

## 3. 교차 검증의 구성 원칙

각 검사에 ‘어떤 관찰이 틀리면 실패인가’를 적는다. 이름이 다른 도구가 같은 응답만 읽으면 독립된 증거가 늘지 않을 수 있다.

- HTTP 200 확인 + 실제 저장 내용 확인: 응답과 효과를 교차 확인한다.
- 소비자 계약 + 실제 통합 흐름: 요청 형식과 제품 행동을 교차 확인한다.
- 상태 모델 + 실제 병렬 실행: 설계 가정과 구현 경계를 교차 확인한다.
- 부하 지연 + 큐·자원·프로파일: 사용자 증상과 원인 후보를 교차 확인한다.
- 보안 스캔 + 실제 권한 거부와 데이터 대조: 패턴 탐지와 보호 행동을 교차 확인한다.

독립성에도 한계가 있다. 참조 모델과 구현을 같은 로직으로 작성하거나 두 도구가 같은 누락된 데이터만 보면 같은 오류를 놓친다. 그 경우 승인된 예제, 다른 관측 지점, 과거 반례를 추가한다.

## 4. 적용 예시

### API 계약과 저장 효과

작업: 주문 생성 API의 필드를 바꾼다. 승인된 소비자 요구 필드와 의미를 확인하고 계약 검사를 수행한다. 실제 API에서 생성된 주문의 소유자·가격·수량을 읽어 비교한다. 거부된 입력과 다른 사용자의 요청이 데이터를 만들거나 노출하지 않는지도 확인한다. 지원해야 할 구버전 소비자가 있다면 버전별 결과를 남긴다.

판정은 계약 통과와 저장 효과 통과를 따로 기록한다. 계약 통과만으로 주문 생성의 정확성이나 접근 제어를 선언하지 않는다.

### 상태·동시성·재시도

작업: 같은 자원에 동시 갱신과 재시도가 가능해진다. 명령과 상태를 정의하고 승인된 불변식으로 사후조건을 만든다. 반복 요청의 중복 효과와 실패한 요청의 잔여 효과를 검사한다. 병렬 실행 결과가 어떤 순서의 성공 실행으로 설명되어야 하는지 제품 계약에서 정한다.

복잡한 설계는 TLC로 반례를 찾을 수 있다. 모델의 원자적 단계가 실제 트랜잭션·락·외부 호출의 어디에 해당하는지 기록한다. 찾은 반례를 실제 DB에서 재현한다. 외부 호출을 포함한 모델의 한 단계가 실제로 분리된다면 모델을 수정하거나 해당 가정을 미확인으로 둔다. 모델 통과를 구현 통과로 재사용하지 않는다.

### 성능과 발생기 신뢰성

작업: 조회 API의 처리 성능을 개선한다. 같은 데이터 규모·설정·사용자 흐름에서 변경 전후를 비교한다. 예상 부하, 한계 탐색, 지속 부하 중 작업 위험에 맞는 것을 고른다. 성공 처리량과 지연 분포를 보면서 DB 대기·큐·CPU·메모리·I/O를 연결한다.

부하 발생기도 관측한다. 발생기가 느려져 요청을 덜 보내면 지연이 좋아 보일 수 있다. 응답을 기다린 뒤 다음 요청을 만드는 부하가 실제 도착률을 표현하는지 확인한다. [JMeter 공식 지침](https://jmeter.apache.org/usermanual/best-practices.html)이 지적하는 coordinated omission도 검토한다. 관측 도구의 비용과 캐시 상태를 기록하고, 바뀐 조건이 있으면 직접 성능 개선의 증거로 비교하지 않는다.

### 보안과 데이터 격리

작업: 인증된 사용자의 데이터 조회·수정 기능을 추가한다. 사용자·테넌트·자원 소유권·신뢰 경계에서 허용/거부 조합을 뽑는다. 정적 검사와 의존성 검사를 수행하고, 인증을 포함한 실제 요청으로 우회 경로를 검사한다. 동적 검사에는 해당 경로에 도달할 수 있는 설정과 계정을 사용한다.

거부 응답만 확인하지 않고 저장 상태와 다른 계정의 조회 결과를 확인한다. 알려진 취약 라이브러리 발견은 실제 영향 경로를 조사한다. 자동 결과의 오탐·미확인·검증된 발견을 분리한다. 데이터 격리 검사를 통과해도 모든 보안 속성을 검증했다는 결론으로 확대하지 않는다.

### 장애와 배포 후 검증

작업: 외부 서비스 실패 시 재시도와 복구를 추가한다. 정상 비즈니스 결과와 허용 가능한 실패 상태를 먼저 정한다. 타임아웃, 응답 유실, 부분 성공 등 실제 경계에서 한 가지씩 실패를 만든다. 재시도가 중복 데이터를 만들지 않는지, 큐가 회복되는지, 사용자 결과가 허용 조건을 만족하는지 관측한다.

실험에는 범위·중단 조건·복구 절차가 필요하다. 운영에서 할지는 기존 권한과 승인된 계획에 따른다. 배포 후에는 시험한 아티팩트와 실제 배포 아티팩트의 동일성, 설정·데이터 전환, 핵심 흐름을 확인한다. 단순 기동 성공과 실제 기능 성공을 별도 결과로 남긴다.

### 기대값이 불명확한 탐색

작업: 입력 종류가 많고 정답 전체를 미리 적기 어렵다. 대상·수단·찾으려는 위험을 짧은 탐색 헌장으로 정한다. 범위, 내부 일관성, 독립 예제, 적합한 표준이나 근사 특성에서 판정 근거를 찾는다. 자동화 가능한 반례는 재현 사례로 남긴다.

발견된 불편함·불일치는 관찰 사실로 적고, 기존 요구사항 위반과 새 제품 판단이 필요한 항목을 분리한다. 비교 제품과 다르다는 이유만으로 결함을 확정하지 않는다.

## 5. 지표 정의와 오해 방지

| 지표 | 함께 기록할 정의 | 잘못된 해석 |
|---|---|---|
| 조건별 검사 결과 | 대상 조건, 환경, 실제 실행/제외/미확인 | 검사 개수가 많으면 정확성이 높다 |
| 생성 입력·명령 분포 | 생성 범위·제약·seed·실행 횟수·시간 | 많이 반복하면 모든 경로를 확인했다 |
| mutation 또는 오류 주입 탐지율 | 유효한 대상 수, 탐지 수, 제외 이유, 미분류 | 높은 점수면 제품이 안전하다 |
| 계약 확인 범위 | 소비자·공급자·버전 조합과 미확인 조합 | 한 조합의 성공이면 모든 배포 조합이 호환된다 |
| 성공 처리량·오류율 | 작업 단위, 분모, 거부/실패/시간초과/불명 결과 | 모든 4xx는 장애, 모든 2xx는 성공 |
| 지연 분포 | 시작/끝, 단위, 측정 구간, 부하, 실패 포함 여부 | 평균이나 노드별 p99 평균이 전체 꼬리 지연이다 |
| 자원 사용·포화 | 실제 제한, 관측 간격, 큐·대기·오류 | 사용률 하나가 병목을 확정한다 |
| 상태·이력 위반 | 불변식, 허용 이력, 미완료 연산의 처리 | 관측되지 않은 결과는 실패하지 않았으니 성공이다 |
| 복구 시간 | 실패·회복의 정의, 관측 공백, 잔여 효과 | 프로세스 재기동이면 비즈니스가 복구됐다 |
| 출시 후 누락 결함 | 영향, 원인, 기존 검사에서 놓친 조건 | 신고가 적으면 품질이 높다 |

단일 종합 품질 점수로 합치지 않는다. 임계값은 목적과 비용에 따라 BOSS가 승인한 기준을 쓴다. 기준이 없으면 측정 결과와 제안 합격선을 분리해 제시한다.

## 6. 결과 상태와 충돌 처리

각 보호 조건마다 `PASS`, `FAIL`, `UNKNOWN`, `NOT_RUN`, `NOT_APPLICABLE`을 기록하는 형식을 제안한다. `NOT_APPLICABLE`에는 제외 근거가 필요하다. 실행되지 않았거나 관측이 불완전한 검사를 `PASS`로 바꾸지 않는다. 전체 판정 방식과 필수 조건은 승인된 규칙을 따른다.

검사 결과가 충돌하면 같은 코드·아티팩트·입력·환경·규칙 버전인지 먼저 확인한다. 다음으로 판정기의 가정, 대역과 실제 시스템의 차이, 관측 공백, 비결정성을 조사한다. 다수결로 통과시키지 않는다. 검사 오류가 밝혀져도 합격선이나 요구사항을 조용히 바꾸지 않고 기존 [규칙 관리](규칙-관리.md) 절차로 변경안을 제시한다.

## 7. 요구사항–작업계획–검증계획 연결 양식

아래는 채울 양식이며 실행 결과가 아니다.

```yaml
requirement:
  id: <approved requirement id>
  behavior: <input, expected effect, rejected conditions>
  failure_effect: <allowed state after failure or retry>
  rule_version: <approved version>
work:
  change: <small implementation scope>
  attributes: [<relevant attributes>]
verification:
  - property: <what must hold>
    oracle_source: <approved example, invariant, or contract>
    primary_check: <test and observation>
    cross_check: <different evidence and reason>
    environment: <runtime, data, artifact, versions>
    threshold_source: <approved rule or unresolved proposal>
    evidence: <command, result, trace, history, seed>
    result: NOT_RUN
    limits: <excluded scope and assumptions>
delivery:
  approved_scope: <existing authorization>
  checks: <artifact, migration, user effect, recovery>
```

역할 사이에는 작업 계획과 함께 보호 조건, 판정 근거, 검사 전제, 실행 대상, 결과, 남은 불확실성을 전달한다.


## 8. 에이전트 역할로 연결할 때

작업 속성 분석자는 승인된 요구사항에서 위험과 검증 후보를 뽑는다. 구현자는 계획에 맞춰 작은 변경과 재현 가능한 실행 대상을 만든다. 검증자는 구현 결과뿐 아니라 판정기의 근거·관측 범위·빠진 조건을 검토한다. 구조 정리는 같은 보호 조건을 유지하면서 별도 변경으로 검증한다.

새 결함이나 탐지 공백은 다음 작은 일감으로 제안할 수 있다. 합격선을 바꾸거나 새 요구사항을 만드는 일은 규칙 개정으로 분리한다. 이 역할 구분은 구현 후보이며 이번 작업에서 스킬이나 에이전트를 설치하지 않았다.

## 9. 실제 채택 전 남은 일

제품과 언어가 정해지면 위 표에서 필요한 행만 선택하고 구체 도구·실행 명령·비용을 확정한다. 알려진 정상 사례와 실패 사례로 검사와 판정기를 시험한다. 관측 가능한 범위, 제외 조건, 반복 가능성을 확인한 뒤 BOSS가 규칙과 합격선을 승인한다.

이번에 완료한 것은 서적 선택 검토와 검증 설계안이다. 실제 제품에서의 도구 실행, 성능 기준 확정, 배포 검증은 미실행이다. 기존 구현 지침은 [검토 안내](검토-안내.md)에서 확인한다.
