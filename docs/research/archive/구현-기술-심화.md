# 구현 기술 심화 검토

작성일: 2026-10-05 · 버전: 0.2 · 상태: 적용 제안, 규칙 채택 전

여섯 권 전체 본문·코드·표·도식을 검토한 적용 제안이다. 장별 근거와 원문 불일치는 [전체 읽기 기록](전체-읽기-기록.md)에 남겼다. 아래 본문 근거와 이를 연결한 자체 적용 제안을 구분한다. 1–7절은 기본 판단 절차이며 8–10절은 전체 읽기에서 보완한 구현 경계와 실행 계약이다. 교육용 반례 실험 외에 실제 제품 구현·배포는 수행하지 않았다.

기존 개발 사이클과 승인된 규칙은 그대로 유지한다. 이 문서의 절차·수치·예시는 새로운 강제 규칙이나 실행 권한을 부여하지 않는다. 기준의 의미나 합격 조건을 바꾸려면 기존 규칙 변경 절차를 따른다.

## 1. 결합: 무엇을 함께 바꾸고 무엇을 숨길 것인가

### 본문 근거

Balancing Coupling in Software Design의 [7장](https://learning.oreilly.com/library/view/balancing-coupling-in/9780137353514/ch07.xhtml)은 통합 강도를 내부 지식, 기능, 모델, 계약의 관점에서 구분한다. 직접 호출하지 않아도 같은 업무 규칙 때문에 동시에 바뀌는 관계가 있다. 내부 모델을 그대로 옮긴 DTO는 그 모델에 대한 지식을 숨기지 못한다.

[8장](https://learning.oreilly.com/library/view/balancing-coupling-in/9780137353514/ch08.xhtml)의 거리는 코드 위치뿐 아니라 변경 조정과 실행 시 관계에도 연결된다. 비동기 호출은 가용성 의존을 줄일 수 있지만 메시지 형식의 동시 변경 문제를 없애지는 않는다. [9장](https://learning.oreilly.com/library/view/balancing-coupling-in/9780137353514/ch09.xhtml)은 예상 변동성을 사업·문제·해결 방식의 변화와 연결한다.

[10장](https://learning.oreilly.com/library/view/balancing-coupling-in/9780137353514/ch10.xhtml)의 수치 모델은 정밀한 측정 공식이 아니다. [11장](https://learning.oreilly.com/library/view/balancing-coupling-in/9780137353514/ch11.xhtml)의 사례에서는 비동기 전달과 사전 조회만으로 경합이 해결되지 않으며, 관련 책임을 옮겨 경계를 조정한다. 변화가 적을 때 감수한 관계도 사업상 중요도와 변화 빈도가 달라지면 재검토한다.

### 적용 제안

문제 신호는 같은 요구 때문에 반복되는 여러 위치의 수정, 순차 배포 강제, 내부 데이터에 대한 외부의 의존이다. 파일 수나 import 수만으로 일감을 만들지 않는다.

| 선택지 | 적합한 조건 | 새로 생기는 비용·확인점 |
|---|---|---|
| 유지 | 실제 변경 부담이 작고 예상 변화 근거도 약함 | 관찰할 재검토 조건을 남김 |
| 관련 책임을 가까이 이동 | 같은 불변식·업무 규칙을 일관되게 변경해야 함 | 무관한 책임까지 합쳐 복잡도를 키우는지 확인 |
| 좁은 계약으로 분리 | 소비자가 필요한 지식이 내부 모델보다 작음 | 변환·버전 호환·오류 의미를 구현해야 함 |
| 비동기로 전환 | 즉시 완료가 필요 없고 지연을 허용함 | 전달 중복·순서·실패·중간 상태의 의미가 필요 |

작업 순서는 관계 하나 선택 → 공유 지식과 실제 동시 변경 이력 확인 → 두 대안 이상 비교 → 최소 책임 이동 또는 계약 축소 → 같은 요구를 변경 전후에 대입해 영향 범위 비교다. 계약을 바꾸는 경우 구·신 소비자가 공존하는 동안의 조합도 검사한다.

완료 증거는 수정 대상·계약·배포 경계의 비교와 동작 보존 검사다. 추상화나 서비스 수의 증가는 개선 증거가 아니다. 변동성 예측은 가설로 남기며, 낮은 변동성으로 기존 결함을 정당화하지 않는다.

## 2. 레거시 코드: 검사 가능한 최소 경계 확보

### 본문 근거

Working Effectively with Legacy Code [3장](https://learning.oreilly.com/library/view/working-effectively-with/0131177052/ch03.html)은 결과를 관찰할 수 없는 문제와 테스트 환경에서 실행할 수 없는 문제를 구분한다. 대역은 관찰 지점을 만들지만 실제 장치 연동까지 증명하지는 않는다. [4장](https://learning.oreilly.com/library/view/working-effectively-with/0131177052/ch04.html)의 seam은 해당 사용 지점을 편집하지 않고 다른 동작을 선택할 수 있는 경계이며, 선택이 일어나는 enabling point가 필요하다.

[25장](https://learning.oreilly.com/library/view/working-effectively-with/0131177052/ch25.html)의 24개 의존성 절단 기법을 모두 검토했다. 대표적으로 Parameterize Constructor와 Extract Interface는 필요한 의존성을 밖에서 전달하거나 문맥에 필요한 인터페이스를 추출해 검사 대역을 연결한다. 기존 생성 경로를 유지하는 방식도 가능하지만 호출자에게 노출되는 책임은 검토해야 한다. [13장](https://learning.oreilly.com/library/view/working-effectively-with/0131177052/ch13.html)의 특성화 테스트는 현재 동작의 기록이다. 요구사항상 올바름의 판정과 구분한다.

### 적용 제안

1. 바꿀 동작의 입력, 반환값, 저장·외부 호출 효과를 적는다. 관찰 불가인지 실행 불가인지 먼저 분류한다.
2. 가장 가까운 기존 seam을 찾는다. 없다면 생성자 인자나 좁은 어댑터 등 최소 변경으로 만든다. 전체 의존성 주입 체계를 도입할 필요는 없다.
3. 기존 생성 경로와 기본 동작을 보존한다. 테스트 경로만 실제 외부 효과를 대역으로 교체한다.
4. 변경 전 버전의 출력과 효과를 기록한다. 승인 요구와 다른 동작은 버그 후보로 분리한다.
5. 경계 확보, 동작 수정, 후속 정리를 구분해 작은 변경으로 진행한다. 단계마다 관련 검사를 실행한다.
6. 실제 어댑터·라이브러리 연결 검사를 별도로 수행해 대역과 현실의 차이를 확인한다.

예를 들어 시간에 의존하는 만료 판단은 시계 입력을 통제하면 경계 사례를 만들 수 있다. 하지만 그 검사로 실제 타이머 취소나 스케줄러 종료까지 증명되지는 않는다. 이 예시는 자체 적용 예시다.

컴파일 성공은 호출 형태의 일부 증거다. 예외·자원 소유권·부수 효과의 보존은 별도 검사한다. 테스트를 만들기 전 수행하는 의존성 분리는 그 자체가 위험하므로 변경 범위를 줄이고 외부 관찰 비교를 함께 남긴다. 25장 전체 기법의 전제와 주의점은 전체 읽기 기록의 표에 정리했다.

## 3. 검사: 기대값과 오류 탐지 능력을 설계

### 본문 근거

Effective Software Testing [2장](https://learning.oreilly.com/library/view/effective-software-testing/9781633439931/OEBPS/Text/02.htm)의 명세·분할·경계 도출에 더해, [3장](https://learning.oreilly.com/library/view/effective-software-testing/9781633439931/OEBPS/Text/03.htm)의 구조 검사 한계와 변이 검사 비용 관련 부분을 확인했다. 높은 경로 커버리지로 명세의 누락이 해소되지는 않는다.

[4장](https://learning.oreilly.com/library/view/effective-software-testing/9781633439931/OEBPS/Text/04.htm)은 사전·사후 조건, 객체 불변식, 계약 변경, 입력 검증과 내부 계약의 차이를 다룬다. 사전 조건을 강화하면 기존 호출자를 깨뜨릴 수 있다. [5장](https://learning.oreilly.com/library/view/effective-software-testing/9781633439931/OEBPS/Text/05.htm)의 속성 검사는 예시 검사를 보완하며 생성기 편향과 제약 설정이 중요하다. [6장](https://learning.oreilly.com/library/view/effective-software-testing/9781633439931/OEBPS/Text/06.htm)과 [9장](https://learning.oreilly.com/library/view/effective-software-testing/9781633439931/OEBPS/Text/09.htm)은 대역, 실제 라이브러리·DB 연결, 통합 검사와 데이터 준비를 보완한다.

### 적용 제안

| 확인하려는 오류 | 검사 선택 | 중요한 한계 |
|---|---|---|
| 요구의 경계·예외 누락 | 분할별 예시와 경계 양쪽 검사 | 기대값을 구현에서 복사하지 않음 |
| 입력·상태 조합의 넓은 범위 | 속성과 생성기, 필요한 경우 동작 순서 생성 | 편향된 생성기로 중요한 경우를 놓칠 수 있음 |
| 코드 분기 누락 | 명세 검사 뒤 구조 커버리지 확인 | 커버리지가 명세의 정확성을 보장하지 않음 |
| 잘못된 구현을 못 잡는 검사 | 중요한 로직에 제한한 변이 검사 | 동등 변이·실행 비용을 해석해야 함 |
| 판단 로직의 외부 의존 | 대역으로 결과·실패 입력 통제 | 대역 통과는 실제 연결 성공이 아님 |
| SQL·제약·직렬화·라이브러리 차이 | 실제 구성요소와 통합 검사 | 전용 시험 데이터와 격리가 필요 |

작업마다 먼저 `사전 조건 → 실행 → 사후 조건`, 그리고 공개 동작 전후에 유지할 불변식을 적는다. 입력 오류의 응답과 내부 오류의 처리를 구분한다. 실행 환경에서 비활성화될 수 있는 assert만으로 필수 입력 검증을 구현하지 않는다.

속성을 추가할 때는 요구사항상의 이유, 유효·무효 입력의 생성 범위, 관측할 상태를 적는다. 실패 입력과 재현 설정을 보관하는 것은 이 문서의 실행 제안이다. 생성 횟수만 늘리고 의미 있는 사례가 생성됐는지 보지 않는 방식을 피한다.

DB 검사는 해당 제품·버전·격리 설정을 반영한 전용 환경에서 준비·실행·검증·정리를 수행한다. 메모리 DB에서 통과한 결과를 실제 DB 보장으로 확대하지 않는다. 실제 테스트 프레임워크와 명령은 프로젝트 선정 후 결정한다.

## 4. 데이터: 동시 실행과 결과 미확인을 분리

### 본문 근거

Designing Data-Intensive Applications 2판 [8장](https://learning.oreilly.com/library/view/designing-data-intensive-applications/9781098119058/ch08.html)의 격리·갱신 유실·write skew·직렬화·분산 트랜잭션 부분을 포함해 전 장을 검토했다. 스냅샷을 일관되게 읽어도 여러 레코드의 업무 조건이 깨지는 write skew는 가능하다. 조건부 갱신은 성공 여부를 확인해야 한다. 직렬화 구현에는 잠금·대기 또는 충돌 중단과 재시도 비용이 있다.

2단계 커밋에서는 참여자가 준비를 약속한 뒤 조정자의 결정을 모르면 임의로 종료할 수 없는 상태가 생긴다. 이메일 같은 프로토콜 밖의 효과까지 자동으로 원자화되는 것은 아니다. 결과 응답 유실과 확정된 실패도 다르다.

### 적용 제안

변경 전 다음 네 가지를 한 장에 적는다: 보존할 업무 불변식, 읽고 쓰는 데이터, 함께 커밋해야 하는 범위, DB 밖의 효과.

| 문제 | 비교할 대안 | 확인할 증거 |
|---|---|---|
| 한 레코드 갱신 유실 | 원자 갱신·버전 조건 갱신·잠금 | 동일 초기 버전의 경쟁 요청 결과와 최종 값 |
| 여러 레코드의 조건 위반 | DB 제약·적절한 잠금·직렬화 | 둘 다 조건을 읽은 후 쓰는 실행 순서를 재현 |
| 성공 응답 유실 | 요청 식별과 결과 조회·재사용 | 재실행 후 저장·외부 효과가 중복되지 않음 |
| DB와 외부 효과의 부분 완료 | 처리 단계 기록과 조정·재처리 설계 | 각 중단 지점에서 실제 상태를 확인하고 회복 |

위 대안은 보편적인 처방이 아니다. DB의 격리 이름이 같아도 세부 동작은 다를 수 있으므로 제품 공식 문서와 재현 실험으로 선택한다. 상태 비교 후 별도로 쓰는 코드는 사이에 다른 쓰기가 가능한지 확인한다.

재시도는 실패 분류, 전체 기한, 횟수, 대기, 중복 방지 범위를 함께 정한다. 커밋 여부를 모르면 성공·실패 중 하나로 추정하지 않는다. 외부 효과의 중복 방지가 불가능한 경우 자동 재실행 가능 범위도 좁혀야 한다.

원자적 처리 범위를 줄일 수 있다면 우선 비교한다. 분산 트랜잭션이나 outbox를 기본 도입하지 않는다. outbox의 구체적 구현과 스키마 마이그레이션은 이번 검토로 확정하지 않았다.

## 5. 장애 대응: 대기·자원·회복을 함께 제한

### 본문 근거

Release It! 2판 [Timeouts](https://learning.oreilly.com/library/view/release-it-2nd/9781680504552/f_0048.xhtml), [Circuit Breaker](https://learning.oreilly.com/library/view/release-it-2nd/9781680504552/f_0049.xhtml), [Bulkheads](https://learning.oreilly.com/library/view/release-it-2nd/9781680504552/f_0050.xhtml), [Create Back Pressure](https://learning.oreilly.com/library/view/release-it-2nd/9781680504552/f_0058.xhtml)를 확인했다. 대기 종료, 반복 실패 시 호출 억제, 자원 분리, 생산 속도 제어는 서로 다른 문제를 다룬다. 유한 큐가 차면 거절·대기·폐기 등의 의미를 결정해야 한다.

[Adopting Your Own Monkey](https://learning.oreilly.com/library/view/release-it-2nd/9781680504552/f_0144.xhtml)는 정상 상태의 관측, 반증 가능한 가설, 영향 범위 제한과 회복 계획을 장애 실험의 전제로 둔다. 장애 제거만으로 정상 복귀가 보장되지는 않는다.

### 적용 제안

| 수단 | 적용 신호 | 검증할 핵심 |
|---|---|---|
| 타임아웃 | 호출·풀·잠금 대기가 끝나지 않음 | 실제 적용 범위, 자원 회수, 원격 처리가 계속되는 경우 |
| 차단기 | 실패한 의존성에 반복 호출이 누적됨 | open 상태의 빠른 실패, half-open 시험, 회복 후 재개 |
| 자원 분리 | 한 기능이 공용 풀을 소진함 | 해당 기능 포화 때 다른 기능의 유지 여부 |
| 역압력·유입 제한 | 유입이 처리량을 초과함 | 큐 길이·대기 시간 한도와 포화 시 응답 |

선택한 수단 하나부터 느린 응답·무응답·포화·회복을 검사한다. 사용자 응답 시간과 내부 전체 대기 예산을 연결하고, 여러 계층의 재시도가 증폭되는지 확인한다. fallback은 업무 의미가 달라지므로 승인된 요구 범위인지 확인한다. 데이터 폐기나 낡은 값 반환을 성공으로 숨기지 않는다.

장애 실험 기록에는 가설, 시험 환경, 주입 위치, 영향 범위, 정상 기준, 중단 기준, 복구 절차, 관측 결과를 둔다. 최초 적용은 격리된 시험 환경을 대상으로 한다. 실제 운영 환경 실험은 이번 문서 작성의 실행 범위에 포함되지 않는다.

공유 DB·호스트·연결 풀이 남아 있으면 코드상의 분리만으로 장애가 격리되지 않을 수 있다. 책의 예시 임계값이나 오래된 인프라 가정을 현재 제품에 그대로 복사하지 않는다.

## 6. 에이전트 평가: 완료 주장과 실제 결과 대조

### 본문 근거

AI Engineering [3장](https://learning.oreilly.com/library/view/ai-engineering/9781098166298/ch03.html)의 Functional Correctness와 AI 심사 한계, [4장](https://learning.oreilly.com/library/view/ai-engineering/9781098166298/ch04.html)의 평가 파이프라인, [6장](https://learning.oreilly.com/library/view/ai-engineering/9781098166298/ch06.html)의 Agent Failure Modes and Evaluation을 확인했다.

실제 작업 결과와 구성요소를 함께 평가해야 실패 위치를 찾을 수 있다. 대표 분포 외에 빈번한 실패와 범위 밖 사례를 나눠 볼 필요가 있다. AI 심사는 모델·프롬프트·설정에 따라 달라지고 일관된 오판도 가능하다. 계획·도구·인자·목표·완료 판단의 오류를 구분하며 비용과 지연도 평가한다.

### 적용 제안

평가 사례에는 초기 저장소 상태, 요청, 적용 규칙 버전, 허용 도구·대상, 기대 결과, 완료 판정법을 고정한다. 정상 작업, 애매한 요구, 도구 실패, 결과 미확인, 중단·재개를 별도 사례로 구성한다. 마지막 두 범주는 실행 엔진 검증을 위한 자체 확장 제안이다.

| 평가 대상 | 증거 | 판정 시 주의 |
|---|---|---|
| 목표 달성 | 실제 변경·실행 결과·대상 상태 | 완료 문장과 분리 |
| 제약 준수 | 적용 규칙과 행동 기록 | 성공률 평균으로 위반을 상쇄하지 않음 |
| 실패 원인 | 계획·인자·도구 결과·후속 판단 | 도구 장애와 판단 오류를 구분 |
| 반복 안정성 | 동일 조건의 반복 결과, 실패 유형 | 한 번 성공한 것으로 신뢰도를 확정하지 않음 |
| 효율 | 성공까지의 비용·시간·시도 수 | 반복 횟수가 다른 결과를 같은 점수로 비교하지 않음 |

실행 가능한 검사는 실제 실행 결과로 판정한다. 설명 품질처럼 정성 판단이 필요한 항목에는 예시가 있는 rubric을 쓰고 사람이 판정한 표본과 대조한다. AI 심사기는 보조 근거로 두며 모델·프롬프트·설정·평가 데이터 버전을 기록한다. 설정을 고정해도 완전한 재현성을 보장하지는 않는다.

평가 기준이 바뀌면 구·신 기준으로 같은 사례를 다시 평가해 제품 변화와 평가 변화의 효과를 구분한다. 합격선·허용 행동·기대 결과의 의미 변경은 사용자 확인 대상이다. 사례 추가도 합격 조건의 실질적 변경인지 먼저 구분한다.

도구·계획·메모리·평가·서빙을 포함한 전 장을 검토했다. 그러나 책 읽기는 durable checkpoint, 취소, 재개, 프로세스 격리의 제품 구현을 대신하지 않는다.

## 7. 실제 변경 한 건에 쓰는 기록 양식

아래는 여섯 권을 연결한 자체 작성 양식이다. 모든 변경에 모든 검사를 요구하지 않는다. 해당하지 않는 항목은 이유를 남긴다.

```text
작업 / 대상 버전:
문제 관측 / 원인 가설 / 반증할 증거:
승인 요구사항과 규칙 버전:
보존할 동작 / 업무 불변식:
관계와 상태 변경 범위 / 외부 효과:
대안 A / 대안 B / 현상 유지의 비용:
선택 이유 / 선택을 다시 볼 조건:
검사 가능한 경계 / 실제 연결로 확인할 부분:
작은 변경 순서 / 중간 상태의 호환성:
예시·경계·속성·동시성·실패 검사 중 필요한 것:
각 검사의 기대 결과 출처:
실제 명령 / 환경 / 결과 / 증거 위치:
중단·복구 방법 / 결과를 모를 때 처리:
확인된 결과 / 미검증 항목 / 남은 결정:
```

예를 들어 저장 요청의 중복 생성 문제라면, 경계를 늘리는 설계 논의보다 요청 식별·트랜잭션 경계·응답 유실을 먼저 확인한다. 재현 검사로 실패를 보인 뒤 최소 변경을 하고 같은 사례를 다시 실행한다. 에이전트 평가는 그 결과와 완료 보고가 일치하는지 검사한다. 이 예시는 실행한 사례가 아니다.

## 8. 전체 읽기에서 보완한 구현 판단

아래는 책의 내용을 연결한 자체 제안이다. 모든 프로젝트에 모두 적용하는 체크리스트가 아니다. 해당 변경이 실제로 지나가는 경계만 선택한다.

### 8.1 구조 변경과 실행 의미

근거: Balancing Coupling 1–6·12–14장, Legacy Code 5–12·14–25장. 상세 사례와 기법별 전제는 [전체 읽기 기록](전체-읽기-기록.md)에 있다.

공유 지식과 공유 생명주기를 따로 적는다. 폴더를 옮겨도 공동 배포가 남을 수 있고 서비스로 분리해도 동일 업무 규칙을 중복 구현할 수 있다. 변경 대상 관계와 양쪽 모듈의 책임을 함께 비교한다. 현재 불편이 없는 추상화를 미래 교체 가능성만으로 추가하지 않는다.

레거시 변경은 다음 중 실제 방해 요인에 맞춰 선택한다.

| 방해 요인 | 작은 시작점 | 반드시 보존할 것 |
|---|---|---|
| 생성 시 DB·네트워크 연결 | 의존성 인자화 또는 생성 경계 분리 | 기본 생성 경로·자원 소유권·해제 |
| 전역 상태·정적 호출 | 좁은 접근 경계 또는 인스턴스 위임 | 초기화 순서·동시성·기존 호출자의 의미 |
| 거대한 메서드 | 특성화 후 한 계산·효과 추출 | 실제 진입점의 호출 연결·예외·수치 변환 |
| 새 기능만 독립 시험 가능 | sprout 또는 wrap | 기존 동작과 결합되는 위치·실패 순서 |
| 변경 이해가 어려움 | 임시 탐색 리팩터링으로 가설 확인 | 탐색용 변경과 납품 변경 분리 |
| 빌드 대기가 병목 | 변경이 전파되는 의존 경계 조사 | 전체 빌드와 증분 빌드 모두의 결과 |

언어별 동적 디스패치, C++의 수명·virtual·링크 경계, Java의 예외·컬렉션 의미는 개념도만으로 보장되지 않는다. 컴파일러 검색은 리플렉션·설정·문자열 기반 호출을 놓칠 수 있다. 이동 전후 관측을 비교하고 타깃 런타임에서 확인한다.

### 8.2 검사의 판정 근거와 실제 경계

근거: Effective Software Testing 1–11장과 해설 부록, Legacy Code 13·16·21–25장.

명세에서 입력 분할·경계·실패 결과를 정한 뒤 구조 커버리지로 빠진 실행 경로를 찾는다. 기대값을 현재 구현에서 그대로 계산하면 같은 결함을 공유한다. 속성에는 추가 원소·순서·중복·상태 변화처럼 요구에 중요한 조건이 모두 포함되는지 반례를 만든다. 넓은 생성 범위보다 실제 생성된 분포와 실패 재현이 중요하다.

통합 검사는 커밋 뒤 다른 연결에서 보이는 상태, 제약 위반, 직렬화, 실제 라이브러리 오류를 대상으로 한다. 테스트 끝의 자동 rollback이 실제 commit 실패를 가릴 수 있다. UI 검사는 사용자 경로를 실제로 통과시키고 정리 단계에서 브라우저·프로세스·시험 데이터를 회수한다. 건너뛴 검사와 환경 오류는 통과로 집계하지 않는다. 성능·보안·접근성 등 별도 품질은 기능 테스트 성공에서 추론하지 않는다.

검사 추가의 기준은 수정 줄 수가 아니라 놓칠 경우의 손실과 실패 경계다. 의미 없는 구현 복제 테스트를 늘리거나 모든 변경에 변이 검사·대형 E2E를 강제하지 않는다.

### 8.3 데이터 모델부터 재생까지

근거: DDIA 2판 [3장](https://learning.oreilly.com/library/view/designing-data-intensive-applications/9781098119058/ch03.html)–[14장](https://learning.oreilly.com/library/view/designing-data-intensive-applications/9781098119058/ch14.html), Release It! 13장. 데이터 정확성은 트랜잭션 설정 하나로 끝나지 않는다.

| 변경 | 먼저 정할 계약 | 확인할 실행 경계 |
|---|---|---|
| 모델·인덱스 선택 | 조회 형태·갱신 비율·규모·불변식 | 실제 실행 계획·쓰기 증폭·hot key·복구 비용 |
| 스키마·메시지 형식 변경 | 구·신 reader/writer의 공존 조합 | 확장→전환→정리, 과거 메시지·rollback 버전 |
| backfill·파생 데이터 | 기준 snapshot·후속 변경 시작 위치 | 동시 쓰기 누락·중복·재시작·검산 |
| 복제·failover | 읽기 가시성·허용 손실·복구 목표 | 구리더 fencing·후보 데이터·클라이언트 전환 |
| 샤딩·이동 | 라우팅 버전·소유권·키 분포 | 구 mapping 요청·복사 중 쓰기·공간·과부하 |
| stream·CDC·재생 | 순서·중복 단위·시간·지연 데이터 | checkpoint와 효과의 커밋 경계·외부 효과 |
| 삭제·권한 취소 | 원본·파생·캐시·로그·백업의 처리 | 지연 복제·복원·재생 시 데이터 부활 |

동기 복제의 ACK가 수신·디스크 반영·적용 중 무엇을 뜻하는지 확인한다. 합의로 로그 순서를 정해도 업무 불변식과 외부 효과가 자동으로 보장되지는 않는다. lease가 만료된 실행자를 막아야 하면 대상 저장소가 fencing token을 실제로 거부하는지 검증한다. 시간 초과만으로 상대가 죽었다고 단정하지 않는다.

CDC와 outbox는 DB 밖 효과까지 원자화하지 않는다. 재생 가능한 계산과 결제·이메일 같은 비가역 효과를 분리한다. 재처리 ID의 보존 기간은 실제 replay·백업 복원·수동 재실행 범위와 맞춘다. 복제는 잘못된 삭제도 전파하므로 복구 가능한 백업과 다르다.

### 8.4 배포와 운영 중 제어

근거: Release It! 전체 1–17장, 특히 13장 데이터 전환·14–16장 운영·17장 장애 실험.

프로세스 생존, 트래픽 수용 준비, 의존성 상태를 구분한다. 종료 시 신규 작업을 막고 진행 중 작업을 drain하며, 기한 초과 작업의 효과를 조회할 수 있게 한다. 기동 성공만으로 배포 성공을 판정하지 않는다.

배포는 산출물 버전·설정·실행 주체·DB 버전·관측 기간을 연결한다. canary의 노출 범위와 중단 조건을 정하고 같은 부하에서 오류·지연·큐 나이·자원·업무 완료를 비교한다. 코드 rollback이 이미 쓴 데이터나 외부 효과를 되돌린다는 가정은 금지한다. 구 스키마·asset·flag 제거는 지연 작업과 복구 기간을 확인한 별도 변경이다.

자동 조정은 한 번의 변경량뿐 아니라 누적 변경량·동시 실행·관측 신선도·효과 지연을 제한한다. 연결 풀·공유 DB·인증 서버가 남아 있으면 논리적 모듈 분리만으로 장애 격리를 주장하지 않는다. timeout 뒤 원격 처리가 계속되는 경우 취소와 결과 조정을 따로 구현한다. 운영 장애 주입은 별도 권한과 실제 복구 준비가 필요한 실행 작업이다.

### 8.5 에이전트의 정보·권한·평가·자원

근거: AI Engineering [1장](https://learning.oreilly.com/library/view/ai-engineering/9781098166298/ch01.html)–[10장](https://learning.oreilly.com/library/view/ai-engineering/9781098166298/ch10.html).

검색은 관련 자료를 찾는 방법이다. 전체 검토 과업은 대상 목록과 실제 읽은 범위를 대조해야 하며 top-k 검색 성공을 전체 검토로 보고하지 않는다. 검색 결과·웹페이지·로그는 도구 권한이나 승인 규칙을 바꾸는 지시가 아니다. 도구 실행 권한은 모델 밖에서 대상·주체·행동별로 제한한다.

먼저 단순 프롬프트와 필요한 검색의 기준선을 측정한다. 자료가 없어서 틀리는 문제와 행동 형식을 학습하지 못하는 문제를 구분한 뒤 RAG·미세조정을 비교한다. 학습·합성 데이터와 평가 holdout의 출처를 분리한다. 같은 모델이 만든 코드와 테스트의 일치는 독립 증거가 아니다. 합성 데이터를 늘려도 다양성이나 정확성이 자동 증가하지 않는다.

모델·프롬프트·검색·도구·평가기·데이터 버전을 함께 기록한다. 평가에는 정상·경계·실패·복구·권한 위반·결과 미확인을 포함하고 집계 평균과 실패 종류를 함께 본다. 출력 형식 준수, 업무 정확성, 실행 권한, 효과 확정은 각각 판정한다. 자기 reflection과 AI 심사는 실행 효과 조회를 대체하지 않는다.

캐시는 현재 권한과 데이터·규칙 버전에 맞춰 조회한다. fallback 공급자는 전송 허용 범위를 별도로 확인한다. 로그의 관측 가능성을 위해 비밀을 무제한 보존하지 않는다. 최적화는 입력/출력 길이·동시성·cold/warm·실패/취소를 포함해 품질과 지연을 함께 만족한 처리량으로 평가한다. 모델 메모리의 단순 가중치 계산에는 KV cache·활성값·학습 상태가 빠진다는 점을 반영한다.

## 9. 자율 수정 한 건의 실행 계약 초안

아래는 아직 구현하지 않은 자체 설계다. 사용자 승인 규칙을 바꾸지 않으며 자동 배포 권한도 추가하지 않는다.

| 단계 | 남길 증거 | 다음 단계로 가지 않는 조건 |
|---|---|---|
| 후보 발견 | 실제 장애·변경 부담·실패 검사, 대상 버전 | 스타일 선호·근거 없는 점수만 있음 |
| 조사 | 재현·원인 가설·대안·현상 유지 비용 | 원인 불명은 조사 작업으로 유지 |
| 범위 고정 | 승인 요구·규칙 버전·허용 효과·완료 조건 | 요구 의미·권한·합격선 변경 필요 |
| 작은 변경 | 격리된 변경과 이전 상태·복구 방법 | 무관한 일반화·작업 범위 확대 |
| 검증 | 변경 전 실패와 변경 후 결과·회귀·실패 경로 | 누락·환경 오류·효과 미확인 |
| 허용된 배포 | 산출물·대상·혼합 버전·중단 조건 | 해당 배포 권한이나 복구 준비 없음 |
| 효과 확인 | 실제 대상 상태·관측 기간·남은 문제 | 완료 응답만 있고 효과 증거 없음 |
| 종료·재개 | 전체 대상 대조·증거 위치·재개 조건 | 일부 성공을 전체 완료로 보고할 수 없음 |

실행 상태는 `준비 → 실행 중 → 효과 확인 중 → 확인된 성공`을 구분한다. 응답 유실은 `결과 미확인`으로 남긴다. 조회로 성공이 확인되면 재실행하지 않고, 효과가 없다는 근거가 있을 때만 허용된 재시도를 한다. 조회도 불가능하면 임의 성공·실패로 닫지 않는다. 확정 실패와 취소 요청도 이미 발생한 효과를 없애지 않는다.

예시: 완료 표시는 있는데 결과 레코드가 없는 작업을 발견했다면, 관련 요청 하나의 기록·효과 저장 경계를 조사한다. 동일 DB라면 같은 커밋으로 묶는 대안과 결과를 조회해 조정하는 대안을 비교한다. 기록 전/후·효과 전/후·커밋 후 응답 전 중단을 검사한다. 외부 API가 포함되면 동일 DB 실험의 보장을 확대하지 않는다. 이 예시에서 실제로 실행한 부분은 [교육용 SQLite 실험](experiments/README.md)뿐이다.

## 10. 규칙의 진화와 적용 재검토

기존 규칙의 적용은 허용 범위에서 에이전트가 수행한다. 기준의 의미·합격선·허용 행동 변경은 BOSS 확인 대상이다. 반복된 거짓 경보, 통과했지만 발생한 실패, 검증 비용 증가, 환경·요구 변경을 발견하면 다음을 제안 자료로 남긴다.

- 현재 규칙 버전과 놓친 실제 사례, 기존 기준을 유지할 비용.
- 변경안과 반례, 구·신 기준으로 같은 사례를 평가한 차이.
- 새로 허용되거나 거부되는 행동과 기존 작업에 미치는 영향.
- 적용 범위·전환 방법·되돌릴 조건, 승인 여부.

검사 구현 결함을 발견해도 통과를 위해 기준을 몰래 완화하지 않는다. 기록·재현·수정 제안을 분리하고 승인 전에는 기존 승인 상태를 유지한다. 서적의 예시 숫자와 오래된 제품 사양은 합격선으로 복사하지 않는다. 실제 제품에서 언어·DB·라이브러리 버전을 고정하고 검증하는 단계는 독서 완료와 별개의 구현 작업이다.
