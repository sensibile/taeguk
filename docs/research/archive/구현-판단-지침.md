# 구현 판단 지침

작성일: 2026-10-05 · 문서 버전: 0.1 · 상태: 본문 선택 검토에 근거한 적용 제안

기존 운영 원칙에 더해, 무엇을 바꾸고 어떻게 검증할지 판단하는 기술을 정리한다. 2026-10-05 O’Reilly 로그인 세션에서 아래 본문을 확인했다. 여섯 권 전체나 지정된 장 전체의 정독을 뜻하지 않는다. 실제 저장소에서 구현·실험하지 않았으며 새로운 강제 규칙이나 실행 권한을 추가하지 않는다.

## 1. 결합 관계를 어떻게 바꿀지 판단

책에서 확인한 원리: 변경 전파 가능성은 공유하는 지식의 종류와 연관되며, 거리는 함께 변경하는 비용에, 변동성은 그 비용을 얼마나 자주 부담하는지에 영향을 준다. 강한 관계를 가까이 두는 것도 모듈성을 높일 수 있다. 수치 모델은 저자도 정확한 과학이 아니라고 명시한다. 근거는 위 10장이다.

적용 제안:

1. 평가 단위를 고정한다. 함수·모듈·서비스를 한 점수표에서 혼합하지 않는다.
2. 누가 누구의 내부 구조·업무 규칙·모델·공개 계약을 알고 있는지 코드와 호출 관계로 확인한다.
3. 같은 변경을 처리하기 위해 필요한 수정·검토·배포 경계를 기록한다.
4. 이력과 예정된 변경에서 변동성의 근거를 찾고 추측을 구분한다.
5. 현상 유지, 함께 변경하는 책임의 근접 배치, 공유 지식 축소를 비교한다. 각 대안이 다른 관계의 비용을 늘리는지도 확인한다.

변경 전후 같은 요구사항을 구현하는 데 영향을 받는 위치·계약·배포 단위와 검사 결과를 비교한다. import 수 감소나 파일 이동만으로 개선을 주장하지 않는다. 낮은 변동성은 변경 비용의 판단 근거일 뿐 보안·기능 결함의 면제가 아니다. 거래의 원자성을 깨면서 서비스 경계를 늘리는 선택은 별도의 데이터 정확성 검토가 필요하다.

## 2. 이해가 부족한 기존 코드 변경

책에서 확인한 원리: 특성화 테스트는 현재 동작의 기록이며 올바름의 최종 기준이 아니다. 의심스러운 동작은 표시하고 영향 확인이 필요하다. 코드 이해에는 메모·그림·변경 효과의 추적이 도움이 되며, 이해를 위한 실험적 리팩터링은 실제 반영할 변경과 구분한다. 근거는 13·16장이다.

적용 제안:

1. 변경할 입력·결과·부수 효과와 그 영향 경로를 적는다.
2. 변경 전 버전에서 현재 동작을 관찰해 테스트로 남긴다. 기대값의 출처를 `현재 동작 관찰`과 `승인된 요구사항`으로 구분한다.
3. 둘이 충돌하면 버그 후보로 기록한다. 구조 정리와 동작 수정의 목표를 혼합하지 않는다.
4. 변경으로 깨뜨릴 수 있는 부분을 기존 검사가 감지하는지 확인한다. 감지 근거가 약하면 범위를 줄이거나 검사 경계를 먼저 확보한다.
5. 이해를 위한 실험은 격리된 사본에서 수행하고, 실험 결과를 검증된 제품 변경으로 바로 승격하지 않는다.

주의할 구분: 변경 전 동작을 처음 관찰해 기록하는 것과, 변경 후 실패한 검사의 기대값을 실제 출력에 맞춰 바꾸는 것은 다르다. 후자는 승인 기준을 약화시키는 행위일 수 있다. 미사용 코드는 정적 참조 검색만으로 판단하지 않고 동적 호출·설정·외부 진입점을 확인한다. 이 절은 아직 구체적인 seam 적용법을 제공하지 않는다.

## 3. 요구사항에서 검사 사례 도출

책에서 확인한 원리: 요구사항에서 입력·출력을 이해하고 행동이 달라지는 분할과 경계를 찾는다. 모든 조합을 기계적으로 늘리지 않으며 명세 기반 검사와 코드 구조 기반 검사를 반복적으로 보완한다. 근거는 Effective Software Testing 2장 선택 부분이다.

적용 제안:

1. 검사할 업무 규칙과 기대 결과의 출처를 적는다.
2. 입력뿐 아니라 초기 상태와 입력 간 관계에 따라 결과가 달라지는 경우를 나눈다.
3. 분할마다 대표 사례를 만들고, 경계의 양쪽과 동등 조건을 확인한다.
4. 함께 작용하는 입력을 골라 조합 검사한다. 제외한 조합의 이유를 남긴다.
5. 사례마다 출력 외에 저장 상태·중복 효과·외부 호출 등 관련 결과를 검증한다.
6. 구현을 읽어 빠진 경로를 보완하되 구현 자체를 기대값의 유일한 근거로 삼지 않는다.

직접 만든 예시: 정수 길이 n이 1 이상 100 이하라는 승인 조건이 있다면 0·1·100·101을 경계 후보로 삼는다. 문자열 길이라면 바이트·코드 포인트·사용자 인식 문자 중 무엇인지 먼저 정해야 한다. 이 예시는 책의 예제가 아니며 실제 제품 기준도 아니다.

사례 수나 커버리지 증가만으로 검사 품질을 판정하지 않는다. 속성 기반 검사와 변이 테스트의 구체적 실행법은 이번 본문 검토로 완성하지 않았다.

## 4. 데이터 변경과 재시도의 안전성

책에서 확인한 원리: 트랜잭션의 원자성과 동시 실행의 격리는 다르다. 업무 불변식은 선언된 제약과 애플리케이션의 올바른 사용에 의존한다. 커밋 응답이 유실되면 클라이언트가 실패로 보아도 처리는 완료됐을 수 있다. DB 밖의 효과는 DB 롤백으로 되돌아가지 않으며, 과부하에서 재시도는 상황을 악화시킬 수 있다. 근거는 DDIA 2판 8장 선택 부분이다.

적용 제안:

- 먼저 유지할 업무 불변식, 함께 성공·실패해야 할 쓰기, 트랜잭션 밖의 효과를 적는다.
- DB 제품·버전·실제 격리 설정과 제약을 확인한다. ACID라는 이름만으로 원하는 보장을 가정하지 않는다.
- 실패를 확정된 중단, 결과 미확인, 영구 오류, 일시 오류로 나눈다. 결과 미확인에는 상태 조회·중복 방지 등의 설계가 먼저 필요하다.
- 재시도 대상·한도·대기·중복 요청 식별과 결과 재사용 조건을 정한다. 식별자만 추가했다고 중복 방지가 증명되지는 않는다.
- 중간 실패, 동시 갱신, 처리 성공 후 응답 유실, 동일 요청 재실행을 재현해 불변식과 외부 효과 횟수를 확인한다.

어떤 격리 수준이나 분산 처리 패턴을 기본값으로 채택할지는 미정이다. 외부 효과와 DB 쓰기의 일관성을 보장하는 구체적 설계는 추가 본문 및 제품 공식 문서 검토가 필요하다.

## 5. 대기와 장애 전파 제한

책에서 확인한 원리: 원격 호출뿐 아니라 자원 풀 대기도 멈출 수 있다. 타임아웃은 기다림을 제한하며, 즉각적인 반복 재시도는 대기와 자원 점유를 늘릴 수 있다. 패턴의 적용 개수는 품질 지표가 아니다. 근거는 Release It! 5장 도입과 Timeouts 절이다.

적용 제안:

1. 한 요청에서 기다리는 호출·연결 풀·잠금·작업 대기열을 식별한다.
2. 사용자 응답 시간과 내부 대기의 한도를 연결하고, 실제 라이브러리의 타임아웃 적용 범위를 확인한다.
3. 시간 초과 시 어떤 결과를 보고하고 어떤 자원을 해제하는지 정한다. 기다림 종료와 원격 작업 취소를 같다고 보지 않는다.
4. 느린 응답·무응답·자원 고갈을 격리된 시험 환경에서 만들고 종료 시간·자원 회수·회복 후 동작을 확인한다.
5. 지연 재시도를 채택한다면 4절의 중복 효과 검증을 함께 적용한다.

책의 지연 시간 예시를 공통 임계값으로 복사하지 않는다. 큐를 넣는 것은 작업 유실·중복·보관 한도·재개라는 새 설계 문제를 만든다. 차단기와 역압력의 상세 적용법은 다음 검토 범위다.

## 6. 에이전트 실행 결과 평가

책에서 확인한 원리: 실패에는 잘못된 계획·도구·인자, 목표나 제약 미충족, 잘못된 완료 판단, 도구 자체의 오류가 있다. 성공 여부 외에 단계 수·비용·소요 시간도 비교할 수 있다. 근거는 AI Engineering 6장의 해당 절이다.

적용 제안:

1. 대표 작업과 사용 가능한 도구, 목표, 제약, 실제 완료 판정법으로 평가 사례를 만든다.
2. 도구명·인자 형식의 적합성과 값·대상 선택의 정확성을 별도로 본다.
3. 계획이 유효한지, 실행이 성공했는지, 실제 목표가 충족됐는지를 나눠 기록한다.
4. 동일 조건의 반복 평가에서 실패 유형과 빈도, 성공까지의 시간·비용을 남긴다. 반복 횟수는 아직 정하지 않는다.
5. 도구 자체의 실패와 에이전트 판단 실패를 구분한다. 실행 로그에는 진단에 필요한 정보만 남기고 비밀값은 제거한다.

작업 완료 주장은 실제 파일·테스트·대상 시스템의 결과로 확인한다. 다른 에이전트의 동의만으로 독립 검증이 되지는 않는다. 지속 실행의 중단·재개·체크포인트·격리는 이 절의 평가 관점만으로 해결되지 않으며, 실행 엔진을 정한 뒤 별도로 검증한다.

## 다음 심화와 적용

이번 결과는 여섯 영역의 첫 본문 검토다. 먼저 결합도 7~9장과 레거시 코드의 seam·의존성 분리 기법을 확인해 실제 변경 방법을 보완한다. 이어서 테스트의 구조·속성·통합 검증을 연결한다. 데이터와 장애 대응은 실제 작업의 요구가 있으면 앞당긴다.

작은 실제 작업에서는 적용되는 절만 사용해 문제 근거, 대안, 선택 이유, 변경 전후 검증을 남긴다. 아직 읽지 않은 부분을 완료로 표시하거나 이 초안을 자동 배포 조건으로 사용하지 않는다.
