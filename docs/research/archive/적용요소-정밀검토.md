# 구현 지침에 반영할 요소의 정밀 검토

작성일 2026-10-05 · 상태 적용 후보 · 승인 규칙 변경 없음

여섯 권 전체 본문·코드·표·도식을 읽고, 실제 적용 전에 확인할 반례와 증거를 정리했다. 결론은 **원칙을 더 추가하기보다 각 원칙이 잘못 적용되는 조건을 검사할 수 있어야 한다**는 것이다. Python 반례 실험 네 가지와 Java 언어 의미의 최소 재현 한 가지를 실행했다. 전체 독서 검토는 완료했지만 제품 적용을 완료했다는 뜻은 아니다.

이번 결과에서 우선 가치가 높은 것은 변경 수요를 반영한 일감 선정, 이동·추출 경로의 보존 검사, 검사 자체에 대한 반례, 데이터 효과와 완료 기록의 원자성, 에이전트 평가 조건의 고정이다. 모든 기법을 공통 의무로 만들지는 않는다.

## 검토 범위와 근거

여섯 권의 모든 본문 장과 코드·표·그림을 확인했다. 책별 부속 자료와 제외 범위는 [전체 읽기 기록](전체-읽기-기록.md)의 범위 표를 따른다. 아래는 적용 가치와 반례를 선별한 문서이며 장별 요약을 중복하지 않는다. 전체 검토를 반영한 구현 선택과 실행 계약은 [구현 기술 심화](구현-기술-심화.md) 8–10절에 있다. 모든 예제 실행이나 실제 제품 배포까지 검증한 것은 아니다.

## 설계와 일감 선정

### 변경 횟수만으로 우선순위를 결정하지 않기

**본문 근거.** Balancing Coupling [9장](https://learning.oreilly.com/library/view/balancing-coupling-in/9780137353514/ch09.xhtml)은 코드 변경 횟수의 오판 가능성을 다룬다. 사업상 필요한 변경이 어려워 포기된 모듈은 이력상 안정적으로 보일 수 있다. 자체 요구가 안정적이어도 변동이 큰 상위 모듈에 강하게 의존하면 함께 바뀐다.

**적용 후보.** 에이전트가 구조 개선 일감을 만들 때 `관측된 변경`, `지연·포기된 변경`, `상위 변경에서 전파된 수정`을 분리한다. 변경 요청이나 장애 근거를 찾을 수 없으면 구조 문제를 확정하지 않고 조사 후보로 남긴다.

**반례.** 커밋이 적다는 이유로 변경 비용이 큰 오래된 모듈을 제외하는 판단. 반대로 포맷 변경 커밋이 많다는 이유로 핵심 변경 지점으로 선정하는 판단.

**필요한 증거.** 대표 변경 하나의 요구·이슈·수정 경로, 현재 또는 예정된 변경 수요, 이력 해석의 불확실성. 향후 변경을 자동 예측했다는 점수는 증거가 아니다.

### 강한 관계를 가까이 두되 무관한 책임은 합치지 않기

**본문 근거.** [10장](https://learning.oreilly.com/library/view/balancing-coupling-in/9780137353514/ch10.xhtml)은 관계별 유지 비용만 낮춰도 그 관계를 담는 모듈의 복잡도는 커질 수 있다고 설명한다. [11장](https://learning.oreilly.com/library/view/balancing-coupling-in/9780137353514/ch11.xhtml)의 일시정지 사례는 사전 조회나 서비스 전체 병합의 한계를 비교하고 관련 기능만 이동한다.

**적용 후보.** 이동 전후에 대상 관계뿐 아니라 양쪽 모듈의 책임과 주변 의존성도 비교한다. “같은 프로세스에 있으니 원자적”이라는 추론은 하지 않는다. 같은 DB 또는 모듈에 배치한 뒤에도 트랜잭션·잠금 등 실제 동시성 보장을 별도로 확인해야 한다. 후자는 데이터 검토와 연결한 자체 판단이다.

**검사 예시.** 사용자가 일시정지를 확정한 뒤 새 배정이 생기지 않아야 한다면, 정지와 배정이 겹치는 실행 순서를 만든다. 승인 요구가 단지 일정 시간 내 반영이라면 이 검사는 달라진다. 즉시성의 의미를 에이전트가 임의로 강화하지 않는다.

**보류할 일반화.** 결합 점수 미달 자동 리팩터링, 비동기 전환을 자동 개선으로 분류, 중복 코드의 일괄 공통화. [7장](https://learning.oreilly.com/library/view/balancing-coupling-in/9780137353514/ch07.xhtml)의 핵심은 코드 모양보다 공유하는 지식과 함께 바뀌어야 하는 이유다.

## 기존 코드 변경과 검사 품질

### 현재 동작 보존과 바람직한 동작 판정을 분리하기

**본문 근거.** Legacy Code [13장](https://learning.oreilly.com/library/view/working-effectively-with/0131177052/ch13.html)은 현재 행동을 특성화한 뒤, 실제 이동·추출 대상이 검사에 연결돼 있는지 확인한다. 단순한 경로 실행 외에 변환이 손실을 드러내는 입력도 필요하다. 현재 행동 기록에는 요구사항을 승인하는 권한이 없다.

**적용 후보.** 특성화 사례에 `관찰한 원본 버전`, `관찰한 결과`, `의심스러운 동작`, `승인 요구와의 관계`를 남긴다. 리팩터링 검사에는 추출 함수의 단독 결과와 기존 진입점에서의 연결 결과를 구분한다. 대역 사용 시 무엇을 관찰할 수 있는지는 [3장](https://learning.oreilly.com/library/view/working-effectively-with/0131177052/ch03.html)의 범위에 맞춰 적는다.

**직접 확인한 반례.** 정수로 잘라 반환하는 잘못된 추출 함수는 입력 12.0에서 기대값과 같지만 12.5에서 달라진다. 이번 Python 실험은 이 원리를 보인 것이며 책의 Java 코드를 컴파일한 결과는 아니다.

**필요한 증거.** 이동한 코드가 호출되지 않거나, 다른 인자로 호출되거나, 변환에서 정보가 사라지는 잘못된 변형을 관련 검사가 탐지하는지 확인한다. 모든 코드에 변이 테스트 도구를 도입한다는 뜻은 아니다.

### 검사 속성 자체의 누락을 확인하기

**본문 근거.** Effective Software Testing [5장](https://learning.oreilly.com/library/view/effective-software-testing/9781633439931/OEBPS/Text/05.htm)은 요구를 속성으로 표현하고 생성기로 반례를 찾는 과정을 다룬다. 입력 분포와 경계가 잘못되면 중요한 경우를 충분히 검사하지 못한다. 상태를 유지하는 예제는 동작 순서를 생성하지만, 저자는 간단한 해당 문제에는 예시 검사를 선택할 수도 있다고 설명한다.

**검토에서 발견한 한계.** 5.2의 unique 예제에 보이는 세 주장, 즉 입력 원소 포함·중복 없음·내림차순만으로는 출력에 불필요한 값이 추가되는 오류를 배제하지 못한다. 이는 책의 기법에 대한 반박이 아니라 표시된 검사 조건의 누락이다. 같은 장 5.4의 `unmodifiableSet`을 복사라고 설명한 주석도 그대로 채택할 수 없다. Java API는 원본을 읽는 수정 불가 뷰라고 명시한다. [Oracle API 근거](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/util/Collections.html#unmodifiableSet(java.util.Set))

**적용 후보.** “이 속성을 만족하지만 요구에는 틀린 결과”를 먼저 하나 만들어 본다. 집합 결과라면 포함뿐 아니라 추가 원소 배제도 확인한다. 상태 검사는 구현의 현재 상태를 기대값의 유일한 근거로 쓰지 않고, 필요하면 독립적인 작은 기준 모델을 둔다. 조회 API도 읽기 전용 뷰인지, 시점 사본인지, 내부 변경을 반영하는지 구분한다.

**실험 결과.** 길이 0~4, 값 0~2인 121개 입력에 불필요한 99를 붙인 출력은 약한 세 조건을 모두 통과했다. 입력·출력의 원소 집합이 같아야 한다는 조건을 더하면 121개 모두 거부된다. AssertJ·jqwik 자체 실행 결과가 아니라 조건의 논리적 누락을 확인한 독립 Python 실험이다.

**적용 한계.** 121개 통과가 일반적 정확성 증명은 아니다. 생성 횟수나 시드 고정만으로 입력 공간을 충분히 다뤘다고 판단하지 않는다. 실패 입력·시드·라이브러리 버전과 실제 생성 분포를 함께 기록하는 것이 적용 후보다.

## 데이터 변경과 재실행

### 조건 확인과 쓰기를 하나의 경쟁 문제로 보기

**본문 근거.** DDIA 2판 [8장](https://learning.oreilly.com/library/view/designing-data-intensive-applications/9781098119058/ch08.html)의 write skew 설명은 다른 레코드를 갱신해도 공동 불변식이 깨질 수 있음을 보인다. 존재하지 않는 행을 찾은 결과에 행 잠금만 기대는 방법은 보장을 충분히 설명하지 못한다. 같은 장의 메시지 재처리 절은 처리 ID와 데이터 효과를 한 트랜잭션에 기록한다.

**적용 후보.** 일감 조사 시 `조회 결과로 허용 판단 → 쓰기` 형태를 발견하면, 조회한 조건을 다른 실행이 언제 바꿀 수 있는지 적는다. 행 하나의 중복 갱신인지, 여러 행의 조건인지, 행 부재의 조건인지 구분한다. 조건에 맞는 제약·원자 연산·잠금·격리 수준을 비교한 뒤 DB별로 검증한다.

**실험 결과.** 두 작업의 읽기·쓰기 순서를 보존하는 추상 실행 순서 6개를 나열했다. 그중 4개에서 “최소 한 작업자는 활성 상태”라는 불변식이 깨졌다. 이 수치는 실제 운영 실패 확률이 아니며 특정 DB의 격리 실험도 아니다.

**반례.** “트랜잭션을 썼다”, “같은 서비스를 호출한다”, “조회에 잠금을 붙였다”만으로 동시성 문제를 해결했다고 보고하는 것. 최종 상태와 경쟁한 요청들의 결과를 함께 봐야 한다.

### 완료 기록과 데이터 효과의 원자성을 검증하기

**적용 후보.** 중복 처리 방지의 단위는 요청 ID뿐 아니라 그 ID가 보호하는 효과다. 한 DB 안의 작업이라면 완료 기록과 효과를 같은 커밋 범위에 둘 수 있는지 확인한다. 실패 후에는 해당 범위가 실제로 완료됐는지 조회해 재실행 여부를 판단한다.

**실험 결과.** 임시 SQLite DB에서 자식 프로세스를 네 지점에 강제 종료했다. 처리 기록 전, 기록 후, 효과 적용 후의 커밋 이전 종료는 재조회 시 기록과 효과가 모두 없었다. 커밋 후 종료는 둘 다 남았다. 각 경우에 동일 요청을 두 번 다시 실행했을 때 최종 효과는 한 번이었다. 반대로 처리 기록부터 별도 커밋한 구현은 그 직후 종료하면 재실행이 건너뛰어져 효과가 영구 누락됐다.

**추가 확인이 필요한 조건.** 같은 ID에 다른 내용이 온 경우, ID 유효 기간, 실제 브로커의 재전달·수동 재처리, 외부 API의 효과를 다뤄야 한다. 본문에서 ACK 후 처리 ID를 지울 수 있다는 설명은 해당 메시지가 다시 처리되지 않는 전제를 갖는다. 제품의 재처리 범위를 확인하지 않고 삭제 시점을 일반화하지 않는다.

**적용 한계.** 이번 실험은 단일 로컬 DB와 순차 재실행이다. 다중 소비자 경쟁, 네트워크 분할, 브로커, 전원 손실, 이메일·결제 같은 외부 효과를 검증하지 않았다. 외부 효과까지 한 번만 발생한다고 확대 해석할 수 없다.

## 장애 대응과 에이전트 평가

### 차단기를 부착 여부가 아닌 전이와 회복으로 평가하기

**본문 근거.** Release It! [Circuit Breaker](https://learning.oreilly.com/library/view/release-it-2nd/9781680504552/f_0049.xhtml)는 정상 호출, 차단, 시험 호출, 회복 또는 재차단을 설명한다. 단순 누적 실패 수보다 시간에 따른 실패 밀도가 중요하며 대체 응답은 업무 결과를 바꾼다. 저자는 공유 상태를 위한 별도 통신이 새 실패 경로가 될 수 있음을 지적한다.

**적용 후보.** 정상→실패 누적→차단→시험 호출→회복과 재차단을 모두 검사하는 사례를 준비한다. 차단 중 실제 호출이 억제되는지, 시험 호출이 실패하면 다시 차단되는지, 회복 후 성공이 이어지는지 확인한다. 상태 전이 시점·실제 호출 수·응답·자원 점유를 증거로 남긴다.

**추가 자체 검토.** 사용자 입력 오류를 원격 장애로 집계하면 정상 서비스까지 차단할 수 있다. 어떤 오류가 집계 대상인지는 의존성의 실패 의미에 맞춰 정해야 한다. half-open 동안 여러 요청이 몰릴 때 시험 호출 수와 자원 사용이 제한되는지도 실제 라이브러리로 확인한다.

**적용 한계.** 이번에는 차단기 실행 실험을 하지 않았다. 프로세스별 상태는 저자의 권고이며 모든 분산 구조에 강제할 규칙으로 채택하지 않았다. 캐시 응답·데이터 폐기·나중 처리로 요구 의미가 달라지는 경우에는 기존 승인 조건을 확인한다.

### 같은 평가 조건에서 과업 결과를 비교하기

**본문 근거.** AI Engineering [4장 평가 파이프라인](https://learning.oreilly.com/library/view/ai-engineering/9781098166298/ch04.html)은 구성요소와 전체 과업을 함께 평가하고, 데이터 부분집합별 결과와 평가 분산을 보도록 한다. 데이터 구성에 따라 집계 순위가 뒤집힐 수 있다. 평가 데이터·rubric·심사 프롬프트와 설정도 기록 대상이다.

**적용 후보.** 에이전트 변경 전후 비교에는 같은 작업 집합과 초기 상태를 사용한다. 작업 ID별로 성공, 실패, 결과 미확인, 제약 위반을 남긴다. 시도별 성공률과 과업별 성공률을 분리하고 사용한 재시도 예산도 기록한다. 성공한 실행만 비용 계산에 남기지 않는다.

**판정 반례.** 쉬운 작업 비율을 늘리거나 재시도를 늘려 점수가 오른 것을 에이전트 개선으로 보고하는 것. 완료 문장은 성공이지만 실제 변경이 없는 사례를 평가기에 넣었을 때, 판정기가 이를 거부하는지도 확인해야 한다.

**추가 자체 검토.** 동일 사례를 반복한 변동과 사례 집합을 바꾼 변동을 분리한다. 부트스트랩은 원래 표본에 없는 실패 유형을 찾아주지 않으므로 대표 사례·알려진 실패·범위 밖 사례가 필요하다. 책의 표본 수 예시를 보편적인 출시 합격선으로 사용하지 않는다.

**권한과 한계.** 실제 에이전트 반복 평가나 AI 심사 호출은 실행하지 않았다. 합격선과 허용 행동의 의미 변경은 사용자 확인 대상이다. 검사 구현 오류를 수정하는 일과 합격 기준을 완화하는 일을 구분해 변경 근거를 남긴다.

## 적용 후보를 실제 작업으로 옮기는 형식

다음 형식은 책의 원문 양식이 아닌 자체 작성 제안이다. 적용 후보 한 개마다 작성하고, 확인되지 않은 값을 임의로 채우지 않는다.

```text
관측한 문제와 적용할 위치:
승인된 요구와 적용 규칙 버전:
원인 가설과 반증 가능한 조건:
후보 기법과 현상 유지 대안:
적용 전제 / 적용하지 않을 조건:
요구를 위반하지만 기존 검사를 통과하는 예:
변경 순서와 중간 상태:
탐지해야 할 실패 / 기대 결과의 근거:
실제 환경·명령·관측 결과:
보장한 범위 / 보장하지 못한 범위:
기준의 의미 변경 여부 / 다시 검토할 조건:
```

예를 들어 “작업 완료 기록은 있는데 결과가 없다”는 실제 문제라면, 먼저 기록과 효과의 저장 경계를 조사한다. 관련된 한 작업의 재현을 만든 뒤 원자적 처리 또는 결과 조정 방식을 비교한다. 그 작업이 해결됐다는 증거가 쌓이기 전에는 공통 실행 플랫폼으로 확대하지 않는다.

## 실험 자료와 적용 경계

[재현 코드](experiments/book_review_probes.py)와 [실행 결과](experiments/book_review_results.json)를 함께 보관했다. 실행법과 보장 범위는 [실험 안내](experiments/README.md)에 있다. Python 3.13.16, SQLite 3.53.1에서 네 가지 실험을 실행했다.

전체 독서 검토와 적용 후보 정리는 완료했다. 실프로젝트 적용은 별개다. 다음 적용에서는 문제 하나와 실제 저장소를 정한 뒤, 해당 후보의 기술 선택·동시성·복구를 대상 환경에서 확인해야 한다. 후보를 기존 승인 규칙으로 자동 편입하지 않았다.


## 전체 읽기로 추가한 우선 적용 후보

| 후보 | 적용 신호와 전제 | 잘못 적용한 반례 | 확인할 증거 |
|---|---|---|---|
| 혼합 버전 계약 | 스키마·이벤트·API 전환 | 새 서버만 통과하고 구 소비자 실패 | 구·신 reader/writer 조합, 과거 메시지·rollback |
| backfill과 후속 변경 연결 | 파생 데이터 재구축 | snapshot 뒤 발생한 쓰기 누락 | 시작 위치·동시 갱신·재시작·원본 대조 |
| 자원과 실행 수명 | timeout·취소·재시작 | 응답은 끝났지만 원격 쓰기는 계속 | 자원 회수·효과 조회·중복 방지·drain |
| 실제 완료 대조 | 여러 대상의 일괄 작업 | 일부 대상만 처리하고 완료 선언 | 요청 대상 목록과 대상별 실제 결과 |
| 권한 밖 정보의 분리 | 검색·도구 출력·캐시 | 문서 지시나 낡은 캐시가 권한을 변경 | 인증 주체별 허용 대상, 최신 권한 거부 검사 |
| 고정 평가와 실패 분류 | 모델·프롬프트·도구 변경 | 쉬운 표본이나 재시도 증가로 점수 상승 | 동일 사례·예산·버전, 부분집합·미확인 결과 |
| 규칙 변경의 명시적 제안 | 거짓 경보·누락·환경 변화 | 에이전트가 합격선을 낮춰 통과 | 실제 반례·구/신 판정 차이·사용자 승인 |

이 표는 여섯 권을 연결한 자체 적용 판단이다. 구체 근거는 전체 읽기 기록의 DDIA 5–14장, Release It! 13–17장, AI Engineering 3–10장 및 구현 기술 심화 8절에 있다. 권한 검증·규칙 승인 절차는 책의 문구를 그대로 옮긴 것이 아니라 BOSS와 합의한 개발 방식에 맞춘 조건이다.

## 원문 예제를 규칙으로 옮기기 전 확인한 문제

원문을 넓게 읽으면서 원칙뿐 아니라 코드·수식·도식의 불일치도 확인했다. 결합 책의 퇴화 삼각형 경계와 날짜 부호, 레거시 코드의 추출 후 조건 변화, 테스트 책의 추가 원소를 허용하는 속성, AI 책의 goodput 집계와 메모리 대역폭 산술 등이 해당한다. 상세 위치·관찰·한계는 전체 읽기 기록에 남겼다. 공인 정오표라고 주장하지 않으며 모든 불일치를 실행으로 검증한 것도 아니다.

적용에서는 설명의 의도 → 요구상의 불변식 → 반례 → 타깃 환경 실행을 거친다. 책의 권위나 그림의 화살표만으로 자동 규칙을 만들지 않는다. Java 최소 재현은 선언만 한 checked exception이 컴파일된다는 점과 부동소수점 0/0이 NaN이라는 점만 확인한다. 레거시 책의 모든 Java/C++ 예제를 검증한 결과로 확대하지 않는다.
