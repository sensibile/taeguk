# 에이전트 개발 사이클

작성일: 2026-10-05 · 문서 버전: 0.6

## 목적과 현재 단계

사람과 에이전트가 요구사항과 검증 기준을 합의한 뒤, 에이전트가 일감을 발견하고 작은 수정·검증·배포 후 확인을 반복하는 개발 지침을 만든다. 우선 목표는 합의된 환경과 시나리오에서 동작하는 제품이다. 운영 편의성은 별도 요구사항으로 다룬다.

현재는 문서로 원칙을 정리하는 단계다. 실제 프로젝트 적용과 검증은 아직 수행하지 않았다. 이 문서는 스킬 설치, 에이전트 실행, 자동 배포 또는 외부 시스템 접근을 승인하지 않는다.

## 대화에서 합의한 방향

- 사람이 에이전트와 목적, 요구사항, 검증 규칙을 먼저 정리한다.
- 에이전트는 승인된 규칙과 작업 권한 안에서 일감 발견, 구현, 구조 정리, 검증을 자율적으로 수행한다.
- 규칙의 추가·수정·폐기와 예외 허용은 사용자 확인을 받는다.
- 먼저 이 디렉터리에 지침을 정리하고, 실제 적용 후 스킬과 에이전트 역할로 발전시킨다.

배포까지 이어지는 루프는 목표로 합의했지만, 프로젝트별 배포 대상·허용 변경·복구 권한은 아직 정의하지 않았다.

## 사이클 초안 — 프로젝트 적용 전 구체화 필요

| 단계 | 수행 내용 | 남길 결과 |
|---|---|---|
| 1. 합의 | 목적, 범위, 비목표, 사용자 시나리오, 보존 조건, 권한을 정한다 | 요구사항과 적용 규칙 버전 |
| 2. 발견 | 승인된 기준으로 위반이나 개선 후보를 찾는다 | 위치, 관찰 결과, 재현·측정 근거 |
| 3. 선택 | 문제의 영향, 수정 가치, 위험과 범위를 평가한다 | 선택 이유 또는 보류 이유 |
| 4. 수정 | 하나의 의도로 독립적으로 검증·복구할 수 있는 변경을 만든다 | 변경 내용과 예상 효과 |
| 5. 검증 | 개선 목표 달성과 기존 기능·구조 조건 보존을 확인한다 | 대상 버전, 환경, 검사 결과와 한계 |
| 6. 반영·배포 | 프로젝트에서 승인된 대상과 절차에 따라 반영한다 | 반영 상태, 배포 산출물과 버전 |
| 7. 배포 후 확인 | 실제 배포 버전에서 합의한 시나리오와 관측 조건을 확인한다 | 완료·실패·미확인 상태, 복구 결과 |

문제 후보가 없거나 수정 가치가 부족하면 변경 없이 종료할 수 있다. 수정 횟수나 코드 변경량 자체를 성과로 삼지 않는다.

## 단계별 기준 참조 — 모두 적용 제안

세부 판정은 [규칙 목록](규칙-목록.md)에 한 번만 정의하고, 이 문서는 진행 순서를 안내한다. 규칙의 상태·변경 절차는 [규칙 관리](규칙-관리.md), 출처와 사례·기록 양식은 [서적 검토](서적-검토.md)를 참조한다.

| 단계 | 참조할 규칙 | 단계 간 연결 |
|---|---|---|
| 합의 | REQ-001~004, GOV-004 | 사용자 목표에서 구체적 사례와 전체 수용 시나리오로 연결 |
| 발견·선택 | SEL-001~005, STR-001 | 발견 신호 → 조사 → 실제 문제 확인 → 작은 수정 후보. 중요한 기능 오류를 낮은 변경 빈도 때문에 제외하지 않음 |
| 수정·정리 | DEV-002, TID-001·002·004, GOV-005 | 정리 시점과 변경 단위를 정하고 목표 달성 후 종료. 불확실성·복구 곤란이 드러나면 안전한 상태를 보존하고 재평가 |
| 검증 | DEV-001, VER-001·002, REQ-006, GOV-003 | 보존 조건(기능·계약·데이터 의미·구조 제약)과 개선 목표(해소할 문제)를 각각 확인 |
| 반영·배포 | REL-001~004·006·007 | 검사한 산출물, 대상 환경, 권한, 복구 준비를 실제 전달과 연결 |
| 배포 후 확인 | REL-005·006, REQ-006 | 합의된 관측 결과를 기록하고 실패한 릴리스와 복구 결과를 구분. 복구 후 실제 서비스 상태도 확인 |

## 완료와 중단 초안

완료는 해당 작업에 필요한 검사와 승인된 전달 단계가 끝나고, 증거가 연결된 상태다. 로컬 검증, 반영, 배포, 배포 후 확인을 각각 기록한다. 배포하지 않았거나 관측 시간이 부족하면 그 상태를 명시한다.

규칙 해석이 불명확하거나, 요구사항·계약·권한 변경이 필요하거나, 검증 자체가 불가능하면 영향을 받는 작업을 보류하고 근거를 사용자에게 제시한다. 독립적인 작업은 계속할 수 있다. 규칙을 완화하거나 검사를 생략해서 완료 처리하지 않는다.

재시도 횟수, 실행 시간·비용, 수정 범위, 배포 후 관측 기간, 복구 조건은 프로젝트별로 합의한다. 현재 공통 수치는 정하지 않았다.

## 이후 스킬과 에이전트로 구성하는 순서

1. 작은 실제 작업에 문서를 적용하고 누락·오탐·불필요한 작업을 기록한다.
2. 지침 변경은 사용자 확인을 거쳐 반영한다.
3. 반복 가능한 절차를 스킬로 묶는다.
4. 지속적인 책임과 권한이 분명한 부분을 에이전트 역할로 분리한다.

구현, 구조 정리, 검증은 역할 후보이며 별도 에이전트 구성은 아직 확정하지 않았다.

## 변경 이력

- 0.1: 개발 사이클과 권한·완료 조건의 초안 작성.
- 0.2: 일감 발견 신호와 수정 판단을 분리하는 제안 추가. 실제 적용과 규칙 승인은 아직 수행하지 않음.
- 0.3: 목표·사례·검사·증거의 연결과 상위 수용 시나리오에 관한 제안 추가.
- 0.4: 정리 시점·변경 묶음·가역성·종료 조건 제안 추가.
- 0.5: 산출물 동일성, 단계별 검증, 배포 후 확인과 복구의 구분 추가. 모두 적용 제안.
- 0.6: 단계별 상세 규칙의 반복 서술을 참조표로 정리하고 서적 근거 문서 연결. 승인 상태는 유지.
