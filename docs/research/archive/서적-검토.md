#### 에이전트 적용 해석과 한계

다음은 책의 직접 지시가 아니라 이 개발 사이클을 위한 제안이다.

- 핫스팟은 조사 후보를 만든다. 결함·계약 위반·반복 수정 부담 등의 근거를 확인한 뒤 수정 후보로 전환한다.
- 기능 오류나 중요한 요구사항 위반은 낮은 변경 빈도 때문에 뒤로 밀지 않는다. 변경 빈도는 유지보수 관점의 신호이지 제품 중요도나 안전성의 대체 지표가 아니다.
- 분석 기간, 대상 커밋, 제외 항목, 계산 방법을 기록한다. 이력이 짧거나 불완전하면 코드 검사·재현 사례·예정된 변경을 보완 근거로 삼고 한계를 명시한다.
- 에이전트가 만드는 잦은 정리 커밋 자체가 핫스팟을 강화할 수 있다. 반복적인 기계적 변경을 식별하고 이전 분석과 조건이 비교 가능한지 확인한다. 불리한 결과를 숨기기 위한 임의 제외는 허용하지 않는다.
- 코드 지표 개선은 즉시 확인할 수 있어도 향후 수정 시간·장애 감소는 즉시 입증하기 어렵다. 구현 완료와 장기 효과 관측을 분리한다.
- 공통 점수식이나 임계값은 아직 채택하지 않는다. 후보별 영향·근거의 확실성·예상 이득·수정 위험·검증 가능성을 설명해 선택한다.

#### 에이전트 적용 해석 — 제안

- 사용자에게 모든 구현 방법을 정하도록 요구하지 않는다. 에이전트가 해결책과 구체적 사례를 제안하고, 사용자가 의도·수용 조건을 확인한다.
- 에이전트가 작성한 기대값은 사용자 의도의 증거가 아니다. 승인 명세나 합의된 사례에서 도출할 수 없는 결과는 미결정으로 남긴다.
- 사례 몇 개의 통과를 모든 입력에 대한 보장으로 취급하지 않는다. 사례는 의미 합의와 회귀 검증의 출발점이며 필요한 기술·구조·통합 검사는 별도로 유지한다.
- 업무 의미와 승인 기준이 그대로인 테스트 실행 코드 개선까지 매번 규칙 개정으로 보지는 않는 방안을 제안한다. 다만 검사 범위·기대값·허용 오차·실패 판정이 달라지면 규칙 변경이다. 의미 보존이 불명확하면 사용자에게 확인한다. 이 구분 자체는 아직 미승인이다.
- UI 아래에서 실행한 업무 검사가 실제 UI 경험을 보장하지는 않는다. 화면·접근성·실제 흐름이 수용 조건이면 그 경로도 확인한다.
- 현실적인 데이터를 활용할 때는 승인된 자료와 익명화된 사례를 우선한다. 이 원칙이 실제 개인정보의 외부 전송을 허가하지 않는다.
- 읽기 쉬운 명세와 자동 검증의 연결이 목적이다. 특정 BDD 도구나 자연어 DSL을 의무화하지 않는다.

#### 시점 판단표 — 에이전트 적용 제안

| 선택 | 판단 근거 | 남길 내용 |
|---|---|---|
| 먼저 | 지금 이해하거나 구현할 부분을 명확하게 쉽게 만들며 방법을 알고 있음 | 방해 요인, 최소 정리, 이어서 할 본 작업 |
| 직후 | 방금 얻은 맥락 덕분에 지금 정리하는 비용이 낮고 재변경 가능성이 있음 | 지금 해야 할 이유와 제한 범위 |
| 나중 | 이득은 예상되지만 현재 작업과 직접 연결되지 않거나 규모가 큼 | 별도 후보와 다시 검토할 조건 |
| 하지 않기 | 현재 확인된 이득이 비용·위험을 정당화하지 못함 | 생략 이유. 새로운 요구·장애 근거가 생기면 재평가 |

책의 ‘다시는 변경하지 않는 코드’라는 강한 조건을 에이전트가 단정하기는 어렵다. 따라서 여기서는 ‘현재 근거로 정리하지 않음’으로 기록하는 방안을 제안한다. 기능 결함이나 필수 규칙 위반을 방치하는 면제 조건으로 쓰지 않는다.

#### 종료·복구·권한에 대한 적용 해석 — 제안

- 필요한 방해 요인이 해소되고 검증이 끝나면 본래 작업으로 돌아간다. 주변의 다른 정리를 발견했다는 사실만으로 범위를 늘리지 않는다.
- 독립적인 정리 작업이라면 ‘다음 기능’을 억지로 만들지 않는다. 이미 확인된 반복 변경 비용이나 승인된 구조 위반 해소를 목적·종료 조건으로 삼는다.
- 중간에 방법이 불확실해지거나 예상보다 범위가 커지면 안전한 상태를 보존하고 작업을 재분류한다. 실패 결과를 숨기거나 사용자의 기존 변경을 덮어쓰지 않는다.
- 책의 시간 감각을 에이전트의 공통 실행 제한으로 그대로 옮기지 않는다. 시간·비용·재시도 한도는 프로젝트별로 합의한다.
- 책에는 숙련과 신뢰를 바탕으로 정리 리뷰 생략을 실험하는 제안도 있다. 이를 현재 프로세스의 리뷰 면제로 채택하지 않는다. 검증·리뷰 정책을 바꾸려면 사용자 확인이 필요하다.
- 파일 수·함수 수 감소를 목표로 삼지 않는다. 추출과 인라인처럼 서로 반대인 정리를 반복하지 않도록 이전 결정 이유와 실제 효과를 확인한다.

정리 후보에는 ‘시점 선택 / 현재 방해 요인 / 예상 이득 / 최소 변경 / 동작 보존 검사 / 복구 방법 / 종료 조건 / 보류 시 재검토 조건’을 추가한다. 후보가 승인되기 전까지 자동 실행 규칙으로 사용하지 않는다.

### Continuous Delivery — 파이프라인·릴리스 선택 부분 검토

Jez Humble, David Farley. Addison-Wesley Professional, 2010.

2026-10-05 O’Reilly 로그인 세션에서 아래 부분의 본문을 확인했다. 5·10장 전체 또는 책 전체를 검토한 것은 아니다. 배포 도구의 현재 기능이나 실제 환경을 검증하지 않았다.

#### 에이전트 적용 해석 — 제안

- ‘배포할 준비가 됨’과 ‘자동으로 운영에 배포함’을 구분한다. 현재는 프로젝트별 운영 배포 권한을 정하지 않았다.
- 빌드한 산출물을 식별해 검사·배포에 재사용한다. 인터프리터 언어도 패키징된 파일 집합 등 실제 전달물을 식별한다. 환경별 설정·의존 서비스·데이터 상태가 다르면 그 차이도 기록한다.
- 빠르고 비용이 작은 검사를 앞에 두고, 필요한 통합·수용·비기능 검사를 이어간다. 실패·미실행·판정불가 필수 단계가 있으면 해당 후보를 다음 승인 단계로 보내지 않는다. 독립적인 작업까지 무조건 중단하는 공통 정책은 채택하지 않는다.
- 코드가 바뀌거나 재빌드되면 새 후보로 추적하고 관련 검증을 다시 수행한다. 비결정적 실패나 환경 문제는 원인·재시도 이력을 남기며 실패를 삭제하지 않는다.
- 스모크 테스트는 기동과 기본 의존성 확인이다. 사용자 목적의 달성이나 모든 운영 조건을 보장하지 않으므로 필요한 수용 시나리오와 관측 조건을 별도로 둔다.
- 블루그린·카나리는 선택지이며 공통 의무가 아니다. 선택 시 혼합 버전·공유 데이터 호환성, 공개 확대·중단 조건을 합의한다.
- 복구 시점·방법·권한을 미리 정한다. 데이터 복원으로 배포 이후의 유효한 쓰기가 사라질 수 있다면 자동 복원을 당연한 기본값으로 삼지 않는다. 구버전 재배포·트래픽 전환·전진 수정 중 실행 가능한 방식을 검증한다.
- 복구 명령 성공 뒤에도 서비스와 데이터 상태를 확인한다. 복구에 성공해도 실패했던 릴리스를 완료로 바꾸지 않는다.
- 운영 설정·비밀 값은 무분별하게 문서나 저장소에 복사하지 않는다. 필요한 버전·참조와 접근 권한을 기록한다.
- 오래된 도구 예시, 시간 수치, 복구를 통한 위험 제거에 관한 강한 표현은 그대로 공통 규칙화하지 않는다. 자동화와 복구는 위험을 줄이는 수단이며 무위험의 증거가 아니다.

#### 배포 후보 기록 양식 — 제안

| 항목 | 기록 내용 |
|---|---|
| 후보 식별 | 소스 커밋, 빌드 ID, 산출물 해시·위치, 규칙 버전 |
| 검증 이력 | 단계별 결과·시각·환경·검사 버전·실패와 재시도 근거 |
| 배포 대상 | 환경·설정 참조·기존 실행 버전·데이터 마이그레이션과 외부 의존성 |
| 권한과 공개 | 허용된 실행자·대상 범위·사용자 공개 조건 |
| 사전 복구 확인 | 정상 복구 지점, 절차·연습 결과, 데이터 손실·호환성 한계 |
| 실제 배포 | 배포 실행 결과, 확인된 산출물·실행 버전 |
| 배포 후 검증 | 기동·의존 서비스·핵심 시나리오 결과, 관측 기간·조건 |
| 최종 상태 | 준비됨 / 배포됨·확인 중 / 검증 완료 / 실패 / 복구 중 / 복구 확인 / 판정불가 |

위 상태는 구현된 상태 머신이 아니라 기록 초안이다. 타임아웃·공개 비율·관측 기간·허용 지표·복구 방식은 프로젝트별로 정해야 한다. 데이터 마이그레이션의 상세 절차는 12장 등 추가 검토가 필요하다.
