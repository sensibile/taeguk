# 검증 및 운영 지표의 측정과 검증 설계

2026-10-10 · v0.1 · 승인 전 제안

## 검토 결론

각 지표에 대해 목적, 사건 단위, 관찰 위치, 계산, 측정 검증, 제품 판정 조건을 연결해야 한다. 측정 도구가 값을 반환하는 것과 그 값이 올바른 것, 제품이 요구사항을 만족하는 것은 서로 다른 판단이다.

대상은 [검증 도구 선택 지침](검증-도구-선택-지침.md)과 [SRE 운영 지표 검토](SRE-운영-지표-검토.md)에 나온 지표다. 이 설계는 도구 도입이나 자동 배포 결정과 독립적이다. 제품별 임계값·허용 행동·규칙 변경은 기존 승인 절차를 따른다.

## 기존 설계에서 보완한 점

| 기존 공백 | 보완 |
|---|---|
| 지표 이름과 분모만 설명 | 원시 사건과 수집 위치, 계산 및 측정기의 검증 사례 연결 |
| 요청·재시도·업무가 혼재할 수 있음 | 논리적 업무와 각 호출 시도를 별도 식별 |
| 완료된 요청·작업만 집계할 수 있음 | 시작된 대상 집합에서 진행 중·시간초과·불명을 추적 |
| 정확성 판정 근거가 추상적 | 승인된 예제·독립 모델·데이터 대조 중 근거를 명시 |
| UNKNOWN 하나가 원인을 숨김 | 데이터 품질, 판정 상태, 판정 불가 사유 분리 |
| 복구와 배포 성공의 시점이 불명확 | 업무 회복·배포 상태·데이터 회복을 별도 사건으로 기록 |
| 경보 발생만 검사할 수 있음 | 발화·해제·중복·전달 경로까지 단계별 검증 |

## 측정 대상과 집계의 공통 정의

**대상 집합:** 어떤 기간에 시작·도착·완료·배포된 항목을 셀지 지표마다 정한다. 시간창은 기본적으로 `[start, end)`로 정의해 경계의 중복 집계를 방지한다. 완료 기준 통계와 도착 기준 품질 통계는 같은 값이 아니다. 후자의 진행 중 작업은 평가 마감 시각과 완료 기한으로 처리한다.

**식별:** `logical_operation_id`는 업무, `attempt_id`는 재시도마다의 실행을 구분한다. 배포·아티팩트·규칙·측정식 버전도 식별한다. 요청 ID나 사용자 식별자를 시계열 라벨에 무제한 넣지 않고, 상세 연계는 접근 통제된 로그·이력에 둔다.

**시간:** 한 프로세스의 경과 시간에는 단조 증가 시계를 사용한다. 다른 호스트의 사건 순서·최신성에는 동기화된 시각과 오차를 고려한다. 음수 지연·미래의 원천 시각을 0으로 보정해 정상으로 만들지 않는다.

**집계:** 합산할 수 있는 건수·분포를 먼저 합치고 비율을 계산한다. 노드별 성공률이나 백분위의 단순 평균은 전체값을 대신하지 않는다. counter reset, 샘플링, 중복 수집, 늦게 도착한 사건의 처리도 정의한다. 집계 후 수정된 값에는 평가 시점과 수정 이력을 남긴다.

**판정:** 불량이 확실한 사건과 결과를 알 수 없는 사건을 분리한다. 불명이 있는 비율은 가능한 최솟값·최댓값 또는 별도 미확인 수를 제시한다. 확실한 위반은 데이터 일부 누락이 있어도 보고하며, 누락을 이유로 위반을 지우지 않는다. 전체 통과를 주장할 근거가 부족하면 UNKNOWN이다.

Prometheus 계측 문서는 클라이언트·서버 관측, 온라인 요청, 파이프라인 단계, 배치 완료를 구별한다. 여기서는 이 구분을 도구 중립적인 사건 설계로 확장했다. [계측 공식 문서](https://prometheus.io/docs/practices/instrumentation/)

## 검증 활동과 탐지력

아래 표의 측정·검증 방법은 적용 설계 제안이다. 모든 항목을 의무 지표로 도입하지 않는다.

| ID와 지표 | 측정과 계산 | 측정값을 검증하는 방법 | 판정 한계 |
|---|---|---|---|
| V01 조건별 검사 결과 | 승인된 조건 목록을 분모로 실행 대상·결과·증거를 연결. 조건별 상태와 미실행 수를 보존 | 누락된 조건, 중복 결과, 실행 실패를 넣어 상태가 올바르게 분류되는지 확인 | 조건 목록 밖의 오류는 보장하지 않음 |
| V02 생성 입력·명령 분포 | seed·생성기 버전·입력 범위·명령/전이 빈도·유효/거부/축소 건수 수집 | 특정 명령을 생성하지 않는 생성기로 빈 경로가 드러나는지 확인. 저장한 반례 재실행 | 실행 횟수는 경로 전체 보장이나 입력 분포의 적합성을 대신하지 않음 |
| V03 오류 주입·mutation 탐지율 | 선택된 유효 변이 중 검사가 탐지한 수. 동등·실행 불가·미분류 변이는 분리 | 알려진 탐지/비탐지 오류를 넣고 분류 대조. timeout만으로 탐지 처리하는 기준도 시험 | 동등 변이를 확정하지 못하면 점수의 분모도 불확실 |
| V04 계약 확인 범위 | 지원해야 할 소비자·공급자·버전 조합 목록과 검증 결과 연결 | 목록에 미검증 조합을 넣어 누락 탐지. 의도적 호환성 파괴가 잡히는지 확인 | 조합의 수가 실제 업무 효과와 의미적 호환성을 보장하지 않음 |
| V05 상태·동시성 위반 | 호출/완료/실패/불명 이력과 승인된 모델로 위반 수·축소 반례 기록 | 허용 이력과 금지 이력을 각각 검사기에 입력. 불명 호출이 있는 이력도 시험 | 검사기의 모델 자체가 틀릴 수 있음. 구현에 원자성 가정 연결 필요 |
| V06 상태·스케줄 탐색 범위 | 초기 상태, 입력 경계, 스케줄 정책, 탐색 종료 이유·상태 수 기록 | 알려진 경쟁 반례를 포함하는 범위에서 탐지, 제외 범위에서는 미탐지임을 확인 | 상태 수 증가나 유한 범위 성공을 전체 증명으로 확대하지 않음 |
| V07 보안 발견 및 권한 조합 | 원시 발견·검증된 발견·오탐·미확인 분리. 허용/거부 행렬과 실제 데이터 효과 기록 | 검증 환경의 알려진 취약/보호 사례, 다른 소유자 접근, 경로 미도달로 탐지 및 누락 확인 | 스캔 0건은 취약점 0개가 아님. 제품 보안 검증은 별도 |
| V08 출시 후 누락 결함 | 사고/결함을 변경·규칙 버전·기존 검사와 연결. 원인·놓친 조건 분류 | 같은 결함의 중복 신고를 합치고 기존 실패 사례가 회귀 검사에 연결되는지 확인 | 신고 수는 노출·탐지·사용량에 영향받음 |

## 사용자 품질과 데이터

SRE의 SLI 사양은 사용자 결과, SLI 구현은 그 결과를 어떻게 관측하는지다. 사용자 경로에 따라 가용성·지연·최신성·정확성·처리 범위·내구성 중 필요한 것을 선택한다. [Workbook SLO 설계](https://sre.google/workbook/implementing-slos/)

| ID와 지표 | 측정과 계산 | 측정값을 검증하는 방법 | 판정 한계 |
|---|---|---|---|
| U01 업무 성공률 | 적격 논리적 업무 집합과 승인된 완료 효과를 대조. 성공/불량/진행/불명 수 기록 | 200이지만 미저장, 응답 유실 후 저장, 재시도 중복, 서버 미도달 사례로 분류 확인 | HTTP 시도 성공률과 업무 성공률을 혼합하지 않음 |
| U02 지연 충족률과 분포 | 지정 경계의 경과 시간. 성공·실패·timeout 구분. 기한 내 완료한 적격 업무/전체 대상 | 경계 직전·동일·직후 입력, 고정 시간 목록, 시계 오류·timeout으로 기대 분류 대조 | timeout을 제외한 지연 분포가 더 좋아 보일 수 있음 |
| U03 품질 저하 비율 | 계약에 정의한 정상/축소 결과를 응답 메타데이터와 결과 검사로 분류 | fallback이 실제로 사용된 응답과 정상 응답을 넣어 분류 검증 | fallback 성공이 원래 품질 목표를 충족한다는 뜻은 아님 |
| U04 데이터 최신성 | 사용 시각과 명시한 원천 갱신 시각의 차이. 적격 접근 중 허용 나이 충족 비율 | 오래된 데이터, 미래 시각, 재수집했지만 원천은 같은 데이터로 시험 | 캐시 작성 시각은 원천 최신성을 대신하지 않음 |
| U05 데이터 정확성 | 원천/승인 예제/독립 계산과 산출물 비교. 검증 범위·오류 유형·미확인 분리 | 의도적 오계산·누락·중복·변환 오류를 넣고 잡히는지 확인 | 표본 검사율과 전체 정확률은 다름. 독립 근거 없으면 정확성 미확인 |
| U06 처리 범위 | 마감까지 처리해야 하는 고유 입력 집합과 성공 산출물 집합 비교 | 입력 중 일부 누락·중복 출력·지연 도착으로 집합 차이 확인 | 단순 입출력 건수 일치는 누락과 중복의 상쇄를 놓침 |
| U07 배치·파이프라인 기한 충족 | 예정 실행 목록/도착 집합, 완료 기한, 실제 완료 시각으로 충족률 계산 | 한 번도 시작하지 않은 작업, 실패한 완료, 계속 실행 중인 작업을 포함해 확인 | 완료된 작업만 분모로 삼으면 미실행·멈춤을 숨김 |
| U08 내구성과 복구 데이터 | 저장 확인한 대상의 보존 계약에 따라 내용·버전·체크섬 대조. 복구 시험은 별도 기록 | 삭제·손상·누락을 넣어 대조기 검증. 복구한 사본에서 읽기와 업무 검사 | 읽기 장애와 영구 손실을 구별. 짧은 시험으로 장기 내구성 확정 불가 |

지연 집계에는 분포를 합칠 수 있는 표현이 필요하다. Prometheus histogram과 summary는 집계 가능성과 오차가 다르며, summary의 노드별 quantile을 합쳐 전체 quantile로 만들 수 없다. 임계값 충족률은 경계와 버킷을 맞추거나 원시 사건으로 계산한다. native histogram 사용 여부는 실제 계측·저장 호환성을 확인한 뒤 정한다. [분포 공식 문서](https://prometheus.io/docs/practices/histograms/)

## 부하와 자원

| ID와 지표 | 측정과 계산 | 측정값을 검증하는 방법 | 판정 한계 |
|---|---|---|---|
| R01 트래픽·성공 처리량 | 예정 도착, 실제 전송, 수신, 완료, 성공을 각 단위로 집계 | 알려진 요청 수와 각 관측점 대조. 발생기 제한으로 예정과 실제 차이가 드러나는지 확인 | 성공 처리량을 품질·지연과 함께 봄. 요청 감소를 개선으로 착각하지 않음 |
| R02 오류율 | 시도 또는 업무 중 하나를 명시. 유형별 실패/적격 전체. 불명은 별도 | 정상 거부·서버 실패·잘못된 200·timeout 주입으로 분류 검사 | 상태 코드 분류만으로 전체 오류를 판정하지 않음 |
| R03 사용량·사용률 | 자원별 실제 사용량과 사용 가능한 제한. CPU·메모리·디스크 의미 별도 | 제한값 변경·컨테이너 throttling·독립 OS 관측과 대조 | 호스트 여유와 프로세스/컨테이너 제한은 다름 |
| R04 포화·대기 | 큐 깊이, 가장 오래된 대기 나이, 연결/락 대기, throttling, 유입-처리 차이 | 처리기를 멈추고 큐가 쌓이는지 확인. 깊이 감소에도 오래된 작업이 남는 사례 시험 | 큐 길이 하나가 지연·정체를 모두 설명하지 않음 |
| R05 자원 오류·성장·누수 | 실패 건수, live 사용량, 정리 후 잔여량, 일정 부하에서 시간 추세 | 수명 종료 후 정리되는 정상 자원과 미정리 사례 비교. 계측 오버헤드 별도 | 캐시 성장·정상 보유를 누수로 확정하지 않음 |
| R06 재시도 증폭 | 같은 업무의 전체 시도 수/고유 업무 수, 하위 호출 증폭 별도 | 알려진 재시도 횟수와 연계 ID 대조. 응답 유실 후 중복 효과 확인 | 시도 증가의 원인이 정책 변경일 수도 있음 |
| R07 관측·검증 비용 | 실행 벽시계 시간, CPU/메모리/저장·전송 비용과 서비스 영향 | 계측 켜짐/꺼짐에서 같은 조건의 반복 비교 | 환경 변화와 계측 효과를 혼합하지 않음 |

## SLO 버짓과 경보

| ID와 지표 | 측정과 계산 | 측정값을 검증하는 방법 | 판정 한계 |
|---|---|---|---|
| A01 에러 버짓 소비 | 같은 SLI·평가창의 불량 수 / `적격 전체 × (1-SLO)` | 손계산 사례, 0건·전부 실패·초과 소비·미확인 수로 대조 | 요청 기반/시간 기반을 구별. 100% SLO에서 분모 0 |
| A02 burn rate | 관측창 불량 비율 / 허용 불량 비율 | 일정 오류, 급증, 회복 시계열로 계산·임계값 비교 | 장기창과 짧은창의 분모가 다름. 소비량 예측은 트래픽 가정 필요 |
| A03 경보 정밀도·재현율 | 중복을 합친 경보 사건과 독립 사고 목록을 승인된 연결 시간으로 대조 | 알려진 사고/비사고 시나리오로 TP·FP·FN 대조 | 사고 목록 자체가 불완전하면 실제 재현율도 미확인 |
| A04 탐지·해제·전달 시간 | 영향 시작→탐지, 영향 회복→해제, 발화→전달을 별도 측정 | 정상→오류→회복, 지연 전달·중복·전달 실패 시나리오 | 규칙 발화와 최종 전달 성공을 구별 |

SRE 경보 평가의 정밀도·재현율·탐지·해제 시간과 복수 시간창의 목적은 공식 본문을 따른다. 임계값은 예시를 복사하지 않고 제품 위험에 맞게 정한다. [SLO 경보](https://sre.google/workbook/alerting-on-slos/)

경보는 세 단계로 시험한다. ① 고정 입력으로 계산·판정 검사 ② 검증 환경의 계측과 수집 경로 검사 ③ 승인된 테스트 수신 경로에서 전달·중복 억제·회복 확인. 사용자 허가 없이 실제 사람에게 알림을 보내는 시험은 하지 않는다. Prometheus를 선택하면 `promtool test rules`로 recording/alerting rule 및 표현식을 시험할 수 있다. 이는 계측과 실제 전달 경로의 검증을 대신하지 않는다. [규칙 테스트](https://prometheus.io/docs/prometheus/latest/configuration/unit_testing_rules/)

## 측정 파이프라인 자체의 검증

모든 지표에는 아래 품질 항목을 연결한다. 이 목록은 자체 설계 제안이다.

| 항목 | 측정 | 검증 사례 |
|---|---|---|
| 수집 완전성 | 알려진 입력/원천 사건과 관측 수 대조, gap·드롭 기록 | collector 중단·네트워크 단절·미도달 요청 |
| 중복 | 고유 사건 대비 중복 수와 제거 정책 | 재전송·동일 exporter의 이중 수집 |
| 시간 신뢰성 | 시계 오차·늦은 사건·관측 지연 | 미래 시각·역순·경계 시각 |
| 계산 적합성 | 단위·분모·라벨·집계·reset 처리 | 0 분모·불균등 트래픽·counter reset |
| 표본 적합성 | 표본 수·선택 방법·누락 집단·불확실성 | 실패만 덜 수집되는 편향, 중요 사용자 집단 누락 |
| 재현성 | 원시 입력·쿼리·버전·평가 시각 보존 | 같은 입력의 재계산 결과 비교 |

표본에서 오류가 0건이어도 전체 오류가 없다고 결론 내리지 않는다. 신뢰구간·최소 표본 기준은 표본 추출 방식과 독립성에 맞게 정한다. 제품별로 이 전제가 없으면 표본 관찰 결과만 보고한다. 실시간 근삿값과 봉인한 사건 집합의 정확 집계는 표현과 허용 오차를 구분한다.

## 수집 방식 선택과 검증 주기

| 방식 | 맞는 대상 | 수집 검증 |
|---|---|---|
| 누적 counter | 요청·오류·완료 건수 | 증가 시점, 재시작 reset, 중복 collector, 알려진 사건 수 대조 |
| gauge와 timestamp | 큐·진행 중·제한값·마지막 성공 시각 | 순간값을 독립 조회와 대조, 오래된 값·작업 종료 후 잔여값 확인 |
| histogram | 지연·대기·작업 시간 분포 | 단위·경계·관측 건수, 전체 분포 합산과 raw 표본 대조 |
| 사건 원장과 join | 업무 효과·입출력·커밋·배포·사고·개입 | 고유 키·누락 링크·중복·미완료·늦은 사건 확인 |
| 통제된 실험 이력 | 장애·동시성·복구·탐지력 | 알려진 정상/실패 결과, 반복 재현, 관찰 범위 확인 |

기존 시스템에서 원시 사건이 제공되면 그것을 활용한다. 별도 도구나 자체 구현은 입력·출력·권한·비용을 비교해 결정한다. metrics는 추세와 경보에, 상세 원장은 정확한 대상 대조에 활용할 수 있지만 두 계측 경로가 같은 누락을 공유하는지도 확인한다.

측정 정의·쿼리·수집기 변경 시 고정 사례를 다시 시험한다. 실제 경계가 바뀌는 배포에서는 수집 경로와 업무 효과를 재확인한다. 정기적으로 과거 사고·실제 관측·미탐지 사례와 대조하고, 기준 변경이 필요하면 근거와 기존 사례의 판정 차이를 BOSS에게 제시한다. 검사 주기는 위험과 비용에 따라 정하며 전 항목을 매번 실행하지 않는다.

## 한 지표를 끝까지 설계하는 예

대상은 주문 생성 업무의 성공률(U01)이다. 성공은 승인된 주문이 한 번 저장되고 소유자·수량·금액이 계약을 만족하는 것이다. 이 정의 자체는 예시이며 제품 요구사항을 대신하지 않는다.

1. 도착 기준 적격 업무 집합을 만들고 각 업무와 호출 시도를 구분한다. 평가창·평가 마감·완료 기한·제외 조건을 기록한다.
2. 요청 원장, 시도 로그, 저장 결과를 업무 ID로 연결한다. 서버 로그만으로 서버 미도달을 정상 처리하지 않는다.
3. 업무별 성공·확실한 불량·불명 상태를 계산한다. 20건 중 성공 18, 불량 1, 불명 1이면 확정 성공 90%, 가능한 성공 범위 90~95%다.
4. 측정기를 정상 저장, 잘못된 200, 응답 유실 후 저장, 중복 저장, 다른 소유자 저장, 수집 누락으로 시험한다. 기대 분류는 승인된 요구사항에서 정한다.
5. 같은 구현·데이터의 의존성을 공유하지 않는 원천 원장 또는 읽기 경로로 결과를 대조한다. 독립성이 약하면 그 한계를 표시한다.
6. 확실한 불량은 보고한다. 승인된 기준이 99%인 경우 위 성공 범위의 최댓값도 기준 미달이므로 FAIL을 판단할 수 있다. 미확인 내용을 함께 남긴다. 기준이 없으면 기준 미정으로 보고한다.

이처럼 데이터 부족은 무조건 모든 판단을 막는 사유도, 통과 사유도 아니다. 어떤 결론이 현재 증거로 가능한지 판정한다.

## 계산과 판정의 고정 사례

아래는 측정기 구현 시 사용할 기대값 설계다. 운영 도구로 실행한 결과는 아니다.

1. **불균등 집계:** A는 성공 9/10, B는 0/1이면 전체는 9/11, 약 81.818%다. 비율 평균 45%는 오류다.
2. **불명 결과:** 10건 중 성공 8, 확실한 실패 1, 불명 1이면 성공률 범위는 80~90%다. 90%로 확정하지 않는다. 확실한 실패 1건도 유지한다.
3. **재시도:** 업무 하나가 세 번 실행돼 마지막에 완료하면 업무 성공은 1/1, 시도 성공은 1/3, 증폭은 3이다. 두 성공률은 다른 지표다.
4. **집합 대조:** 입력 A/B/C, 출력 A/A/C는 건수가 같지만 B 누락과 A 중복이다.
5. **기한:** 5건 중 3건 기한 내 완료, 1건 기한 뒤 완료, 1건 기한 지나 미완료면 충족은 3/5다. 완료된 4건을 분모로 쓰지 않는다.
6. **버짓:** SLO 99.9%, 전체 100,000, 불량 200이면 허용 100, 소비 200%, 같은 창 burn rate 2다. 전체 0건이면 계산 불가다.
7. **시간 경계:** 평가창 끝과 같은 시각의 사건은 다음 `[start,end)` 창에 속한다. 양쪽에 중복하지 않는다.
8. **계산 근사:** raw count가 정확해도 scrape 기반 rate/increase는 창 경계의 근사 차이가 생길 수 있다. 정확 사건 집계와 무조건 정수 일치를 요구하지 않고 적용 방식의 오차를 시험한다. [Prometheus increase 정의](https://prometheus.io/docs/prometheus/latest/querying/functions/#increase)

## 에이전트에게 전달할 계약

```yaml
measurement:
  metric_id: <catalog id>
  definition_version: <version>
  population: <service, environment, cohort, eligibility>
  event_unit: <logical operation, attempt, record, deployment>
  observation_boundary: <start, end, collector>
  window: <start inclusive, end exclusive, evaluation cutoff>
  raw_evidence: <immutable event or series snapshot reference>
  calculation: <query or formula with version and units>
  unknown_policy: <pending, timeout, missing, late events>
validation:
  oracle: <approved example, independent ledger or model>
  known_cases: <normal, bad, missing, duplicate, boundary>
  checks_result: <measurement verification evidence>
quality:
  status: <VALID, DEGRADED, UNAVAILABLE>
  counts: <eligible, good, bad, unknown, excluded>
  gaps: <collection and population gaps>
  uncertainty: <range, approximation or sampling limits>
decision:
  rule_version: <approved target and version>
  result: <PASS, FAIL, UNKNOWN, NOT_RUN, NOT_APPLICABLE>
  reasons: <confirmed violations and unresolved conditions>
  allowed_action: <existing authorization>
```

데이터 품질 상태와 제품 판정은 별도 필드다. `DEGRADED` 데이터에서도 확실한 위반은 FAIL로 보고할 수 있다. 표본 부족·판정 기준 없음·관측 누락은 서로 다른 UNKNOWN 사유다. 결과를 개선하려고 사건을 제외하거나 임계값을 바꾸는 일은 규칙 변경으로 분리한다.

## 실제 적용 순서와 검토 범위

먼저 핵심 업무 하나를 골라 필요한 지표 ID만 선택한다. 승인된 행동·실패 효과에서 정의를 작성하고, 기대값이 알려진 사건으로 수집기·계산기·판정기를 각각 검증한다. 이어 검증 환경에서 실제 경로를 대조한 뒤, 제품 관측에서 샘플·누락·비용을 확인한다. 측정이 유효해도 제품 기준이 승인되지 않았으면 결과와 제안 기준을 분리한다.

이번 재검토는 기존 두 지침의 모든 지표군을 측정·검증 설계로 확장했다. 공식 자료는 SLO와 경보 정의, 현재 DORA, Prometheus 계측·분포·규칙 테스트 관련 구간을 확인했다. 표의 상세 사건 모델과 검증 사례는 그 위에 구성한 자체 제안이다. 추가 후보 도서의 본문 전체 검토나 제품용 측정기의 실행 결과로 표시하지 않는다.
