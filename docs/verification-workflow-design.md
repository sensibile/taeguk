# 검증 계획을 중심으로 연결하는 Taeguk 개발 흐름

## 목적과 이 문서의 상태

BOSS가 승인한 흐름은 제품 목적·요구 → 설계 → verifier의 검증 계획 → 구현 → 도구·지표 검사와 LLM 검토 → 수정·재검증이다. 검증 계획은 구현자와 검증자의 공통 목표이며, 원래 요구를 대체하지 않고 그 요구와 설계를 확인 가능한 항목으로 연결한다.

이 문서는 역할·스킬·설치 구성의 보완 설계다. 구현이나 이번 변경에 대한 실행 검증 계획은 아직 아니다. 다음 검증 계획자가 원 요구와 이 설계를 읽고 별도 계획을 작성한다. 현재 제품 효과 개선은 가설이며 역할 수, 모델 지정, 문서 작성으로 입증하지 않는다.

기준 소스는 `37ad82416a29252631899a17773c22de56ba3373`, 작업 트리는 `feat/verification-workflow`다. 이번 작업은 local-only이며 원격 조회·push·PR·실제 설치·앱·DB 변경을 포함하지 않는다. 일반 자동 orchestration 엔진, 새 API, 모델 호출 플랫폼도 범위 밖이다.

## 역할과 모델 배치

> 2026-10-25 변경: BOSS 지시로 아래 역할별 모델·effort 고정을 해제했다. 현재 역할 TOML은 모델을 지정하지 않고 실행 환경을 상속한다([구성과 실행 계약](architecture.md)). 아래 표와 인계 문구는 2026-10-11 설계 당시의 기록으로 보존한다.

기존 역할 여섯 개 중 세 개를 보완하고 세 개를 추가한다. 모델 이름과 reasoning은 각 역할 TOML의 최상위 `model`, `model_reasoning_effort`에 둔다. 전역 설정은 변경하지 않는다.

| 역할 | 모델 | effort | 책임과 출력 |
| --- | --- | --- | --- |
| `taeguk_coordinator` | 기존 상속 유지 | 기존 상속 유지 | 원 요구·승인 범위·단계 인계를 유지하고 결과를 요구별로 종합한다. |
| `taeguk_designer` (신규) | `gpt-6-astra` | `medium` | 목적·요구·보존 조건을 바탕으로 작은 변경 설계와 설계 인계를 작성한다. |
| `taeguk_verifier` (기존 보완) | `gpt-6-sol` | `medium` | 구현 전에 원 요구와 설계를 읽고 검증 계획을 작성·관리한다. 검증 결과의 누락과 재검증 범위를 계획에 연결한다. |
| `taeguk_implementer` | `gpt-6-luna` | 미지정 | 인계받은 설계와 계획을 기준으로 구현·수정하고 정확한 산출물 버전과 실행 근거를 반환한다. |
| `taeguk_tool_verifier` (신규) | `gpt-6-luna` | 미지정 | 계획에 지정된 도구 검사·수치 대조·재현을 수행하고 실제 관측과 누락을 반환한다. |
| `taeguk_llm_reviewer` (신규) | `gpt-6-astra` | `low` | 원 요구·설계·산출물·증거를 대조해 의미 적합성, 범위 누락, 추론의 근거를 검토한다. |

미지정 effort는 키를 생략한다. 임의로 low나 medium을 선택하지 않는다. BOSS의 LLM 검증 표현 `light`는 지원되는 설정명 `low`로 반영한다. 현재 runtime 지원 및 TOML 필드 근거는 부모 작업의 공식 문서 확인을 인계받았다. 이 설계 단계에서는 모델 호출을 실행하지 않았다. 공식 근거: [Custom agents](https://learn.chatgpt.com/docs/agent-configuration/subagents?surface=app).

`taeguk_structure_reviewer`, `taeguk_outcome_observer`, `taeguk_rule_reviewer`의 모델·책임은 유지한다. 역할 정의는 자동 실행 예약이나 위임 허가가 아니다. 실제 작업에서 허용된 위임 범위 안에서 사용한다. 역할 TOML은 권한을 강제하는 보안 장치도 아니다.

## 단계별 인계와 되돌림

1. Coordinator는 목적 가설, 승인된 원 요구와 규칙 버전, 보존 조건, 범위, 대상과 권한을 정리한다. 사용자만 정할 의미가 비어 있으면 미결정으로 남기되 독립적으로 진행 가능한 부분은 계속한다.
2. Designer는 요구에 맞는 변경 경계, 책임, 데이터·상태 영향, 대안과 제외 범위를 설계한다. 아직 쓰지 않은 코드의 성공을 주장하지 않고 `DESIGN_HANDOFF`를 verifier에게 준다.
3. Verifier는 원 요구와 설계를 함께 읽어 검증 계획을 작성한다. 설계의 누락을 발견하면 designer에게 되돌리고, 원 요구 의미의 변경이 필요하면 coordinator를 통해 BOSS 확인 사항으로 남긴다. 계획이 구현 코드의 결과를 보고 기대값을 역산하는 방식이 되지 않게 한다.
4. Implementer는 해당 설계·계획 버전을 받아 승인 범위 안에서 구현하고 구현에 필요한 검사도 수행한다. 계획이 실제 경계를 잘못 이해했다면 근거를 붙여 정정 요청한다. 현재 구현을 통과시키기 위한 기준 변경은 하지 않는다.
5. Tool verifier와 LLM reviewer는 같은 정확한 산출물 버전을 대상으로 자신의 항목을 확인한다. LLM 검토가 도구 결과에 의존하면 결과 인계를 기다린다. 독립적으로 확인 가능한 항목만 병행할 수 있으며 자동 병행 실행을 요구하지 않는다.
6. 실패·누락·충돌은 요구 ID와 검사 ID를 붙여 반환한다. Implementer가 수정하고 verifier가 변경 영향에 따라 필요한 재검증 범위를 정한다. 관련 산출물·환경·기준이 바뀌면 이전 PASS를 자동 승계하지 않는다.
7. Coordinator는 원 요구별 결과와 남은 조건을 종합한다. 산출물 완료, 설치·전달, 실제 사용자 효과를 구분한다. 필수 항목의 미확인은 승인된 기준에 따라 완료를 제한하며 임의의 새 전역 차단 조건을 만들지 않는다.

## 검증 계획의 정보 구조

기존 evidence packet을 바탕으로 작성하며 새 JSON schema나 DB를 만들지 않는다. 간단한 과제는 짧은 표로 충분하다. 다음 정보가 서로 연결되어야 한다.

| 정보 묶음 | 담을 내용 |
| --- | --- |
| 계획 식별과 입력 | 계획 버전, 목적·요구 ID와 원문 참조, 승인 기준·규칙 버전, 설계 참조, 대상 산출물·환경·데이터 버전 |
| 검증 항목 | 검사 ID, 연결 요구 ID, 확인할 주장, 기대 결과와 oracle 출처, 필수 여부의 승인 근거 |
| 관측과 판단 방법 | 도구·LLM·혼합 구분, 실제 실행 또는 읽을 자료, 담당 역할, 필요한 환경·권한, 원시 증거 보관 위치 |
| 확인 범위와 한계 | 포함·제외 범위, 교차 관측 선택 이유, 공유 가정, 독립성 한계, 예상 누락 또는 미확인 |
| 결과와 후속 행동 | 상태와 이유, 실제 관측·판단 근거, 증거 참조, 문제의 영향, 수정 또는 추가 확인, 재검증 대상 |

구현 전에는 산출물 commit이나 실행 결과가 없을 수 있다. 없음을 표시하고 이후 정확한 버전에 연결한다. 아직 실행하지 않은 검사를 PASS로 채우지 않는다. 계획 정보 구조는 필수 판단 정보를 설명하며 문서 분량이나 검사 개수를 강제하지 않는다.

도구 항목은 실행 결과·상태 관측·수치 비교처럼 외부에서 확인할 수 있는 주장이다. LLM 항목은 요구를 충분히 다루는지, 설명과 구현의 의미가 맞는지처럼 맥락 해석이 필요한 주장이다. 혼합 항목은 LLM이 위험이나 원인 가설을 제시하고 실제 재현·관측으로 그 주장을 확인하는 경우다. 혼합 결과에서 추론과 관측을 분리하고 재현하지 못한 주장을 확인된 사실로 올리지 않는다.

PASS·FAIL·UNKNOWN·NOT_RUN·NOT_APPLICABLE은 기존 의미를 유지한다. UNKNOWN은 근거·기준·해석 부족 등을 이유로 구분하고 NOT_RUN은 실행하지 않은 이유를 남긴다. NOT_APPLICABLE은 승인된 범위에 비추어 적용되지 않는 근거가 필요하다. LLM 검토의 PASS도 명시한 검토 범위의 판단이며 외부 실행이나 실제 효과 증거로 바뀌지 않는다.

역할·모델 차이만으로 독립성을 선언하지 않는다. 동일한 요구 오해, 동일 원본, 동일 생성 테스트를 공유할 수 있다. 필요한 교차 관측은 다른 oracle·관측 층·자료·구현에 근거하고 상관관계를 기록한다. 두 검증 결과가 충돌하면 평균이나 다수결로 통과시키지 않고 해당 주장의 기준과 증거를 다시 조사한다.

새 스킬은 만들지 않고 기존 10개 절차를 연결한다. Designer는 work-contract를, 계획자는 plan-cross-verification을, 도구 검증자는 계획과 필요한 verify-measurement를, LLM 검토자는 work-contract의 completion-review 참고를 사용한다. 증거 packet의 기존 버전·범위·원시 자료 계약을 재사용하며 모든 스킬의 공통 참고를 불필요하게 복제 수정하지 않는다.

현재 installer는 `codex/agents/taeguk_*.toml`을 자동 수집하고 TOML을 복사한다. 새 역할 추가와 모델 필드는 이 경로로 전달 가능하므로 설치 알고리즘 변경은 기본적으로 필요하지 않다. 기존 6개 역할을 삭제·이름 변경하지 않아 receipt의 소유권 연결도 유지한다. 설치 관련 회귀 확인 범위는 검증 계획자가 정한다. 실제 사용자 home 설치는 이번 설계 작업에서 실행하지 않는다.

`docs/direction.md`의 모델 상속 문구, `docs/codex-installation.md`의 모델 미변경 문구, 변경 역할의 상속 문구는 역할별 모델 지정과 충돌하지 않게 고친다. 전역 설정과 명시하지 않은 역할은 계속 상속한다. 역사적 초기 역할 수는 당시 기록임을 분명히 하거나 현재 구성과 분리한다.

규칙 본문·registry, Rust CLI 동작·schema, Elixir 앱·API·DB는 이 설계로 바꿀 필요가 없다. 승인 기록을 보완할 경우 이번 지시의 실제 범위만 기록하고 기존 규칙 의미를 확대하지 않는다.

## 도구 한계와 완료 주장

`taeguk measure`는 제공된 건수를 계산하며 수집 완전성을 확인하지 않는다. `taeguk verify`는 파일 동일성과 선언 상태를 대조한다. `taeguk audit`는 요구·검사 ID와 증거 파일 연결을 선택적으로 점검한다. 어느 도구도 검증 계획 전체를 실행하거나 LLM 의미 검토, 승인 진실성, 실제 효과, 전체 완료를 판정하지 않는다. CLI 성공 exit와 검사 통과도 구분한다.

설치 receipt/hash 일치는 파일 복사 상태의 근거다. 새 세션에서 역할 발견, 지정 모델의 실제 실행, 실제 과제에서의 흐름 적용과 제품 효과는 별도 관측이다. 이번 구성 변경의 검증과 이후 제품 파일럿의 효과 검증을 혼동하지 않는다.

## DESIGN_HANDOFF

다음 담당은 `gpt-6-sol` / `medium` 검증 계획자다. 입력은 이 문서의 WF-01~08, 승인된 사용자 흐름·모델 지시, 원 요구, 기준 소스와 현행 규칙이다. 이 문서의 변경 목록만을 요구의 전부로 취급하지 않는다.

다음 출력은 구현 전 검증 계획이다. 이번 구성 변경에 맞는 oracle·관측·실행 범위·누락·상태를 정하고, 도구 검사와 LLM 검토가 각각 무엇을 확인하는지 명시한다. 계획이 준비되면 구현자가 그 계획을 입력으로 작업한다. 실행 증거 없는 계획 항목은 미실행으로 남긴다.

설계자는 `worktree-first-dev`, `taeguk-work-contract`를 실제 읽고 적용했다. `taeguk-plan-cross-verification`과 관련 참고는 인계 구조를 파악하기 위해 읽었으며 별도 실행 검증 계획을 대신 작성하지 않았다. 관련 역할·설치기·CLI 설명과 현행 규칙을 소스로 확인했다. 설계 단계에서 CLI 실행, 설치 실행, 모델 실행, 앱 실행은 하지 않았다. 문서 검사 결과와 최종 commit은 담당자의 인계 보고에 기록한다.
