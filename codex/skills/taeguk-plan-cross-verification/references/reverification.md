# 수정 후 재검증과 실행 인계

수정 후에는 고정된 검증 계획을 다시 쓰지 않고 변경분과 근거를 연결한다. 이 절차는 검사 기준·권한을 줄이지 않는다.

## 영향 범위와 증거 재사용

수정 diff에서 동작, 호출자, 공유 helper, schema, 설정, fixture 및 oracle의 영향을 따라 필요한 검사 ID를 선택한다. 파일이 같다는 이유만으로 관련 검사를 생략하지 않는다. 각 ID에 `rerun` 또는 `reuse`를 기록하고, 기존/현재 대상 버전, 근거 위치, 관련 환경·데이터·기준의 동일성 또는 차이, 재사용 이유와 한계를 붙인다. 범위가 불명확하면 해당 검사를 다시 실행한다. 공유 상태·통합 경계가 넓게 바뀌었거나 필수 gate가 요구하면 전체 검사를 실행한다.

도구로 실행할 항목, LLM으로 의미를 검토할 항목, 양쪽 근거가 필요한 mixed 항목을 유지한다. UNKNOWN은 방법·도구·환경을 개선할 수 있을 때 다시 열고, 방법이 바뀌지 않았는데 같은 불확실한 probe를 반복하지 않는다. 승인된 필수 항목을 미확인 상태로 남긴 채 완료하지 않는다.

## 공유 자원과 실행 handle

fixture를 바꾸는 테스트와 서버·HTTP·SQL probe가 같은 DB나 포트를 쓰면 실행 소유자를 정하고 직렬화한다. 실제 명령을 시작한 즉시 PID/session handle, 자원, 로그 경로를 기록한다. 실행 도구가 session을 반환하면 그 handle로 완료 또는 실패를 확인한 뒤 다음 의존 실행을 시작한다. 짧은 poll에서 출력이 없다는 이유로 같은 명령을 다시 시작하지 않는다. 자원을 반환할 때 남은 프로세스와 cleanup 결과를 알린다. 한 소유자가 수행하는 정상 HTTP 시나리오의 서버와 probe는 함께 동작해야 한다. 이 종속 동작마다 같은 lock을 중복 획득하지 않고, 다른 fixture 변경 검사와 시나리오 전체를 분리한다.

같은 Unix 자원에서 서로 충돌할 수 있는 최상위 foreground 검사는 [실행기](../scripts/run_exclusive.py)로 실행한다. 기존 실행 환경이 동일 자원의 직렬화를 이미 보장하면 그 방식을 사용하고 근거를 기록한다. 같은 실제 자원은 모든 참여 worktree에서 **동일한 절대 lock 경로**를 선택한다. 경합이면 명령을 시작하지 않고 exit 75를 반환한다. 자동 재시도하지 말고 기존 소유자와 handle을 확인한다. lock 파일은 지우지 않는다.

```sh
python3 <skill-directory>/scripts/run_exclusive.py \
  --lock /private/tmp/taeguk-<project>-<database-port>.lock -- \
  env MIX_ENV=test mix test
```

실행기는 명령의 종료 코드를 전달하고 INT/TERM을 자식 process group에 전달한다. 부모가 갑자기 종료돼도 직접 자식이 상속한 lock을 유지한다. macOS/Linux의 협조적 flock이므로 실행기를 우회한 명령, 다른 lock 이름, 자식이 상속 FD를 닫는 프로그램은 차단하지 못한다. background/daemon 명령은 지원 범위가 아니다. DB·프로세스 소유권 확인을 대체하거나 실행 권한을 부여하지 않는다.

## 결과 먼저, 설명은 변경분만

각 검사가 끝나면 ID·상태·대상 버전·실제 값/exit·원시 근거·한계를 바로 공유한다. 맡은 실행을 끝낸 검증자는 DB/서버 소유권을 반환한다. 긴 보고서 완성을 기다리며 실행 자원을 잡아 두지 않는다. 소스 검토는 도구 실행과 독립적으로 진행하고, tool/mixed 완료 판정은 실제 결과를 받은 뒤 내린다.

현재 판정 표는 한 곳에서 갱신하고 이전 실행/실패 raw와 버전은 보존한다. 재검증 인계에는 수정 diff, 영향 ID, 새 결과, 재사용 근거, 남은 FAIL/UNKNOWN/NOT_RUN만 전달한다. 전체 설계·계획·모든 원시 로그를 매번 복제하지 않는다. 원시 파일은 위치로 참조하고 필요한 부분만 읽는다. 의미 판정에 필요한 입력은 생략하지 않는다.

새 코드·실패·기준/환경 변화가 없으면 보고서 정정만으로 제품 검사를 다시 실행하지 않는다. 결과 충돌은 해당 ID의 oracle과 관측 층을 대조해 해결하고, 기준을 바꿔야 하면 기존 승인 절차를 따른다. 별도로 약속한 외부 benchmark는 유지하되 내부 검증과 공통 범위를 연결해 중복을 식별한다.
